## Architektonický přehled

- **Next.js** tvoří serverové API a aplikaci; **SQLite** je kanonický serverový stav a **Dexie/IndexedDB** lokální cache se synchronizací a konflikty. Webová PWA je instalovatelná na Mac a iPhone.
- **PACT** znamená Projects, Agents, Context a Tools; **Context Resolver** filtruje minimální oprávněný kontext a typovaný **Tool Registry** omezuje akce.
- **Attention Engine** vyhodnocuje stabilní signály a jejich stav; produktová pravidla, meze a deduplikaci definuje [produktový kontrakt](PRODUCT.md#attention-contract--target-requirement).
- **Planning Engine** pracuje s ověřenou čerstvostí kalendáře a nepovažuje neznámé časové bloky za volné.
- **Action Engine** dodržuje `intent → context → allowlisted tool → proposal → approval → execution → audit → guarded Undo`; API a storage vynucují revize, idempotenci a hranice workspace.
- **Privacy-first:** cílové Osobní a Sdílené jsou oddělené hranicí oprávnění odvozenou z Oblasti, `Můj plán` je jen osobní agregovaný čtecí rozsah; citlivé či neověřené claims nejsou automatickým důkazem ani povoleným kontextem pro agenty.
- Stav implementace je důsledně oddělen od **target specification** v níže uvedených oddílech. Při rozporu UI návrhu s oprávněními a integritou dat platí přísnější bezpečnostní kontrakt.

## Current MVP

- Responsive desktop and mobile task workspace
- Inbox, Today, Overdue, Upcoming, Anytime, Someday and Completed views
- Projects, areas, notes, relations and relation-aware search/context
- Persistent Personal and Shared workspaces, scoped views, and an All my work aggregate
- Task dates, deadlines, priority, notes, checklist, recurrence and history
- Quick Capture with Czech today/tomorrow/date parsing, priority tokens and a reviewable Lumi suggestion for project, area, priority, effort and the first suitable free calendar block
- Manual Context Inbox for pasted meeting, email or Copilot summaries. It creates an in-memory preview, matches existing workspace entities, and may suggest a person waiting for a result. The owner selects an existing person or explicitly creates one, then separately saves the relationship as a protected reviewable claim. Ambiguous lines remain literal proposals. Action items remain editable drafts until reviewed in Quick Capture.
- First-class people and organizations in the Context workspace, with workspace-scoped names, duplicate warnings, revision-safe rename/archive, change history and searchable relationships to tasks and projects. Each relationship remains an independently reviewed claim; archiving a person or organization removes its claims from AI eligibility without deleting history.
- SQLite server source of truth with local IndexedDB cache and conflict-aware sync
- When the session ends on the server (it lasts seven days) the app returns to the sign-in screen and says so, instead of looking offline. The local copy and unsent changes are kept and sent after signing in again; only an explicit sign-out clears them.
- Signing out clears the browser's local copy (IndexedDB data, unsent-change markers, remembered workspace) and reloads; other open tabs follow. Unsent changes are synchronized first; if that fails the user chooses whether to discard them. Without a reachable server sign-out is refused and nothing is removed, because the session cookie cannot be cleared offline. A wipe that cannot finish is completed on the next start. The local placeholder for the Personal workspace carries timestamp 0 so it never wins a merge against the server copy. Push subscriptions and device preferences (theme, language, start view) are kept.
- Daily/manual/safety backups (full database copies; older JSON backups stay restorable) and tombstones for deletion sync
- Installable PWA with an offline shell. Started without a connection, a browser that has synchronized before and was not signed out shows the data it holds, marked as offline, instead of only the access screen (owner decision 2026-10-09); changes made meanwhile wait on the device. Access is checked again in the background (on connection, focus and every 15 seconds); if the server then says the session has ended, the sign-in screen replaces the app and the waiting changes are sent after signing in. A browser without such data stays on the access screen.
- The address carries the open view (`/?view=Today`; the start view has the plain address), so Back, Forward and reload keep the place. It never carries a workspace, a search text or a record id; the `?task=` id from a notification link is removed from the address once the task is open, or once a completed synchronization shows the task does not exist.
- Web Push reminders delivered by a server scheduler while the PWA is closed
- Attention notifications: one Web Push when a task deadline comes within 48 hours and one when it passes, evaluated by the server every five minutes with the same rules as Home. Tasks only, never projects. Each item is announced once; snoozed and dismissed items stay silent; nothing is sent between 22:00 and 08:00 local time (held until morning) and at most three are sent per rolling 24 hours. The first pass after enabling records what is already on Home as known instead of announcing a backlog. The message shows a short task title and the reason, including on the lock screen (owner decision 2026-10-07), and opens the task. It needs the reminders switch on and a subscribed device; the message text is Czech. Delivery is at most once per item: with no subscribed device the item is recorded as not delivered and is not sent later; delivery is tracked per subscribed device, so a device whose send failed is retried on later passes (three attempts, never at night) without notifying the devices that already received the message, and a device whose subscription has expired is dropped; a pass interrupted by a restart is not resent. An item that was snoozed is announced when the snooze ends if it had not been announced before. Items held by the daily limit are sent later while their condition lasts. Quiet hours and the daily limit are fixed values for now; the urgent exception, per-rule settings, pause, in-app delivery state and push for waiting follow-ups (shown on Home only) and calendar rules from the target contract are not implemented.
- OS-level urgent-task badges for installed iOS/iPadOS Home Screen and macOS Dock web apps
- Server-verified on-demand priorities in chat and an approval-based task action loop with audit and Undo
- Home now uses a server-evaluated Attention foundation for overdue and soon deadlines, waiting follow-ups, tasks whose planned day has passed, projects without a next action, and idle projects. The last evaluation of each workspace is kept in the browser (owner decision 2026-10-09): until the server has evaluated again, Home shows it marked as a saved copy (or as out of date when the server cannot evaluate), at most 50 items per workspace, with snooze and dismiss disabled; it is also shown, marked as offline, when the app starts without a connection; signing out removes it with the rest of the local copy. A waiting follow-up comes from an explicit waiting task (marked in the task detail with who or what it waits for and an optional follow-up date): it leaves the Inbox (owner decision 2026-10-09), is left out of the day plan, does not carry over to the next occurrence of a repeating task, and returns at the start of the follow-up date in the user's time zone, or 7 days after it was marked when there is no date; waiting-on relationships from reviewed claims are not used yet. Candidates have stable identities, deterministic ordering, explicit reasons, source revisions and evaluation freshness. The five highest-ranked items are shown first; snooze and dismiss are stored in SQLite with content-free lifecycle history, expire or resurface when the underlying condition changes, and are shared across devices. Calendar conflicts and capacity risk remain planned rules and are disclosed as unavailable rather than inferred.
- Lumi's day plan previews ranked tasks in a mobile-friendly timeline and explains why each item matters now. Ranking can use confirmed, current, non-sensitive task/project importance and waiting-party claims in addition to deadlines, priority, calendar availability and measured duration. Exact blocks require a fresh connected calendar and avoid existing planned tasks. Accepting a block uses a server-side, single-task proposal with a current-revision and overlap check, audit history and Undo; it does not change the task's due date. When the calendar is missing or stale, the plan lists tasks without claiming exact free times. Decisions and manual time changes are recorded as task planning feedback.
- Read-only private ICS calendars with normalized recurring events, busy-time merging and free-window planning
- Deterministic threat detection with Web Push fallback and a least-privilege Hermes Telegram outbox

## Project context (B1, owner decision 2026-10-22)

Proposal: [proposals/2026-10-zjednoduseni-ui.md](proposals/2026-10-zjednoduseni-ui.md) §4.3. A project carries `properties.context = { why, goals, doneWhen, provenance, proposalId?, updatedAt }` (`lib/project-context.ts`, one definition for client, server, migration and assistant).

- **Validation.** `why` ≤ 600 characters, `goals` ≤ 5 items of ≤ 200, `doneWhen` ≤ 300, `provenance` is `owner` or `lumi-approved`, `proposalId` (optional, ≤ 240) links an approved Lumi proposal to its audit, `updatedAt` a finite number. The server (`validateSnapshot` in `lib/server-store.ts`) refuses a project whose `context` is present and invalid with the same "invalid entity" error as other records; the client (`lib/sendable.ts`) holds such a record back with reason `context`, so one bad record never blocks the save of the rest. The editor enforces the limits with `maxLength` and never writes more.
- **Migration.** The named migration `2026-10-project-context-from-goal` (`lib/schema-migrations.ts`) copies a non-empty `properties.goal` into `context.doneWhen` (`provenance: owner`, `updatedAt` = the project's own) for projects that have no `context`. `goal` is **kept** and mirrored by every owner save of the context, so an older binary or device still reads it for one version; it is removed in the version after. A goal longer than 300 characters is **never truncated**: such a project gets no `context`, `readProjectContext` shows the full `goal` as "Hotovo, když", and the editor refuses to save it ("Zkraťte na 300 znaků") until the owner shortens it. The record's own `updatedAt` is not changed (the move is not an owner edit and creates no conflict), the store revision is bumped once so clients pull the record. The migration is idempotent and also runs on restored backups (`applySchema`); older backups and JSON backups without `context` read their `goal` as "Hotovo, když" (`readProjectContext`), so nothing depends on the migration having run.
- **When it runs and the backup.** The migration runs when the database is opened (`applySchema`), i.e. at the first start of the new build, never earlier. The pre-migration backup is the deploy's validated pre-start backup: in `deployment/deploy-safe.sh`, step "=== KONZISTENTNI ZALOHA ===" stops the service, copies the data directory, verifies the copy (`cmp`, `diff -qr`, `check-data.mjs`) and only then sets `BACKUP_VALIDATED=1`, before "=== FAST-FORWARD A BUILD ===" and the restart that opens the database. Restoring that backup returns the data before the migration.
- **Older clients.** An older client edits only `goal`. `mergeEntity` (client and server) copies a changed `goal` into `context.doneWhen` when `doneWhen` did not change and the goal fits 300 characters; `goal` is not reported as a conflict of its own (the `context` notice covers a concurrent edit).
- **Privacy and authorship.** `context` has no author or sensitivity flag yet, so it can only be treated as the owner's text in the single-owner product. `providerContext` therefore sends project context only for a resolved workspace and never for the "all" scope. B2 and the multi-user phases must add an author/role (and a sensitivity) to the context before non-owner text may be called "owner" or sent to a provider.
- **Merge.** `context` is merged **as one object** by the generic three-way field merge (`lib/field-merge.ts`): a change on one side is taken; a change on both sides is a conflict, the newer record wins whole and the replaced context is kept as a `properties.context` sync notice that can be restored. Field-by-field merging was rejected: the three fields describe one statement, and a mix of two authors' sentences would be a text nobody wrote. `goal` merges like any property, so a concurrent edit may raise a second notice for the mirror.
- **Assistant and planning.** `providerContext` (`lib/ai-provider-context.ts`) adds `ownerContext` to each project in the canonical entities (why, goals, doneWhen, provenance "owner statement" or "owner-approved Lumi proposal"); it is an owner statement, not a model guess, and is absent when the owner wrote nothing.
- **Not yet built (B2).** "✦ Lumi navrhne": Lumi may propose context only through a PACT proposal and the approval sheet, never by direct write; the approved write sets `provenance: lumi-approved` and `proposalId`.

## PACT architecture

AI Executive uses PACT (Projects, Agents, Context, Tools) as the target operating model for the Personal AI OS. PACT is an architectural layer over the existing local-first task model, not a replacement for it.

### P — Projects

Existing Areas, Projects, Tasks, Notes and Relations form the P layer and retain their IDs, workspace boundaries, recurrence, history and offline/sync behavior. Projects can reference project-scoped context, preferred agents and allowed tools. All my work remains an aggregate read view, never a write target.

### A — Agents

Agents are reusable, versioned definitions of repeatable AI work, not unrestricted chatbots. Each agent declares its purpose/instructions, permitted context scopes, tool capabilities, workspace/project scope, trigger mode, output contract and mutation/approval policy.

Initial built-ins: Executive Assistant, Inbox Processor, Project Manager, Researcher and Meeting Prep. Deterministic ranking remains a safe fallback and validation layer.

Agents never receive provider credentials or bypass authorization. Model-proposed actions always pass through the Tool Registry and policy layer.

### C — Context

Context is a first-class structured layer over the existing canonical entities, tasks and notes. The next specification is [Personal Context Graph v2](#personal-context-graph-v2--target-specification): evidence-backed claims and typed relations, claim-level review, durable revision history and an Obsidian-inspired owner workspace.

Supported PACT scopes remain me, work, family, rules, project and workspace. Scope is not a substitute for workspace authorization or sensitivity. Owner statements, imported evidence and AI inferences remain distinguishable; confirmation applies to an individual claim and never implicitly completes a task or verifies every fact about a person.

The Context Resolver builds the minimum permitted bundle for each agent run from the canonical SQLite state. It enforces workspace/project, agent/tool, sensitivity, review status and freshness before returning data. Sensitive context cannot silently cross workspace boundaries or reach external providers. Graph v2 is a planned extension of this resolver and the existing proposal -> approval -> audit -> Undo boundary, not a second assistant or an independent source of truth.

### T — Tools

Agent capabilities are exposed through a typed Tool Registry rather than direct database/provider access. Initial tools include task read/propose-create/propose-update/propose-complete, project read/search, note read/search, calendar read/find-free-time and context read.

Future adapters can add email search/draft, calendar writes, Microsoft Graph, files, web research and other services without changing agent definitions. Every tool declares input/output schemas, read/write classification, scope, audit behavior and approval policy.

### Executive Orchestrator

For each run the orchestrator resolves workspace/project, loads the agent, resolves minimum context, exposes only allowlisted tools, runs deterministic and/or model reasoning, validates structured output, executes permitted reads and converts mutations into proposals. Confirmation, audit and guarded Undo remain server-controlled.

The model is never the authority for access control or writes.

### Permission model

- READ: automatic only inside explicitly allowed scopes.
- PROPOSE: AI may prepare a mutation but cannot apply it.
- WRITE: a validated proposal is applied only after required approval.
- SEND / EXTERNAL SIDE EFFECT: explicit approval by default plus a dedicated tool policy.

Scheduled/proactive agents may perform read-only analysis automatically and create proposals. Autonomous external side effects require a separately configured policy.

### Target execution flow

    Inputs / events / schedules
              |
              v
     Executive Orchestrator
              |
       +------+------+ 
       |      |      |
     Agents Context Tools
       |      |      |
       +------+------+ 
              |
              v

A run can combine an Executive Assistant with active projects/tasks, relevant personal/work/project context and read-only calendar tools. It identifies risks, capacity and next actions, then proposes changes instead of silently mutating the plan.

### PACT implementation status

The server-side PACT foundation is now in place: SQLite persistence for agents, durable context, tool permissions and agent runs; a default Lumi agent (with the stable internal ID `aifred`); a workspace-scoped Context Resolver; and a typed read-only Tool Registry. Provider-assisted reasoning now receives canonical entities and non-sensitive durable context through the resolver. Mutations continue to use the existing proposal -> confirmation -> audit -> Undo boundary.

The owner UI now exposes a dedicated Agents view with Project Manager and Meeting Prep. Each manual run requires one explicit workspace, uses only the agent's declared tools and context scopes, and records a sanitized operational run without task titles or context contents. Project Manager and Meeting Prep currently return deterministic recommendations and never write data. The former Morning Planner and Evening Reviewer agents and their scheduled briefings were removed on 2026-10-07; their past runs remain in the sanitized history. Rich results are returned only to the authenticated owner session, while persisted history contains status and bounded operational metadata.

The authenticated Lumi integration API is implemented for external conversational clients. It uses a dedicated bearer token and requires one explicit workspace. The planning endpoint can return read-only answers or create approval-bound proposals. A separate read-only tools endpoint exposes only task.read, project.read, note.read, calendar.read, calendar.free_time and context.read; task.propose cannot be invoked through that endpoint. Proposal confirmation is intentionally not exposed to the external integration. Its versioned OpenAPI 3.1 schema remains at the compatibility path `docs/aifred-openapi.json`, and the running app serves it at `/api/integrations/aifred/openapi`. This is the contract for a future ChatGPT/Voice connector; it advertises only planning and allowlisted read operations. Owner-only durable context management is available through `/api/context` and the Settings UI. The owner can list, create and archive context, choose scope and sensitivity, and bind project context only to a project in the same workspace. Sensitive items remain visible to the owner UI/API but are excluded from the external `context.read` tool and provider reasoning by default. Run history records only sanitized operational summaries (kind, trigger and status), not task titles or durable context, and is visible in the owner Agents view. Next: verify the PACT integration in build/CI and complete the Context Graph v2 reliability, provenance, review and export gates below before adding new account adapters. Existing read-only ICS planning remains supported.

The first Context Graph v2 foundation is additive to `pact_context`: owner-authored, workspace-bound claims have stable revisions, independent review/freshness/sensitivity state, non-fabricated sources and evidence as separate records, idempotent transaction commands and content-bearing owner history. The Context view supports create, edit, claim-level review and archive. The resolver adds only confirmed, current, normal and non-archived claims while retaining eligible legacy PACT context. Claim sensitivity has three levels: normal, confidential and restricted. Only normal claims reach agents, the day plan, attention rules or AI providers; the two-level `sensitive` of earlier clients is still accepted by the API and stored as `confidential`, an existing `sensitive` claim was converted to `confidential` by a registered migration, and a stored value nobody recognises is read as restricted and needs review. The Context Inbox saves proposals as confidential. Legacy `pact_context` keeps its own normal/sensitive classification. Claims and standalone people/organizations share one command service: each command carries an idempotency key, object id, explicit workspace and expected revision, and the change, its history and the stored result commit in one transaction (an exact retry returns the stored result, a changed request under the same key is a 409, a no-op writes no history, a stale revision writes nothing, and a failure part-way leaves no object change, history entry or command record). A claim can move between proposed, confirmed and rejected in any direction, each move recorded as a review event, and an edit returns it to proposed. The Context view keeps one idempotency key per user intent until it succeeds or the draft changes, applies each response only to the object it was sent for, and keeps the draft when a save fails. Claims and standalone people/organizations in one workspace have durable multi-step Undo/Redo. Change events carry a per-database sequence, the object type, a kind (change, undo or redo) and the event a reversal reverses, added by a registered migration that backfills existing events without rewriting their content; the Undo and Redo stacks are derived from that table, so they are identical after a restart. An Undo or Redo is an idempotent command that appends a compensating revision and a new change event (history only grows; a reversed review also writes a review event); it is refused with `history_changed` when the step on top is no longer the one the client saw, with `undo_conflict` when the object was changed after that step, and when the restored state would break an invariant (a name another active person or organization already has, an archived or missing related subject), in each case without writing anything. A new ordinary change empties the Redo stack; no-op commands and retries add no step. The Context view shows the next Undo and Redo step with its target (Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z work outside text fields), and each saved edit offers the same Undo. The route `/api/context/history` accepts only the signed-in owner session; the external integration API has no Undo or Redo. Tasks keep their own existing approval-bound Undo. Sources and evidence are records. `context_sources` holds where information came from (provider, account, external id, locator, author/role, source and ingestion time, coverage `metadata`/`excerpt`/`body` and sensitivity) and is unique per external item within a workspace, provider and account (creating a source for an item that exists returns the existing one, raised to a stricter requested sensitivity, and a new source must state its coverage); `context_evidence` links one claim to one source with an optional excerpt of at most 500 characters, a location in the source and a stance (supports or contradicts). Both are workspace-scoped, change only through the same idempotent context commands (change events of object type `source` and `evidence`) and take part in Undo/Redo; a step that can no longer be done can be skipped only after the expected conflict, without changing data. The server never fills in an author, date, external id or quote. Evidence with an excerpt or location needs a source with `excerpt` or `body` coverage; evidence on a metadata-only source only references it and is marked metadata-only, and a claim reports its coverage as missing, metadata-only or documented content. Any evidence change returns the claim to review. Lowering a source's sensitivity needs a non-empty reason, kept in its change event; that and any other edit of what the evidence rests on (coverage, location, author, external id, provider, account, dates) returns every active claim citing the source to review (every citing claim gets a new revision, whatever its review state, so a stale confirm is refused), so agents see its evidence again only after the claims are confirmed again; raising the sensitivity needs no reason. The source/evidence JSON previously stored on claims was converted into records by a registered migration (nothing missing is invented, sensitivity is never weakened, a source shared by several claims keeps the strictest sensitivity and the strongest coverage) and a repair at every start converts claims written later by an older binary (merging into an existing source of the same external item; JSON with an excerpt or location never yields a metadata-only source). Every command marks the claims it writes with `legacy_synced_revision`; an older binary bumps the revision without it, so at every start a claim whose revision differs from that mark and whose JSON source/evidence no longer reads like its records is rebuilt from the JSON in one command (its active evidence is archived, the source is resolved by its external item, coverage is raised to what the evidence needs and lowered only on a source no other claim cites, absent coverage meaning unknown), returns to review with a new revision, and is recorded as a system change event (`claim.legacy_reconcile`) that Undo can reverse; the identity is claim, revision and JSON, so a cycle of edits is never replayed and one start never repairs a claim twice. The JSON is still accepted and kept for older code. This start-up repair is best effort for an accidental short run of an older binary; downgrading below the release that introduced source and evidence records is not supported, and a rollback past it means restoring the database backup made before that deployment. Only evidence from `normal` sources can reach agents, external tools or AI providers; a single serializer strips everything else. Relationship claims (claims with a target) use a predicate from a static, versioned relation registry with Czech and English labels, inverse labels, direction and permitted subject and target types: uses, responsible_for, works_for, participates_in, assigned_to, blocked_by, arose_from, related_to (symmetric), supersedes, and `waiting_for`, which earlier data and the waiting attention rule already use. Other pairs are refused (`invalid_relation`); `supersedes` links only tasks, projects, notes and areas of the same type; an active relationship is unique per subject, predicate and target (`duplicate_relation`; `related_to` also in reverse), and Undo/Redo never recreates a duplicate; literal claims keep free predicates. Existing relationship claims outside the registry are not rewritten: they read as needing review, are never eligible for AI, cannot be confirmed (`relation_needs_fix`) and are fixed by editing them to a registered predicate. No mention or link creates a relation. This slice does not migrate legacy context, expose context mutations to external Lumi tools, implement graph/import/export, or satisfy the full Graph v2 acceptance gates. Full backups (format 2, see Persistence and backups) now include the Context tables, their history and the note versions; older JSON backups still cover canonical entities and relations only.

C1d note history: a note's text (Markdown in `content`) stays in the ordinary entity sync, so it works offline and across devices. The server additionally records a revision in `note_revisions` whenever a saved change alters a note's title or content, inside the same transaction that stores the change (`replaceSnapshot`, and the restore of an older JSON backup with origin `backup_restore`). A new note gets revision 1 (`created`), a changed title or text the next number (`edited`), and the registered migration `2026-10-note-revisions` gave every existing note a `baseline` revision 1. A change of anything else (properties, status, project link, `updatedAt`) or an identical text writes nothing, and a conflict, a refused write or a failure part-way leaves no revision. Restoring an old version is an ordinary new edit, so history only grows; deleting a note (or a note that is gone after a backup restore) deletes its revisions, and a mistaken deletion is recovered from the daily backup. At most 20 revisions are kept per note: beyond that the oldest are pruned (never the newest) and revision numbers are never reused, so the oldest kept version may be higher than 1. Revisions are read only through `/api/notes/revisions` (list: version, time, origin, title, text length and `sameAsRevision`, the newest kept earlier version with identical text (the title is not compared), without content; one version with `revision=N`), which accepts only the signed-in owner session, never the integration token, writes security events without note text and answers 404 for an unknown or deleted note. Revisions never reach agents, PACT tools, AI providers, attention, the day plan, security logs or the client snapshot. The note detail edits the body as text with a local draft kept on every key press (saved on leaving the field through the normal save path) and previews it as untrusted Markdown: raw HTML is dropped, images are not loaded (their alt text is shown), only `http:`, `https:` and `mailto:` links are links and they open with `rel="noopener noreferrer"`. The version history is shown only online, compares a version with the current text by line and restores a version as a new edit. A deleted note that is later revived starts its history again at version 1. AI proposal paths (`lib/ai-actions.ts`) do not target notes today and therefore record no note revisions; if they ever do, they must go through the same transactional recording. Unsaved note text never overwrites newer text from another device: when the text the draft started from is no longer the note's text, nothing is saved, the draft stays in the field and on the device (also a draft left behind by a crashed page, which is adopted by the open page instead of being deleted) and the note shows a conflict in which the owner chooses between using the draft (the other text stays in the version history) and discarding it; restoring a version is disabled while the note has an unsaved draft. Full backups and exports include the note revisions and a restore returns them to the backup's state; an older JSON backup does not (restoring one records a `backup_restore` revision for the notes it changes).

### Implementation roadmap

1. Verify and preserve the current PACT foundation: agents, durable context, Context Resolver, Tool Registry, tracked runs and owner-confirmed task actions.
2. Extend the existing SQLite and mutation service with claim/source schemas, revision checks, idempotent commands and transactional context history; prepare a non-destructive migration.
3. Add claim-level review, explicit evidence, conflict handling and guarded multi-step Undo/Redo. Keep task execution state separate from claim review.
4. Add the Context workspace: Markdown editing, search, dynamic graph, relation details, review queue and history in the current PWA.
5. Complete portable export/import, encrypted backup/restore and server-enforced data-boundary checks before connecting new real accounts. (Done: full backups, export/import and the data-boundary checks, slice D1. Open: encrypted backups.)
6. Introduce normalized external adapters incrementally: one selected personal calendar first, then approved M365 and selective email. Preserve current ICS planning throughout. (Started: the owner's iCloud calendar over CalDAV, read-only, slice E1; ICS feeds remain supported alongside it. Open: M365, selective email, writing to the calendar.)
7. Extend the Context Resolver and typed tools for evidence-backed recommendations and proposals; then expand controlled proactivity under existing approval policies.

The original PACT milestone remains the integration baseline: an Executive Assistant can read one workspace, receive a minimal resolved context bundle, inspect tasks/projects/calendar through registered tools, produce a structured recommendation and propose changes without direct database access or provider credentials. Context Graph v2 adds the acceptance gates below; they must not be described as already implemented.

### ChatGPT / Voice integration contract

External conversational clients authenticate with `Authorization: Bearer <AI_EXECUTIVE_INTEGRATION_TOKEN>`. Use a dedicated random token of at least 32 characters and never reuse the browser password, session secret, Hermes token or calendar secret. The connector must select one explicit workspace for every call; `all` is rejected.

The OpenAPI contract exposes two operations: `planWithAifred` for reasoning and approval-bound proposals, and `readAifredTool` for the allowlisted read-only Tool Registry. A proposal returned to ChatGPT is only a pending proposal; the owner must confirm it through Lumi. The integration has no confirmation, Undo, arbitrary database or provider-credential endpoint.

Before connecting an external client in production, deploy the new code, set `AI_EXECUTIVE_INTEGRATION_TOKEN` in the root-managed service environment, restart AI Executive, and verify that the OpenAPI endpoint is reachable only over the intended HTTPS/Tailscale path. Do not expose the local Node listener directly to the public Internet.

## Víceuživatelské Oblasti — cílový bezpečnostní kontrakt (2026-10-23)

**Stav a rozhodnutí.** Vlastník schválil víceuživatelskou spolupráci jako doplněk Lumi, která zůstává osobním asistentem jednotlivce, nikoli systémem sledování lidí (viz [záznam rozhodnutí](decisions/2026-10-23-prostory-oblasti-muj-plan.md)). Tato kapitola je **budoucí cílová architektura**, nikoli popis dodané podpory více uživatelů. Aktuálně je přihlášení jednouživatelské (`owner`), passkeys a integrační token nerozlišují osoby, `Shared` má pouze členství vlastníka, `GET/PUT /api/store` čtou/zapisují celý snímek, `properties.members` je slučované pole, osobní attention/push stav nemusí být user-scoped a úkoly nemají řešitele. Do dokončení bezpečnostních bran **nesmí být umožněno pozvat další uživatele ani jim zpřístupnit data**. Následující cílová pravidla mají v budoucím víceuživatelském režimu přednost před legacy větami o `All my work`, explicitním workspace a owner-only sessions jinde v tomto dokumentu; popisy **Current MVP** zůstávají historicky pravdivé.

### Model rozsahů, Oblastí a položek

- V UI jsou právě **dva prostory**: Osobní a Sdílené. Přepínač **Můj plán / Osobní / Sdílené** volí pouze **čtecí rozsah**, nikoli vlastníka ani fyzické umístění dat. Home zůstává úvodní obrazovka. V Mém plánu jsou soukromé úkoly uživatele a jemu přidělené sdílené úkoly; unassigned shared se zobrazuje v Sdílené, nikoli automaticky v osobních plánech. Datové výpisy agregují autorizovaná stabilní ID bez duplicit.
- Každá soukromá Oblast vlastníka mapuje do **jeho jediného interního osobního workspace**; každá **sdílená Oblast** se v **cílovém víceuživatelském stavu** mapuje **1:1 na svůj samostatný interní workspace** s přesným členstvím. Současný legacy sdílený workspace však může obsahovat více Oblastí; do dokončení samostatného rozdělovacího migračního kroku je tato struktura pouze jednouživatelská kompatibilita a nesmí se na ní aktivovat sdílení. Rozdělení do interních workspaces specifikuje migrační plán níže; nevytváří další uživatelské prostory. Interní workspaces jsou bezpečnostním detailem serveru, ne uživatelskou hierarchií; stávající zákaz relací napříč interními workspaces zůstává. Odkaz z veřejnější položky na soukromou není automatickou propustkou k původním datům; taková vazba je buď zakázána, nebo reprezentována bezpečným textovým odkazem bez existence/titulu pro neautorizované identity.
- **Oblast je jediným zdrojem sdílené viditelnosti.** Každý projekt má právě jednu Oblast a každý samostatný úkol právě jednu; Oblast úkolu v projektu se **odvozuje pouze z projektu** (nepersistovat samostatnou `belongs_to_area` relaci). Vytvoření úkolu v projektu i přesun úkolu do projektu přijímá Oblast projektu. Při vyjmutí úkolu z projektu se nastaví samostatná Oblast, bezpečným defaultem je uživatelovo soukromé **Nezařazeno**. Nový projekt bez výběru Oblasti též přejde do soukromého Nezařazeno. Inbox je třídicí stav, není Oblast. Oblast může nést jméno „Osobní“, projekt v ní může nést jméno „Rodina“, bez duplicitních tematických Oblastí.
- Zápis z Mého plánu nemíří do agregátu: musí mít **jednu explicitní cílovou Oblast**, zobrazovanou ve formuláři/návrhu (bezpečná soukromá výchozí hodnota je explicitně viditelná). Resolver mapuje Oblast na právě jeden interní workspace a odmítne rozpor, chybějící oprávnění i pokus o zápis přes `all`. Agregované čtení volá pouze autorizované jednotlivé scope dotazy s post-filterem; interní nástroj nikdy nešíří čtecí agregaci na pravomoc zápisu.
- Oblast má stabilní ID, typ `private|shared`, vlastníka/správce, revizi přístupové politiky, uživatelský popisek a řazení. Při archivaci/smazání nelze zanechat osiřelé položky: vyžaduje atomický přesun obsahu do oprávněné cílové Oblasti nebo archivaci pod stejnou politikou; soukromí se nemůže implicitně rozšířit. Změna typu Oblasti je operace nad veškerým jejím obsahem, s potvrzením a auditem.

### Identita, role, členství a vlastnictví (bez automatického sdílení)

- Cílová autentizace má **samostatnou identitu `userId` pro každého člověka**. Sessions, passkeys, password/recovery prostředky, zařízení a lokální cache musí patřit této identitě; žádný implicitní `subject:"owner"` pro nově pozvané osoby. Onboarding: pozvánka oprávněným adminem s omezenou platností a explicitním přijetím; bezpečná obnova účtu, odebrání zařízení a zneplatnění sessions. Všechny tyto akce jsou auditované, bez prozrazení dat do obsahu pozvánky.
- Role **viewer** smí autorizované čtení a **nikdy nemůže být řešitelem**; **editor** smí měnit běžná společná data (úkol/projekt/poznámku) a přiřazovat řešitele pouze mezi členy s rolí editor/admin; **admin** spravuje členství, role, typ a životní cyklus Oblasti, převod/přesun sdílených dat, administrativní mazání a předání správce. Výchozí pozvánka nepřiděluje administrátora. V soukromé Oblasti má práva jen vlastník. Musí existovat alespoň jeden aktivní admin sdílené Oblasti; jeho poslední odchod/odebrání je blokováno, dokud není předána správa. Ztráta členství odstraní přístup i právo upravovat dříve přidělené úkoly.
- Rozlišují se **vlastník**, **řešitel (assignee)** a **člen Oblasti**. Soukromý úkol nemůže být přiřazen jiné identitě; pokud se má přiřadit jiné osobě, vyžaduje potvrzený přesun do sdílené Oblasti. Sdílený řešitel musí mít aktuální členství a roli **editor nebo admin**; odebranému členu se nedokončené úkoly atomicky odeberou z přiřazení, zůstanou v Oblasti jako **Nepřiděleno** a admin dostane soukromé attention upozornění k přeřazení. Změna vlastnictví/admina podléhá potvrzení a revizní kontrole.
- API pro správu členství/rolí je **samostatný serverový příkaz** s autorizací role admin, potvrzením tam, kde mění viditelnost, auditem, revizí politiky a idempotencí. `members` ani ACL se nesmějí přijímat jako běžné slučované entity/pole přes offline sync (`properties.members` z něj vyřadit). Změny členství nesmí způsobit starý klient, import ani restore bez zvláštního oprávnění.
- Každý **integrační token** pro ChatGPT, Hermes/Telegram, externí chat/MCP a budoucí konektory má konkrétního aktéra/userId, povolené scope a akce, expirační/revokační pravidla a minimální privileges. Pro cílový multi-user režim jsou staré globální owner tokeny nekompatibilní a musí být nahrazeny nebo odmítnuty. Pozvánky, členství a potvrzení sdílení nejsou model-controlled operace.

### Příslušnost dat a informační toky

| Datová položka | Cílová příslušnost a autorita | Pravidlo zpřístupnění |
|---|---|---|
| Projekt | Jedna explicitní Oblast | Veškerý současný obsah podle členství cílové Oblasti; dřívější soukromá historie zůstane soukromá |
| Úkol v projektu | Projektová Oblast odvozená z projektu | Nesmí mít vlastní odlišnou oblast/ACL; společná pole vidí oprávnění členové |
| Samostatný úkol | Jedna vlastní Oblast, default soukromé Nezařazeno | Viditelný jen v cílové Oblasti, přiřazení jen aktuálním členům |
| Poznámka a její revize | **Poznámka přímo patřící k projektu povinně dědí jeho Oblast**, bez samostatného přepisu; samostatná poznámka má jednu vlastní Oblast (default soukromá). Pouhé odkazy/backlinky na projekty nejsou přímou příslušností. | Staré revize před zveřejněním nejsou zpřístupněny novým členům; při změně vazby je vyžadováno stejné potvrzení jako u úkolu |
| Context subject, claim, relation, review | Explicitní Oblast/security workspace vlastního kanonického objektu | Zdroj/evidence se čte jen při samostatném oprávnění; žádné relace přes interní workspace |
| Evidence a zdroj, `mailSource`, import | Výchozí soukromý účet/Oblast aktéra a původní citlivost | Zkopírování konkrétního úryvku do sdíleného obsahuje schválenou explicitní publikaci; link nevytváří přístup |
| Kalendářové události a osobní bloky | Vlastník připojeného účtu; osobní plánovací stav uživatele | Soukromá kapacita a detail kalendáře se nezveřejní přes sdílené úkoly |
| Rozhodnutí nad událostí kalendáře (`calendarDecisions`: `hidden` / `notTask`) | **Osobní stav `(userId, calendarSourceId, event/occurrence key)`**, ne společná vlastnost Oblasti | Rozhodnutí jednoho člověka nesmí skrýt událost ani změnit `busy` výpočet druhého člena |
| Attention kandidát a jeho lifecycle | Odvozený obsah autorizované Oblasti + osobní `userId` | Snooze/dismiss/feedback jednotlivce, bez ovlivnění druhých |
| Push subscription / reminder / delivery | Jednoznačné `userId` + zařízení + platná oblastní politika | Bez upozornění odebraným členům; revokované úryvky se zneplatní |
| Audit, event log a historie | Neměnný actor, scope a aktuální přístupová politika plus historická visibility epoch | Novému členovi se nevydají soukromé starší hodnoty; vlastníkovy chráněné revize zůstávají izolované |
| Cache, index, autocomplete, graf, export | Odvozené z kanonických dat se scope a `userId` | Revokace/změna Oblasti okamžitě blokuje serverový výdej i čítače/snippety; cache invalidace |
| Záloha / restore / import | Správce serveru a explicitní strategie identity + členství | Obnova obsahu nikdy automaticky nereaktivuje dřívější přístup ani nevydá data cizí identitě |

Stav ochrany zdrojových dat může být **přísnější** než viditelnost Oblasti, protože odkaz na cizí osobní e-mail nebo source evidence nemění jeho vlastnictví. Pokud zdroj neumožňuje bezpečné přenesení, operace se odmítne nebo zveřejní pouze explicitně odsouhlasený výňatek jako nový sdílený obsah s nezávislou proveniencí. **Oblast zůstává jediným zdrojem viditelnosti kanonických úkolů/projektů/poznámek;** dědičná citlivost a přístup k původnímu externímu zdroji jsou další podmínkou jeho vlastního přečtení, nikoli druhým přepínačem sdílení projektu. Přílohy úkolů nyní nejsou implementované; před budoucím přidáním musí zdědit stejnou ochranu, včetně URL, preview, historie a záloh.

**Osobní vs. společná pole úkolu (cílové rozdělení):**

| Společná kanonická pole úkolu | Oddělený osobní stav `(userId, taskId)` |
|---|---|
| Název, popis, stav dokončení, **sdílený termín/deadline**, **sdílené opakování/recurrence**, řešitel, checklist, společné poznámky a explicitně sdílené čekání (na koho/co, společné datum follow-upu); případná budoucí **sdílená týmová priorita** musí mít vlastní pole a výslovně nastavený význam | `today`, plánovaný den / `when`, přijatý časový blok, **dosavadní priorita `priority` jako osobní**, osobní odhad `effort`/trvání a kapacita, osobní připomínka follow-upu a odložení, plánovací feedback, snooze/dismiss, **rozhodnutí `hidden` / `notTask` o kalendářové události a jejím opakování**, vlastní připomínky a nastavení oznámení |

Změna osobního `when`, `priority` či `effort` jednoho uživatele nemění společný deadline ani osobní hodnoty jiného člena. Současná pole `priority` a odhadu slouží jednotlivci, nikoli týmovému řízení; migrace je zachová ve stavu dosavadního vlastníka, bez tichého převedení na týmovou prioritu. Sdílené čekání je výslovný stav spolupráce; soukromé kontakty, e-mailové podklady a důvody čekání bez schválení zůstávají v osobním kontextu. Sdílená recurrence generuje společné výskyty, osobní odložení nemění společné pravidlo. Pro soukromé úkoly zůstává zachováno stávající uživatelské chování. Rovněž `attention_states` a `push_subscriptions` musí mít user binding; dosavadní workspace-only index není dostatečný. Komentáře/kontext, které mohou být soukromé, se nikdy nevydají jako sdílený obsah bez explicitního záměru.

**Kompatibilita s E3 rozhodnutími o kalendáři (#100, současný stav vs. cíl).** Aktuálně jsou `properties.calendarDecisions` ukládána na workspace entitě a ovlivňují jen jediného existujícího vlastníka; v cílovém víceuživatelském režimu se musejí oddělit podle `userId` (včetně source a occurrence/series klíče), podobně jako `today/when`. Migrace nesmí změnit význam `hidden/notTask`, soukromý busy-time ani duplicitně vytvořit úkol. Při aktivaci více identit nelze sdílet preference jednoho člena s ostatními.

**Převedení události na úkol („Je to úkol?“, #100).** Dnes implementace zakládá běžný úkol v `workspaceId` události a odvozuje identitu úkolu z workspace + provider/source + occurrence; jde o dokumentovaný legacy stav, nikoli výjimku z nového pravidla Oblastí. V cílovém UX musí být **před uložením vidět a potvrzena jedna cílová Oblast** (výchozí je soukromá `Nezařazeno` vlastníka kalendářového účtu, **i když** legacy zdroj/událost pochází ze shared workspace). Převod do sdílené Oblasti vyžaduje zvláštní vědomé potvrzení přesného zveřejněného obsahu, okruhu členů a oprávnění. Úkol uvnitř již vybraného projektu místo toho povinně dědí projektovou Oblast. Zachovat `calendarSourceId`, event/occurrence/series vazby a deduplikaci `eventTaskLinks`; nové kanonické task ID musí být deterministické **pouze z identity aktéra + kalendářového zdroje + jednoznačné identity události nebo konkrétního výskytu**. **Cílová Oblast, projekt ani interní `workspaceId` nejsou součástí identity úkolu**: změna zařazení nikdy nevytváří nový task ID. Dvě souběžná zařízení, která stejnou událost převádějí do různých Oblastí, musí narazit na **stejný kanonický úkol** a serverové revizní/idempotentní vyhodnocení rozdílného zařazení; neshoda se nabídne ke schválení jako konflikt, nikoli jako dva úkoly ani jako tiché přesdílení. Identity různých aktérů se naopak nesmějí omylem sloučit. Při migraci starých úkolů vytvořených z událostí se zachová kanonické task ID a vytvoří se explicitní kompatibilní mapping legacy event identity; nesmí se regenerovat nový úkol z již převedené události.

### Synchronizace, revokace, historie a souběh

1. Server musí při **každém čtení** vyhodnotit aktéra, Oblast, členství/roli, případnou citlivost a účel. `GET /api/store` nesmí v multi-user režimu vracet globální snímek. Oprávněný klient může číst pouze svůj osobní workspace a sdílené Oblasti, jejichž je členem; všechna data, relace, search, count, autocomplete, attention a AI výstupy musejí mít stejný filtr.
2. **Zápisy po položkách / transakčních příkazech**, ne `PUT` celého globálního snapshotu: každá operace včetně tombstone, přesunu, změny rodiče, Undo a „vzkříšení“ starého záznamu kontroluje serverem aktuální revizi, aktéra, právo v cílové Oblasti a idempotenci. Neautorizovaný edit/delayed offline queue nesmí přepsat data jiných uživatelů.
3. Změny členství/Oblasti musí v atomickém kroku aktualizovat **revizi politiky**, zneplatnit čekající návrhy na staré revizi (TOCTOU), revidovat assignees, auditovat dopady, zneplatnit index/caches a při příští synchronizaci nařídit odstranění již neoprávněného obsahu. Schválení vytvořené před odebráním člena či přesunem Oblasti **selže bezpečně**, i když revize úkolu zůstala stejná.
4. **Revokace offline nemůže odstranit dříve staženou kopii**, pokud zařízení zůstane offline nebo si uživatel obsah zkopíroval. Po připojení server okamžitě odmítá čtení i opožděné zápisy a klient odstraní data dané Oblasti, cache, indexové úryvky a offline frontu; UI tento limit komunikuje poctivě. Odhlášení, změna identity, ztráta role a obnova přihlašování musí odstranit nebo kryptograficky oddělit data předchozí identity.
5. Přesun mezi soukromou a sdílenou Oblastí nebo mezi různými sdílenými Oblastmi je **atomická potvrzovaná** změna interního workspace, vazeb, dítěte a indexu, s auditem. **Sdílený obsah spoluvytvářený nebo vlastněný jiným členem nelze prostě převést do soukromého prostoru admina**; pokud existuje takové vlastnictví, příspěvek nebo aktivní cizí řešitel, převod se zamítne do vyřešení práv a explicitního předání dotčenými vlastníky. Případná kopie pouze vlastního obsahu je novou operací bez přenášení historie jiných členů. Změna typu celé sdílené Oblasti na soukromou se řídí stejným pravidlem, ne obejitím přes administrátora. Před potvrzením zobrazit členy nově oprávněné i ty, kdo přístup ztratí, a dopad na přiřazené úkoly. Obsahové revize a předchozí soukromé hodnoty se nezpřístupní novým členům; historická dostupnost je řízena podle visibility epoch, ne jen dnešní Oblasti. **Undo takového přesunu je nový přesun viditelnosti**, proto vyžaduje nové explicitní potvrzení, ověření aktuálního vlastníka, přiřazení, členství a policy revize (TOCTOU); staré schválení nikdy neplatí podruhé. Pokud ochranu nelze vynutit, přesun nebo Undo se zamítne.
6. Sync protokol se **verzuje**. Starší klienti s celým snímkem nesmějí po aktivaci víceuživatelského režimu synchronizovat, dokud neprovedou kontrolovaný upgrade/reconciliaci lokální fronty; žádná tichá ztráta offline změn. Stejně je chráněn restore: stará záloha/datový import nesmí obnovit zrušené členství, tokeny ani starou možnost zápisu. Membership audit/policy revize musí mít obnovovací postup nezávislý na běžném obsahu zálohy.

### AI, schvalování, externalita a provozní požadavky

- Context Resolver musí rozlišit **čtecí agregaci Můj plán** (filtrované jednotlivé autorizované rozsahy) od **jediné cílové Oblasti zápisu**; přepnutý pohled nikdy není oprávnění. Z `create_project_bundle` ani z jiného návrhu nelze zveřejnit osobní poštu, kalendářové události, claim/evidence či soukromé shrnutí do sdílené Oblasti bez konkrétního schválení obsahu a okruhu příjemců. Bez oprávnění se neprozradí ani název/existence entity, počet výsledků, odvozené embeddingy či evidence.
- Notifikace k sdíleným úkolům se cílí na jejich řešitele (nebo admina u nepřidělených actionable položek) dle osobního stavu a platných oprávnění; při revokaci se zastaví nové doručování a vymažou související subscriptions/queue. Dřívější oznámení na cizím zamčeném zařízení nelze vrátit; obsah zohledňuje soukromí a nastavení. 
- Serverový export pro člena obsahuje jen aktuálně povolené položky; privilegovaná záloha celé instance je administrátorská operace, která nesmí být vystavena běžným členům ani přes integrační token. Je nutné definovat obnovu admin přístupu a zachování historie, aniž by restore vrátil revokované členství. Pro změny s dopadem na bezpečnost je nutný audit aktéra, okamžiku, revizí, nové/odebrané množiny členů a úspěchu/odmítnutí bez volného exportu soukromého textu do operačních logů.

### Aktuální implementační plán pro čistý start (rozhodnutí 2026-10-26)

**Priorita pro další vývoj:** [ROADMAP.md](ROADMAP.md) a [rozhodnutí vlastníka](decisions/2026-10-26-cisty-start-d3.md) nahrazují povinnost **převádět převážně testovací legacy data** jako blokátor D3. Funkční a bezpečnostní kontrakt dvou prostorů a Oblastí výše **zůstává nezměněn**. Toto rozhodnutí **není povolení resetu produkční databáze**.

1. **Nový izolovaný kanonický model:** zavést nedestruktivně nový prázdný store/staging s cílovou strukturou: soukromé Oblasti vlastníka a samostatné 1:1 interní workspace pro sdílené Oblasti, právě jedna efektivní Oblast na projekt/samostatný úkol, dědění v projektových úkolech, výchozí soukromé Nezařazeno, explicitní assignee na nových sdílených úkolech. Znovu využít stávající invarianty nových zápisů; žádné automatické spuštění starého migračního aplikátoru.
2. **Serverové oprávnění před aktivací:** per-user identita/sessions/tokeny, scope podle členství/rolí a policy revize, autorizovaný read-model (Home/Inbox/Today/Upcoming/Projects/Search/attention/counts/AI), jednoznačný `writeAreaId` pro zápisy, per-item autorizované příkazy namísto globálního full-snapshot PUT, individuální plánovací stavy a bezpečná revokace.
3. **Sync a klienti:** verzování protokolu a restore generace, odmítnutí starých celosnímkových zápisů před mutací, nepropustné oddělení cache podle identity a Oblasti; staré Dexie/offline fronty se nesmějí potichu ztratit ani znovu importovat do nové DB. Před přepnutím inventarizovat zařízení a rozhodnout o exportu/odmítnutí starého obsahu; nerozhodnuté stavy blokují cutover.
4. **Aktivace D3:** již sloučené selektory a UI komponenty #103/#108 integrovat až s autoritativním zdrojem dat a bezpečnostními testy. Home zůstává výchozí obrazovka, Můj plán je pouze datový rozsah. Víceuživatelské pozvánky zůstávají vypnuté až do dokončení všech odpovídajících ACL/sync/identity/visibility/recovery bran.
5. **Volitelný produkční cutover až po samostatném souhlasu:** nejprve klasifikovat reálná data versus testovací obsah včetně auth, pošty, kalendáře, tokenů, historie, notifikací, offline front, zařízení a konfigurace; vytvořit a **ověřit archivní konzistentní zálohu a obnovu**. Přesně pojmenovaný destruktivní rozsah musí vlastník dodatečně výslovně schválit. Bez něj lze pracovat pouze na odděleném store. Žádná dřívější schválení PR ani toto rozhodnutí reset nepovolují.
6. **Test/release:** unit, integrační a negativní ACL testy pro 2–3 identity, offline/revokaci a restart; standardní PR Checks a review. Celé Browser E2E až před nasazením na přesném SHA podle `AGENTS.md`; deploy a feature gate vyžadují samostatné provozní rozhodnutí.

**Kontrakt trvalých staging sessions (R2-ID.1, pouze izolovaný staging):** staging schema v5 (`TARGET_STORE_SCHEMA_VERSION = 5`) přidává `identities.revocation_epoch` (monotónní, trigger povolí jen +1) a tabulku `staging_sessions` (id, `user_id`, **pouze SHA-256 hash** náhodného 256bitového tokenu, `created_at_ms`, `expires_at_ms` s životností nejvýše 15 minut, `revoked_at_ms`, epocha při vydání). Triggery zakazují odvolání vrátit zpět, změnu uživatele/tokenu/platnosti, nahrazení řádku, vydání už odvolané nebo zastaralé session a překročení kapacity 4096 řádků; mazat lze jen řádky expirované déle než 90 dní. Starší schéma (v4) se nemigruje: preflight ho odmítne a vyžaduje nový bootstrap. Vydání (`issue`), `revokeSession` a `revokeAllForUser` (zvýší epochu) jsou serverová knihovna `lib/target-staging-durable-session.ts` a operátorský CLI `scripts/target-staging-session.mjs` pro syntetické testovací identity; **neexistuje HTTP endpoint pro vydání** (byl by obchvatem autentizace). Zápis používá stejný pinned-fd + `BEGIN IMMEDIATE` základ jako zápis názvu úkolu (`lib/target-staging-pinned-write.ts`). Session je živá, jen pokud není odvolána, nevypršela a její epocha rovná se aktuální epoše identity; platnost se vždy rozhoduje proti **živému** store, takže revokace platí okamžitě na jiném procesu i po restartu. HTTP routy `/api/target-staging/*` přijímají vedle stávajícího owner cookie (beze změny, mapuje se na `AI_EXECUTIVE_TARGET_STAGING_OWNER_USER_ID`) HttpOnly cookie `lumi_target_staging_session`; je-li přítomna, rozhoduje o identitě výhradně ona (nikdy fallback na owner cookie) a její `userId` je aktér soukromých čtení i zápisu názvu. Do podprocesu se předává jen hash tokenu. Cursory jsou vázané na konkrétní session, takže je nelze přenést na jinou identitu ani session. **Linearizační bod čtení:** po návratu čtení nad snapshotem a těsně před uvolněním těla odpovědi `verifyStagingIdentityBeforeRelease` znovu ověří session a epochu proti živému store; odvolaná nebo expirovaná session vrací 401 `no-store` bez dat. **Linearizační bod zápisu:** session, expirace a epocha se ověřují uvnitř `BEGIN IMMEDIATE` před změnou i bezprostředně před `COMMIT`; odvolaná session nezapíše úkol, receipt ani audit (HTTP 401). Obnova ze zálohy vrací i stavy odvolání z doby zálohy, proto po restore generaci vždy vydat nové sessions (staré mají nejvýše 15 minut). Zapisovače nad pinned souborem (včetně zápisu názvu úkolu) nyní čekají na zámky SQLite synchronně až 200 ms místo okamžitého selhání, protože COMMIT se může krátce střetnout se sdílenými zámky živých kontrol session; delší držení zámku zápis dál odmítne. Po dosažení kapacity 4096 řádků vydání selže bezpečně (fail closed) a retence na 90 dní blokuje mazání, takže staging se řeší novým bootstrapem bez migrace. Sdílené Oblasti, členství a UI nejsou součástí R2-ID.1.

**Kontrakt příkazu členství (R2-ID.2a, pouze izolovaný staging, bez UI):** staging schema v6 (`TARGET_STORE_SCHEMA_VERSION = 6`, v5 se nemigruje, preflight ho odmítne) přidává `area_membership_receipts` (klíč = SHA-256 z aktéra, Oblasti a `commandId`, digest payloadu a uložený výsledek) a content-free append-only `area_membership_audit` (aktér, Oblast, cílový uživatel, akce, role před/po, `policy_revision` před/po, restore generace, čas, neprůhledný klíč příkazu; bez UPDATE, DELETE až po 90 dnech, kapacita 4096 fail closed) a triggery `last_admin_*`, které i surové SQL brání tomu, aby sdílená Oblast zůstala bez admina (DELETE, snížení role i `INSERT OR REPLACE`). Knihovna `applyTargetStagingMembershipCommand` (`lib/target-staging-membership-command.ts`) běží v jedné pinned-fd `BEGIN IMMEDIATE` transakci: živá session (před změnou i před `COMMIT`), aktér musí být aktuálně admin **sdílené** Oblasti (nečlen, viewer/editor, neznámá i soukromá Oblast vrací stejné `unavailable`), přesný retry vrátí uložený výsledek, jiný payload pod stejným klíčem je `idempotency_conflict`, `expectedPolicyRevision` se musí rovnat aktuální (jinak `stale_policy_revision` a nic se nezapíše), cíl musí existovat a mít osobní workspace; `add` vyžaduje nečlena (`already_member`), `remove`/`set_role` člena; odebrání nebo snížení posledního admina je `last_admin`. Při odebrání a snížení na viewer se před změnou členství nastaví `assignee_user_id = NULL` všem úkolům cíle v dané Oblasti (včetně úkolů v projektech Oblasti); staging nemá stav dokončení, takže se počítají **všechny** úkoly jako nedokončené a historická atribuce dokončených je odložena. Přeřazení `policy_revision` nemění, změna členství ji zvýší právě o 1; stejná role je receiptovaný no-op bez auditu a bez zvýšení revize; no-op přesto zapisuje receipt a počítá se do kapacity 4096 receiptů (omezeno limitem 30 požadavků / 10 minut na klienta; staging řešení po naplnění je nový bootstrap). Selhání ověření aktéra nebo session vrací 401, ztráta integrity pinu/store 503. Admin při `add` rozliší neznámou cílovou identitu od existujícího nečlena (vlastní přidání člena to nutně prozrazuje; admini jsou důvěryhodní správci Oblasti, nečlen se nedozví nic). Pokud admin odebere nebo sníží sám sebe a ztratí odpověď, opakování stejného `commandId` vrací nerozlišitelné zamítnutí, protože kontrola admina záměrně předchází čtení receiptu (žádný únik uloženého výsledku tomu, kdo ztratil přístup). HTTP `POST /api/target-staging/areas/[areaId]/members` (`{commandId, expectedPolicyRevision, action: add|remove|set_role, targetUserId, role?}`; aktér nikdy z JSON) má pořadí jako PATCH názvu (příznaky, identita, konfigurace, parametry, same-origin, `admitStagingIdentity`, limiter, tělo, validace, nezpoplatněná živá kontrola, podproces) a kódy 200 ok/no-op, 400, 401, 403, 404 (nerozlišitelné), 409 `stale_policy_revision` | `idempotency_conflict` | `already_member`, 422 `last_admin`, 429, 503.

Staré diagnostiky a zachovávací kontroly 2a–2c **zůstávají v kódu a testech** pro případ cíleného převodu později nalezených hodnotných dat, ale jejich zdokonalování není na kritické cestě. Nesmí se tím oslabit současná ochrana dat nebo bezpečnost nové architektury.

### Historická plná migrace 2a–2c — jen pokud bude zvoleno zachování legacy dat

**Podmíněná referenční specifikace, nikoli současná povinná cesta:** následující postup se použije pouze při samostatném schválení převodu starých dat. Pro čistý start platí výše uvedený aktuální plán; zejména není nutné historické backfillovat úkoly ani dokazovat identitu starých Home/Today/Inbox výsledků.


**Přípravná inventura a tři kontrolované migrační kroky (2a–2c):** `pnpm check-data` / `scripts/check-data.mjs` na ověřené kopii, inventář entit, relací, legacy `belongs_to_area` u úkolů v projektech, projektů bez Oblasti, textových `properties.area`, aktuálních `members`, zdrojů, historie, otevřených úkolů a offline front. Zdrojová data zachovat a vytvořit ověřenou konzistentní zálohu.

- **Krok 2a – normalizace bez změny workspaceId:** v existujícím jednouživatelském režimu doplnit chybějící Oblasti do **stejného** interního workspace, ve kterém jsou data nyní; úkol v projektu odvodí Oblast z projektu. Staré názvy/štítky nepředstavují souhlas se sdílením. Projekt z dnešního shared workspace dostane prozatím kompatibilní sdílenou Oblast téhož workspace, nikoli soukromou; chybějící soukromé přiřazení dostane soukromé Nezařazeno vlastníka. Může dočasně existovat **více legacy Oblastí v jednom shared workspace** pouze při vypnutém multi-user přístupu. Zachovat ID, workspace a obsah všech existujících entit i relací; **žádná neauditovaná ztráta ani přidání**: počty se mění jen o záznamy, které migrační report výslovně uvádí (doplněné Oblasti a vazby, odstraněné redundantní vazby jako tombstony). Revize existujících záznamů se mění jen u auditovaných úprav (doplnění `kind` u starých Oblastí, odstranění zbylého `properties.areaId` u úkolů v projektu); nejednoznačná přiřazení uvést v migračním reportu a normalizaci zablokovat.
- **Krok 2b – explicitní rozdělení sdílených interních workspaces na 1:1 Oblast:** **před povolením cílového filtru Můj plán a před zavedením identity dalších členů** provést samostatný, auditovaný, zálohovaný a vratný rozdělovací příkaz. Může **změnit interní `workspaceId`**, nikdy stabilní kanonické ID úkolu/projektu/poznámky, jeho historii či obsah. Atomicky převést vazby a scope u child entit, claims, evidence, indexů/cache, historie a tokenů; bezpečně vyřešit nebo **zablokovat** meziarea relace, které by po rozdělení porušily zákaz cross-workspace hran. Nic tiše neodpojit, nesmazat ani nezpřístupnit. Při nejednoznačném scope, nevyřešeném cross-area vztahu, nesouhlasu kontrolních počtů či nemožnosti rollbacku **fail closed**, zachovat původní stav a sdílení vypnout. Ověřit před/po mapu `oldWorkspaceId → newWorkspaceId / areaId` a kontrolní součty entit/relací; ověřené záznamy o přesunu musí být dohledatelné po restore.
- **Krok 2c – kompatibilita Mého plánu:** ještě před aktivací filtrovaného Mého plánu zavést minimální **nullable `assigneeUserId`** a jeho serverový filtr (i kdyby UI výběru řešitele přišlo až později). U všech **otevřených** legacy úkolů, které byly v dnešním shared workspace a aktuálně mají jediného člena/vlastníka, **deterministicky nastavit řešitele = `owner`**. Zachovat jejich deadline, priority, `today/when`, Inbox status, pořadí a všechny existující zobrazované položky. Nikdy stejným pravidlem nepřidělovat úkoly při vzniku skutečně víceuživatelské Oblasti. Porovnat množiny aktivních úkolů Home/Today/Inbox a počty před/po; odlišnost blokuje aktivaci nového filtru. Pozdější migrace identity mapuje `owner` na konkrétní `userId` při zachování odkazu na úkol. Cílené UX přeřazování a notifikace v dalších fázích navazují na již existující assignee atribut.

**Povinná matice migrace workspace-bound záznamů pro krok 2b.** Nestačí změnit `entities.workspaceId`; ve stejném migračním plánu se pro každou interní vazbu jednoznačně určí cílové `areaId/workspaceId`, způsob převodu složeného klíče, revize a zachování významu:
- **Kanonická práce a kontext:** `entities`, `relations`, tombstones, projektové úkoly/poznámky, `pact_context`, `context_subjects/claims/sources/evidence/review_events/change_events`, `note_revisions`, související provenance, ACL/sensitivity, klíče historií a derivované indexy; nepovolené přesahy mezi cílovými workspaces musejí transakci zablokovat, ne být tiše odpojeny.
- **Attention / push:** `attention_states` používá nyní PK `(workspace_id, attention_key)`; přečíslovat/namapovat celý keyspace včetně lifecycle `snooze/dismiss`, nároků na doručení a odvozených klíčů typu `attention:${workspaceId}:…` v `notification_deliveries` / push deduplication. Zachovat identitu výskytu a stav doručení; **žádné znovu odeslané připomínky, opakované poplachy ani oživení dismissed položek**. `push_subscriptions` a recipient scope musí zůstat konzistentní; při pochybnosti potlačit nové doručení do bezpečné rekonsiliace.
- **Kalendář / plán:** `calendar_sources`, `calendar_events`, `properties.calendarDecisions` na workspace entitě, source/occurrence/series klíče, `eventTaskLinks` a `eventTaskId` identity v úkolech, přijaté bloky, `work_sessions`, `work_session_intervals`, `work_session_events` a osobní plánovací záznamy. `calendarDecisions` vlastní dosavadní `owner`; překlíčovat je na jeho osobní stav, nikdy je nepřenést jako sdílené preference. Zachovat datum, časové pásmo, deduplikaci úkolu z události a osobní `hidden/notTask` pro opakování.
- **Návrhy, příkazy a integrace:** `context_commands`, `work_session_commands`, idempotency/revision keys, `pact_agents/tool_permissions/agent_runs`, `ai_proposals`, integrační token scopes a cache. **Všechny nedokončené proposals / dříve schválené, ale dosud neprovedené akce v dotčených workspaces zneplatnit**, nikoliv je mechanicky převést do nové oblasti; nové vyžadují nové scope, revizi a souhlas. Idempotentní výsledky archivovat pod původním auditním klíčem, aby se nikdy nezopakoval side effect. Staré tokeny neeskalovat ani automaticky nerozšiřovat.
- **Zálohy a klientské kopie:** seznam a audit změněných referencí, lokální Dexie/IndexedDB pending změny, zálohy, obnovovací generace a všechny indexy/notification cache. Nejasně přiřaditelný řádek nebo klíč je důvod zastavit migraci v předběžné validaci. Ne každou cache je třeba fyzicky převádět: odvozené indexy lze atomicky zneplatnit a znovu sestavit, ale jejich starý obsah musí být okamžitě nezpřístupnitelný a opětovné doručení již odeslané události se nesmí aktivovat.

**Předčasná sync bariéra nezávislá na budoucí fázi 5.** Protože rozdělení probíhá už ve fázi 2, **před krokem 2b** musí být nasazena minimální bezpečnostní kompatibilita pro stávající `GET/PUT /api/store`: transakční zvýšení `metadata.restoreGeneration` současně s rozdělením a odmítnutí klientského snapshotu ze staré generace s `409 code:"restored"` **před jakýmkoli zápisem**. Starý klient nesmí vrátit původní `workspaceId`, tombstone ani zápis do zastaralého snapshotu. Před migrací vyžádat synchronizaci dostupných zařízení; offline zařízení nelze předem vynutit. Jejich čekající změny se **nesmějí tiše smazat**: po odmítnutí nabídnout bezpečný lokální export/draft a cílenou rekonsiliaci vůči novému `areaId/workspaceId`, s možností přezkumu konfliktů, než dojde k vyprázdnění fronty. Pokud tento upgrade/konfliktové chování klienta není implementované a ověřené, **krok 2b nespouštět**; není dovoleno čekat na fázi 5. Po dokončení lze zavést nový per-item multi-user sync protokol ve fázi 5. Jakákoli obnova staré zálohy nesmí obnovit předmigrační oprávnění ani znovu aktivovat odebraná členství.

Normalizace, rozdělení a backfill proběhnou v **single-user režimu bez pozvánek**; žádná historická data se tak sama o sobě nezpřístupní dalšímu uživateli. Migrace je vratná z ověřené zálohy; následný multi-user režim má oddělený feature gate.

**Historické fáze pro variantu zachování legacy dat (nejsou aktuální roadmapa):**
1. **Spec-only PR:** historické zdokumentování produktového, UX a bezpečnostního kontraktu (bez změn runtime).
2. **Povinné Oblasti + kompatibilní assignee:** normalizace 2a, **předmigrační sync/restoreGeneration bariéra a offline konfliktový postup**, samostatná auditovaná partition 2b do 1:1 interních workspaces a backfill `assigneeUserId` otevřených legacy sdílených úkolů 2c **před UX**, s kontrolou zachování Home/Today/Inbox. Bez dalších identit a bez sdílení.
3. **UX rozsahů:** přepínač Můj plán / Osobní / Sdílené až po 2a–2c a ověření, že nic z dosavadního plánu vlastníka nezmizelo; Home zůstává výchozí.
4. **Identity a pozvánky:** více uživatelů, passkeys a obnovy, ale **vypnuté** faktické sdílení do další fáze.
5. **Serverová ACL a nový sync protokol:** filtrované čtení, per-item zápis/tombstones, membership commands, klientská invalidace a revokace.
6. **Osobní stav a notifications:** per-user plánování, attention, push a offline chování.
7. **Atomický přesun Oblastí a historie:** potvrzování obou směrů, audit, visibility epochs, revizní/TOCTOU ochrana, invalidace indexu.
8. **Pokročilé řešitelství, vlastník a AI/integrace:** UI a akce přidělování pouze editor/admin členům (základní atribut a legacy backfill existuje od fáze 2), privátní externalita, tokeny vázané na identity; Můj plán již využívá assignee před tímto krokem.
9. **Zálohy / import / export:** členství bez možnosti rollback eskalace, recovery a bezpečné exports. **Aktivovat pozvánky a sdílení až po celé bezpečnostní bráně** (nejméně identity, ACL/sync, per-user stav, revokace, historie/přesuny, AI a recovery podle rozsahu vydání).

**Migrační akceptační testy (jen při schváleném zachování legacy dat):** ověřit dva navazující kroky 2a a 2b (nejdřív neměnné, poté auditovaně změněné `workspaceId`), legacy shared workspace s více Oblastmi a cross-area relacemi, bezpečný abort bez ztráty dat a 2c backfill bez ztráty dřívější Home/Today/Inbox práce. ## Personal Context Graph v2 — target specification

Specification revision: 2026-10-02. This section is a product and implementation contract, not a declaration of shipped functionality. It incorporates the reviewed Lumi context prototype into the AI Executive technical foundation while preserving the application's existing architecture.

### Product and deployment boundaries

- Provide an owner-controlled knowledge workspace with an Obsidian-inspired layout, Markdown notes, backlinks, evidence, a relationship map and a review queue. No Obsidian installation, account, subscription or plugin is required.
- Reuse the existing Next.js application, server-side SQLite, authenticated APIs, Dexie cache and PACT services. Do not add a competing Python server, a second task store or an independent approval mechanism.
- Preserve the installable desktop/mobile PWA and the existing always-on self-hosted Node deployment. A Mac-local installation is an optional deployment profile; a native desktop wrapper is not required to deliver the feature.
- The owner chooses the canonical host. In self-hosted mode, data resides on that host and in explicitly permitted device caches; it is not represented as existing only on the Mac. In a Mac-local profile, remote delivery/scheduled work cannot be promised while the host is off.
- Keep the data contract and core portable across operating systems. There is no mandatory third-party synchronization service, model provider or separate graph database.
- Existing task/project/area/note IDs, workspaces, recurrence, calendar scheduling, notification behavior, tombstones and task-action approval policies remain intact.

### Current foundation versus planned work

| Area | Existing application foundation | Graph v2 requirement |
|---|---|---|
| Canonical storage | server SQLite and local Dexie entity/relation cache | versioned claims, sources, evidence and transactional context history |
| Durable context | PACT context items, scopes, provenance and normal/sensitive classification | independently reviewed claims, validity and source-level evidence |
| Owner context UI | list, create and archive in Settings | edit claims, inspect evidence, review conflicts and navigate a graph |
| Mutations | task proposals, owner confirmation, audit and guarded Undo | reusable revision-safe context commands and durable multi-step Undo/Redo |
| External API | planning and allowlisted read tools | versioned evidence-aware reads/proposals, with no external confirmation or Undo |
| Backups | full SQLite-copy backups with Context, history and note versions, restore, export/import package; older JSON backups stay restorable | encrypted backup option |
| Calendar | normalized read-only ICS planning | additional adapters only after the context acceptance gates pass |

The separate Markdown Atlas pilot is migration input, not production infrastructure. Its fixed graph coordinates, entity-wide confirmation, single last-change snapshot, plain ZIP backup and uncalibrated confidence values must not be carried forward as guarantees.

### Entity, claim and evidence model

Reuse canonical task, project, area and note entities by stable ID. Add person, organization, topic, tool, meeting and decision subjects through an explicitly versioned schema or typed subject reference. Do not duplicate a task as a new independently editable commitment: a commitment refers to its canonical task, or remains a proposal until the owner creates one.

A claim records a subject, a typed predicate and exactly one target entity/reference or literal value. A relationship is a claim whose value is another subject. Entity existence, a Markdown mention and claim confirmation are distinct operations.

Required logical records:

| Record | Required information |
|---|---|
| Subject reference | stable ID, subject type, canonical entity ID when applicable, workspace, display title and revision |
| Claim | ID, revision, subject, predicate, typed value or target, review status, freshness, provenance, evidence references, validity interval and recording time |
| Review event | claim/revision, authenticated actor, decision, timestamp and any correction/reason |
| Source | workspace/account, provider, external ID, accessible URL/locator, author/role, source timestamp, ingestion timestamp, content coverage and sensitivity |
| Evidence | source ID, exact message/section locator or bounded excerpt, supported claim and whether it supports or contradicts it |
| Change event | command ID, workspace, actor, object ID, before/after revisions, operation, time and Undo/Redo linkage |

Source IDs, authors, dates and quotes are never fabricated. A missing source remains explicitly missing. A source with metadata-only coverage cannot support claims requiring its unavailable body.

Conversation titles and cached summaries are discovery signals, not biographies. A conversation about a car does not establish ownership; an assistant suggestion does not establish a user commitment. Preserve the distinction between owner statement, source extraction, inference and legacy import. Owner-authored information may be recorded as such without requiring an external citation.

Do not display invented truth probabilities or auto-merge people using an arbitrary confidence threshold. Ambiguous identity matches require review. Conflicting evidence creates a reviewable proposal rather than silently replacing an accepted claim.

### Independent state dimensions

| Dimension | Target semantics |
|---|---|
| Claim review | proposed / confirmed / rejected; confirmation means accepted by the owner |
| Freshness | current / needs_review / stale |
| Canonical task execution | existing task statuses and scheduling semantics; never overwritten by claim review |
| Decision lifecycle | pending / decided / superseded, including the selected outcome |
| PACT scope | existing me / work / family / rules / project / workspace |
| Authorization boundary | one explicit workspace; All my work is read-only aggregation |
| Sensitivity | normal / confidential / restricted in the versioned target schema |

Maintain compatibility with the current normal/sensitive API until a schema migration is deployed. Map normal to normal and sensitive to protected confidential; both confidential and restricted remain excluded from external tools/provider reasoning by default. Preserve stricter imported labels. Unknown mappings fail closed and require review. Changes to public schemas, validators and clients must ship together; documentation alone does not enable new enum values.

Reviewing a claim that a hosting decision is needed must not mark the task done or choose a hosting option. Archived context must not become active during migration. A new claim about a confirmed person still needs its own review.

Track both when a claim was valid and when the system learned it. Unknown dates remain unknown. A time view must distinguish these two meanings.

### Relations and graph semantics

Retain existing canonical relations such as belongs_to_project and belongs_to_area. Add a typed semantic predicate registry with Czech labels, permitted endpoint types, direction and inverse display where useful:

- uses — používá;
- responsible_for — odpovídá za;
- works_for — pracuje pro;
- participates_in — účastní se;
- assigned_to — přiřazeno;
- blocked_by — blokováno;
- arose_from — vzniklo z;
- related_to — souvisí s (symmetric);
- supersedes — nahrazuje;
- waiting_for — čeká na (the target is a person or organization; used by the Context Inbox, the waiting attention rule and the day plan).

Disambiguate legacy owns during review instead of equating ownership with responsibility. A suggested next step is not evidence for blocked_by. Keep documentary provenance in evidence records. A wiki link only creates a navigational mention; it must not silently create a confirmed semantic claim.

Every semantic relation has its own evidence, review state, freshness and temporal validity. Confirming a subject must not confirm its incident edges. Preserve the current prohibition on cross-workspace relations; multi-workspace display does not authorize cross-workspace writes or hidden-node disclosure.

### Persistence, automatic saving and history

SQLite on the selected canonical host is the source of truth. Store Markdown note content with revisions there; Markdown exports are portable editing artifacts, not a concurrent second database. Reuse or extend existing persistence and mutation services instead of duplicating them.

Each command includes an idempotency key, object ID, explicit workspace and expected revision. Validate authorization and schema, commit state plus change history in one transaction, and return the authoritative saved object/revision. A failed transaction must leave neither a partial object change nor an orphaned history entry.

- UI saves owner edits automatically after field completion, with visible saving/saved/error state. A redundant Save button is not required.
- AI edits remain proposals requiring the existing owner confirmation. Owner autosave must not bypass that boundary for AI-generated changes.
- Bind each response to the requested object, not the current selection. Handle fast switching, repeated clicks, stale responses and overlapping edits.
- No-op commands do not consume an Undo step. Retry of one command does not duplicate it.
- Extend the existing guarded Undo model with durable, workspace-scoped multi-step Undo/Redo. A reversal is a new compensating transaction; it does not erase history.
- Show what will be undone and its target. Revision conflicts must never overwrite later edits.
- Preserve task proposal expiry and session binding. Context history must not make expired task proposals executable.
- Keep content-bearing owner history protected and separate from sanitized agent-run/security logs.
- Offline edits, where allowed by sensitivity, remain explicitly pending until the canonical server accepts them. They cannot be consumed as confirmed context by agents. Scope or session changes must not leak cached data.
- Update backup, restore, tombstone, schema-version and sync handling alongside the context tables; an old client must not erase unknown new data.

### Owner workspace and interaction design

Use the current app shell. Left: areas, projects, search and navigation. Center: Markdown note, graph or review list. Right: properties, claims, evidence and history. Keep Czech labels, keyboard access and mobile layout.

Review operates on a specific claim or relationship and shows its source and proposed difference. Actions are confirm, correct, reject and defer. Bulk confirmation, if added, shows the exact set being approved.

The active review action has a filled background after successful save. Do not add checkmarks, crosses or question marks to graph bubbles. Confirmation does not change task completion.

Graph requirements:

- automatic layout for arbitrary subjects; zoom, pan, pinning and persistent layout preferences;
- views around a person/project, open commitments, and changes awaiting review;
- filters for workspace, relation type, review/freshness and time, consistent with list/search;
- directed edges with Czech labels and selectable evidence/history;
- orange for proposed, green for confirmed, red for rejected, gray for stale/archived, with explicit text state in the detail;
- an entity with several claims shows a documented summary: pending current claims take precedence over an all-confirmed appearance; no claims means neutral;
- entity type and workspace use text/shape labels instead of competing status colors;
- distinguish a rejected relationship from a rejected subject and a stale claim from a completed task.

A generic entity-level badge must never imply that every personal fact has been verified. Each successful edit offers a concrete result and Undo. Failed saves retain the draft and explain the conflict/error.

### Context Resolver and external integration

Extend the existing resolver in lib/pact.ts and registered capabilities in lib/pact-tools.ts. The browser-side relation navigator is not an authorization authority.

Every resolved bundle must obey workspace, project, agent/tool permissions, sensitivity, review and freshness before serialization. Canonical task state and confirmed eligible claims form the factual basis. If an operation explicitly asks for proposals, conflicts or stale context, return them clearly separated and labeled. Source evidence cannot be read through a claim if the source itself is forbidden.

Add versioned logical operations for context search, claim explanation and proposed context changes through the Tool Registry. Register them explicitly; do not automatically expose them through the external tools allowlist. Update docs/aifred-openapi.json and route schemas only when implementation and authorization tests are complete.

External ChatGPT/Voice and other conversational clients retain their dedicated-token, single-workspace read/propose boundary. They cannot confirm claims, invoke owner Undo/Redo, read arbitrary files or obtain provider credentials. Owner UI mutations require the owner session and existing same-origin protections.

Project Manager and Meeting Prep should cite eligible evidence, report missing/conflicting context and avoid converting inference into a commitment. Scheduled runs may prepare proposals; they do not self-approve them.

### Security, export and recovery

- Apply authorization server-side to claims, sources, evidence, attachments, history, search, exports and provider bundles. UI filters are not security boundaries.
- Keep database files, raw imports, history snapshots, credentials and backups outside static serving. Preserve production authentication, size/rate limits, origin checks and security headers.
- Render Markdown and labels as untrusted content; no unsanitized HTML or execution of source instructions.
- Treat metadata and derived summaries as potentially sensitive. Derivations inherit source restrictions unless the owner explicitly reviews a downgrade with a recorded reason.
- Keep secrets in existing protected server/OS secret storage, never in context exports or agent bundles. Localhost binding and SQLite do not by themselves provide encryption.
- Support complete versioned exports: manifest, Markdown notes, JSON subjects/claims/relations/sources, JSONL owner history and permitted attachments with checksums. Markdown alone is not a full history/graph backup.
- External Markdown editing requires import against a recorded base revision, diff preview and conflict handling; it must not silently overwrite canonical data.
- Add encrypted consistent backups covering database and attachments, key recovery instructions and a tested restore. Existing logical JSON backups are not described as encrypted.
- Define retention, archive and explicit erasure separately, including derived copies, caches, indexes, content-bearing history and expiry from older backups.
- A private note or source must remain private even if referenced by an otherwise visible subject.

## Persistence and backups

- SQLite lives at `.data/store.sqlite` or `$AI_EXECUTIVE_DATA_DIR/store.sqlite`.
- An existing `.data/store.json` is migrated on first access without changing entity IDs or relations and remains as a recovery copy.
- Named schema/data migrations are recorded in the `schema_migrations` table and each runs once, inside a transaction, when the database is opened (additive and safe on an existing database). Context writes do not change the task-sync revision.
- Full backups (format 2) live in `.data/backups` (0700; files 0600) as `<time>-<label>.sqlite`, a consistent SQLite copy made with `VACUUM INTO` while the app keeps running, with a sidecar `<time>-<label>.meta.json` (format version, time, label, applied migration ids, row counts per included table, size and SHA-256 of the copy). The copy is cleaned before it is published: the rows of the excluded tables are deleted and the file is vacuumed, so passkeys, push endpoints, security logs and the keys kept in `metadata` are not in a backup or an export (only `schema_migrations` stays, to bring an older copy to the current schema; `metadata` keeps only the store revision and its time). Settings creates, lists and restores them. The table scope is one list in `lib/backup-scope.ts` and a unit test fails when a table of the schema is in neither list, so a new table has to be classified.
  - Included (owner data): `entities`, `relations`, `tombstones`, `pact_context`, `pact_agents`, `pact_tool_permissions`, `pact_agent_runs`, `context_subjects`, `context_claims`, `context_review_events`, `context_change_events` (the durable Undo/Redo history), `context_sources`, `context_evidence`, `note_revisions`, `work_sessions`, `work_session_intervals`, `work_session_events`, `attention_states`, `attention_history`, `calendar_sources` (the address of a calendar subscription, which may contain a secret token, is stored encrypted with a key derived from `AI_EXECUTIVE_CALENDAR_SECRET` or the session secret; the backup and the export hold the ciphertext, so a restore on a server with another secret keeps the rows but cannot read the address), `calendar_accounts` (the iCloud account: the Apple ID and app-specific password, and iCloud's principal and calendar-home addresses, encrypted with the same key; only a masked Apple ID is stored in clear; backups are not encrypted yet, so a backup or an export holds this ciphertext like the calendar addresses) and `ai_action_history`.
  - Excluded and kept as they are on restore: `passkey_credentials`, `passkey_challenges`, `push_subscriptions`, `notification_deliveries`, `security_events`, `security_alerts`, `schema_migrations`, `metadata` (except the store revision; the restore generation lives there).
  - Excluded and emptied on restore, because they refer to results or sessions from before it or are a cache: `context_commands`, `work_session_commands`, `ai_proposals` and `calendar_events` (the feed cache; its rows could belong to a source the restored data no longer has and would keep blocking time in the day plan). After a restore or import every restored calendar source is fetched again in the background (failures are only logged), the calendars of a restored iCloud account through that account.
- Restore generation: `metadata.restoreGeneration` counts restores and imports and is incremented in their transaction. Every snapshot the server returns carries it and every save sends the value the client knows. A save with another value (or none, once a restore has happened) is refused with 409 and `code: "restored"` with the current snapshot, writing nothing. The client then does not merge: it replaces its local copy, held-back records, pending markers and merge base with the server's data and shows a notice that the data was restored from a backup and unsent changes made before it were discarded. The same fence applies to every owner-session write of a covered table, not only to record saves: the client adds the header `x-lumi-restore-generation` to every non-GET same-origin `/api/*` request through one fetch wrapper installed at start (`lib/restore-fence-client.ts`), and the owner routes that write covered tables (Context commands, history, sources, evidence, subjects, claims and inbox, work sessions, attention snooze and dismiss, calendar sources and the iCloud calendar account, agent runs, AI action confirm and undo) call `fenceRestoredClient(request)` (`lib/restore-fence.ts`) after authentication: with a server generation above 0 and a missing or different header the answer is 409 `{ code: "restored" }` and nothing is written; a 409 `restored` from any of them goes through the adoption below. Requests with the integration API token are not fenced (they hold no client copy and are not on those routes). `tests/restore-fence.test.mjs` lists every mutating route that does not call it, with its reason. Every way the client learns of a restore uses one function (`adoptServerCopy` in `app/ui/hooks/use-sync.ts`): the explicit restore or import, the broadcast to other tabs, a refused save (start-up saves included) and a pull that sees a new generation. Adoption ends in a page reload, so no state of the replaced data (titles being edited, note and Context drafts, Context, its history, work sessions, note versions) can survive in memory: from its first step the save paths do nothing, and the local database itself refuses every write except adoption's own (a Dexie middleware, `adoptionWriteGuard` in `lib/adoption.ts`, rejects any write outside adoption's transaction), so a save that checked before adoption began and writes after it cannot put replaced data back into the restored copy; pending marks, deletion and restoration markers and note drafts are not recorded either; the local copy, held-back records, markers, merge base, pending flags and every persisted note draft (all pages) are dropped, the snapshot and generation are adopted into IndexedDB and localStorage, the other tabs of the browser are told (`restore-adopted`, or see the new generation in storage) and reload without announcing it again, and the reloaded page starts from the restored state. If the local copy cannot be replaced (for example storage is full) the page still reloads, with the local copy emptied (the database deleted as a last resort) so it starts from the server's data; the success of the server's restore is reported whatever happens to the local cleanup. A per-tab session flag makes it show the success message of Settings (for the tab that ran the restore or import) or the notice that the data was restored elsewhere. This holds for other tabs and other devices. A browser that never stored a generation but has synchronized before (last used before generations were tracked, or dormant) cannot be told apart from one that predates a restore, so once the server's generation is above 0 it adopts like any other (its unsent changes are discarded); only a browser that never synchronized, holding nothing from before, learns the number and goes on. With generation 0 nothing was ever restored and nothing is protected.
- A restore of a full backup: the name and sidecar are checked and the SHA-256 is verified; the backup is copied (the backup file is never modified) and brought to the current schema by the same table setup and registered migrations as the live database, without its start-up side effects (such as the legacy `store.json` import); a copy that names a migration this build does not know (made by a newer version) is refused with nothing changed; a safety backup `before-restore` of the current state is made; then one `BEGIN IMMEDIATE` transaction on the live database with the copy attached replaces every included table (explicit column lists), empties the cleared tables and treats entities, relations and tombstones as the restore of a JSON backup always did (current records the backup lacks get tombstones, tombstones of restored ids are dropped, the store revision moves to the current one plus one, so clients pull and do not write their copies back). An error rolls the transaction back and leaves the live data as it was. Everything in scope returns to the state of the backup, including Context with its Undo/Redo steps and the note versions (no `backup_restore` revision is added); what was created after the backup survives only in the safety backup. The client, after a restore, drops notes being typed, pulls the snapshot and reloads Context, its history, sources, work sessions and the open note's versions. A restore records a security event without content.
- Retention counts `.json` and `.sqlite` backups together per class (daily 30, manual 20, safety 20, other 10) and deletes a backup's sidecar with it. One automatic daily backup (format 2) is created before the first data change of the day, whichever write it is: `ensureDailyBackup()` (`lib/server-store.ts`) runs before the write transaction (never inside one), only when there is data and no usable daily backup exists (a database backup counts with its sidecar and size). Call sites: `replaceSnapshot` (records, links, note revisions), `runContextCommand` (`lib/context-commands.ts`: every claim, person, source, evidence and history command), `transitionWorkSession` (`lib/work-sessions.ts`), `withAttentionTransaction` (`lib/attention-service.ts`: attention states and history), `saveCalendarSource`, `refreshCalendarSource`, `refreshCalDavAccount` and `deleteCalendarSource` (`lib/calendar.ts`), `storeICloudAccount`, `replaceICloudPassword`, `applyICloudSelection`, `disconnectICloud` and `recordRefusedPassword` (`lib/icloud-calendar.ts`), `ensurePACTDefaults`, `saveOwnerContext`, `archiveOwnerContext`, `beginPACTRun` and `finishPACTRun` (`lib/pact.ts`), `confirmAIProposal` and `undoAIAction` (`lib/ai-actions.ts`). A new writer of a covered table has to call it; this list is the checklist.
- Older logical JSON backups (`<time>-<label>.json`: entities, relations, tombstones, revision) stay in the folder, are listed as "Starší záloha — jen úkoly, projekty a poznámky" and restore as before: entities and relations only, Context and note versions untouched, a `backup_restore` revision for the notes that change. Their confirmation says Context is not changed.
- Export: `GET /api/backups/export` (owner session only; the integration token and a request from another origin are refused; rate limited; `Cache-Control: no-store`; `Content-Disposition: attachment`) builds a ZIP from a fresh backup copy with bounded memory (rows are iterated and written in batches, notes one at a time, the database in pieces, a SHA-256 per entry while writing, the manifest last) into a temporary file of its own, runs the importer's own verification on that file (the shared 200 MB upload limit, entry and size limits, the inflate ratio, checksums) and only then streams it; the temporary file and the database copy are deleted afterwards, also when the browser abandons the download. A package the importer would refuse is answered with 413 and nothing is offered. It holds `manifest.json` (format `lumi-export`, version 1, time, migration ids, row counts, size and SHA-256 of every other file), `database.sqlite` (the full backup copy, the only part an import reads), `notes/<id>.md` (each note as Markdown with a small front matter; a reading copy), `data/<table>.json` for every included table (rows as stored, JSON columns stay strings; a reading copy) and `history/context-changes.jsonl` and `history/note-revisions.jsonl`. The export is refused when it would exceed those same limits or the upload limit (so the app never produces a package it cannot import). It contains all workspaces of the instance; there is one owner, so that is the owner's data only, and it is given only to the owner's session. A security event without content is recorded.
- Import: `POST /api/backups/import` (owner session, same origin, rate limited, body up to 200 MB) writes the ZIP to a temporary file, never into the backups folder, reads it in pieces and checks it completely before anything changes: a file that is not a ZIP or is truncated ("Not a valid export file"), names with `..`, absolute or backslash paths, more than 65 000 entries (the ZIP format of the writer has 16-bit counts), an entry above 1 GiB (the archive is read through its central directory, with sizes checked before and while inflating; a streaming reader that looks for entry ends in the byte stream was found to cut valid archives short at random) (the database above 2 GiB) or a total above 4 GiB while inflating (counted as it inflates, not only as declared), a package that inflates more than 200 times what was read once it passes 64 MiB, a missing or extra file compared with the manifest, a different format or version, and any size or SHA-256 mismatch refuse the package with a reason. It then restores `database.sqlite` through the same pipeline as a backup restore (schema check, safety backup, one transaction), with original IDs and no merging.
- Leftover temporary files of a killed restore, import or export (`<data>/tmp`, own prefixes only) are removed when the database opens and before the next one is created, except those of a request still running. Backup, restore, export and import work synchronously in the server process: for a database of about 165 MB this blocks the process for roughly 10 seconds, a known scale limit that is acceptable at personal scale. An unexpected failure answers with a generic message; the detail (which may name paths) is only logged on the server.
- The browser keeps the downloaded export in memory (fetch to blob) before saving it, so the size it can download is limited by the browser, not the server.
- Encrypted backups are not implemented; backups and exports are plain files, so they need the same protection as the live database.
- `AI_EXECUTIVE_DATA_DIR`, when set, must be an absolute path (a relative value would depend on the working directory, so it is rejected: the process stays up, but `next build` fails and every request that touches the store answers 500). After the move to a dedicated service account, production uses `/var/lib/ai-executive`.
- `pnpm check-data <path to store.sqlite>` opens a database (or a copied backup) read-only and prints only integrity results, row counts per table, and size/SHA-256 of the file (plus WAL size); it never prints content, exits 1 when the file has no tables, and should be run as the account that owns the data (opening creates `-wal`/`-shm`).

These describe what is implemented and tested. Encrypted backups and key recovery remain target requirements above; attachments do not exist yet and are not part of an export.

## Read-only calendar planning

MVP7 accepts a private HTTPS ICS feed for one explicit workspace. The bearer
URL is encrypted at rest and is never returned by the API, copied into normal
entities/backups, sent to AI, or included in audit records. Set a stable random
`AI_EXECUTIVE_CALENDAR_SECRET` (at least 32 characters); otherwise encryption
falls back to the session secret, and rotating that secret requires reconnecting
calendar feeds.

The fetcher pins a validated public DNS answer for each HTTPS hop, rejects
loopback/private/link-local destinations and credentials in URLs, revalidates
redirects, and bounds redirects, time, bytes, lines, events and recurrence
frequency. Parsing uses `node-ical` for TZID, RRULE, EXDATE and recurrence
overrides. Only normalized title/time/status data is kept; descriptions,
attendees and locations are discarded. Private events are stored under the
generic title “Soukromá událost”.

Calendar events remain read-only. The Calendar view merges overlapping busy
intervals and shows actual free blocks inside the configured workday; Home shows
today's fixed events and the resulting free capacity. A failed
or older-than-24-hours source is marked stale, and on-demand priorities will not
claim a free slot from stale data. The current horizon is 14 days back and 90
days forward; sources refresh at most every 30 minutes in the single always-on
Node process. Microsoft Graph can later implement the same normalized adapter
without changing the planning model.

**iCloud calendar (CalDAV).** The owner's iCloud calendars are read directly over CalDAV (RFC 4791), read-only, next to any ICS feeds (`lib/caldav.ts`,
`lib/icloud-calendar.ts`, Settings → Calendar, `/api/calendar/icloud`). The owner authorizes Lumi with the Apple ID and an
app-specific password created at appleid.apple.com; the normal Apple password is never asked for. One iCloud account per
instance. Discovery (current-user-principal → calendar-home-set → the collections) validates the password and lists the
calendars whose supported components include VEVENT (reminder lists, inbox, outbox and notifications are left out); the owner
picks calendars and a workspace for each. The browser sees only opaque calendar ids; connecting or changing the selection
discovers again on the server and maps the ids to its own results, so an address from the client is never used.

Stored: a `calendar_accounts` row with the Apple ID and password (JSON, AES-256-GCM with the calendar key, as ICS addresses),
the principal and calendar-home addresses (encrypted too: they contain iCloud's account number), a masked Apple ID
(`j***@icloud.com`) as its label, a status (`ready`, `syncing`, `error`, `auth_failed`) with a fixed error message and the
last success; each chosen calendar is a `calendar_sources` row with provider `caldav`, the account id and the encrypted
collection address. Events are fetched with one calendar-query REPORT per calendar for the same window as ICS (14 days back,
90 days forward), parsed by the same `parseCalendar` (recurrence, private titles masked, cancelled dropped, the size, line,
component and occurrence limits over the whole calendar) and cached in `calendar_events` in the same shape, so planning and
freshness work exactly as for ICS.

### Owner decisions about calendar events

The calendar stays read-only. What the owner decides about an event is stored on the workspace entity (`type: "workspace"`, the
event's `workspaceId`) under `properties.calendarDecisions`, a map of opaque keys to `"hidden"` or `"notTask"`:
`occ:<sourceId>:<slotKey>` for one occurrence and `series:<sourceId>:<uid>` for every repeat; titles are never stored. `slotKey` is the
repeat's place in its series (`<uid>:<RECURRENCE-ID>` for a repeat moved on its own, else the occurrence key), so a decision and the
task made from one repeat (`calendarEventSlot`, matched by `eventTaskLinks`; `eventTaskId` uses it too) follow that repeat when it is moved.
A uid longer than 160 characters is replaced in the key by a short stable digest. Whether an event repeats comes from its
definition (`recurring`: RRULE, RECURRENCE-ID or overrides, set by the parser), never from how many repeats fall into the cached
window (a yearly series has one); events cached before the flag existed are treated as possibly recurring. Only a one-off event
(`recurring === false`) uses the series key for its decision, so it survives the event being moved in the source calendar (which
changes its id and occurrence key).
It is written through the normal local-first path (Dexie, then `/api/store`), so it syncs across devices; the field merge
treats it like `manualOrders` (merged key by key, never reported as a sync conflict, `lib/field-merge.ts`). The client and server
workspace validators accept it only as a plain object of at most 1,000 `occ:`/`series:` keys (each at most 600 characters) with
`"hidden"`/`"notTask"` values (`validDecisionsValue`). Undo of a decision puts back only the keys that write changed, on the record as
it is then, so a decision or rename made meanwhile on another device stays. A write prunes occurrences that started more than 30 days ago and keeps
at most 500 keys (`lib/calendar-decisions.ts`); the local placeholder of the personal workspace (timestamp 0) is never written.
Decisions belong to the owner's own view (owner decision 2026-10-23): "not a task" and "hidden" describe how one person treats an
event, not a fact about the shared calendar. Today every workspace, shared ones included, has a single account (invitations stay
disabled), so storing them on the workspace entity affects only the owner. Before additional accounts are enabled, decisions must
move to per-member storage (or be keyed by member) so one member's decision never changes another member's agenda or busy time.
Busy time has one definition, `effectiveBusyEvents(events, decisions, tasks)` in `lib/calendar-decisions.ts`: a busy event that is
not hidden and has no task pointing to it. The client (`mergedBusy`, free hours and windows, Calendar conflicts) and the server
(`calendarAvailability` through `effectiveBusyEventsFor` in `lib/calendar.ts`, which reads the workspace entity and tasks from the
store snapshot; so the day plan, task suggestions, priorities and meeting prep) both use it. Hidden events are listed only in the
Calendar view (faded); an event with a task is listed once, as that task, and Today/Home leave it out. “Yes” on “Je to úkol?”
creates an ordinary task with `properties.calendarEventId` (the event's id), `calendarEventKey`, `calendarSourceId`, `calendarEventUid`,
`calendarEventSingle` (for an event that was not recurring; such a task is also matched to its event by source and uid when the id
changed, as long as the calendar defines that event as a one-off and only one cached event has that uid; `eventTaskLinks`), `when` (the
event's date in the calendar time zone) and `estimatedMinutes` (the event's length, 5–480); no deadline is set. Its id is
derived from the workspace, source and the event's identity (uid for a one-off event, the occurrence for a repeat; `eventTaskId`),
so two devices answering "Yes" for the same event create one record that the sync merges by id; a re-created task revives that id. The one-line
reprioritization suggestion (`reprioritizeSuggestion`) compares the day's known task estimates (the new task included) with the
free time computed from the effective busy events; it is shown once per view (Home, Today, Calendar), since the event leaves
Today's and Home's agenda as soon as it is a task. Agents' calendar listings (`lib/pact.ts`, the `calendar.read` tool) leave out hidden
and converted events too (`visibleCalendarEventsFor`).

Requests go only to `caldav.icloud.com` and `pNN-caldav.icloud.com` over HTTPS on port 443, to a validated public address
pinned for the connection; every hop of a redirect (at most three) and every address in a response is checked against that
list before anything is sent, so the Basic authorization header never leaves iCloud. Responses are capped (2 MB per PROPFIND
and per REPORT, 5,000 resources) and bounded in time like ICS. XML is parsed by `fast-xml-parser` with namespaces resolved by
URI; a document type or entity declaration is refused. Refresh: the scheduler takes at most one account per pass (all its
calendars, the same 30-minute interval and `syncing` claim as a source); the Settings button refreshes on demand. A 401 or 403
marks the account `auth_failed`: nothing contacts Apple for it again, automatically or by Refresh, until a new app-specific
password has been validated, so a revoked password cannot get the Apple ID locked. Network errors and 5xx answers are `error`
and retried by the scheduler. The Apple ID, the password, the account number and the addresses never appear in error
messages, logs, security events or responses; responses carry `cache-control: no-store`. Discovery, connect, password change
and calendar selection share a limit of 10 per hour. Actions that ask iCloud before writing (including recording a refused password found while listing calendars) check the
restore fence once more right before their synchronous write. A refresh writes the account's final state only if the account
still has the revision and update time it claimed, so a disconnect, a new password or a restore during the refresh is never
overwritten (likewise, for ICS and iCloud alike, a calendar's events and state are written only if the calendar still has the revision and
workspace it had when its refresh began; a calendar moved to another workspace or deselected meanwhile gets nothing from the
old fetch, and an account refresh fetches a moved calendar once more). Connecting a second Apple ID is refused before anything is sent to Apple, and an unknown action is refused before
any rate limit is counted. Disconnect removes the account, its calendars and their cached events in one
transaction. Writing to the calendar is not implemented.

The browser tests point CalDAV at a local mock server (`e2e/caldav-mock.ts`); the server honours that address only when
`AI_EXECUTIVE_E2E=true` and `AI_EXECUTIVE_E2E_CALDAV_URL` (an `http://` loopback address) are both set in its environment,
which only `playwright.config.ts` does. No request can change it.

Lumi's task suggestion endpoint is authenticated, same-origin protected and
workspace-scoped. It compares the new title with project names and earlier
related tasks, estimates effort from explicit duration or task type, and checks
the next 14 configured workdays for up to three sufficiently long free intervals. The
suggestion is advisory: Quick Capture shows every proposed field before save,
allows edits or one-click opt-out, and never blocks task creation when calendar
data or the suggestion service is unavailable. Only the confirmed values are
stored on the task; those final project and area relations become historical
evidence for future suggestions, including when the owner corrected Lumi.

The application badge counts all open tasks whose scheduled date or deadline
is overdue, today or tomorrow. Foreground sync updates it through the Badging
API and every visible Web Push carries the current canonical count for the
service worker to apply while the installed app is closed. The count is cleared
at zero. iOS requires a Home Screen installation, HTTPS, notification permission
and the system Badges toggle; macOS requires an installed web app (for Safari,
Add to Dock). The Install app settings card reports installation, permission,
Badging API support and the canonical count, and provides a one-item badge test
plus a control to restore the real count. Browsers without the Badging API
continue without an in-app badge.

## Semantic knowledge memory — Variant C (target architecture)

This section specifies a target capability, not a deployed feature. It extends Context Graph v2 within the existing SQLite, Dexie, PACT, approval, and audit contracts. PostgreSQL, pgvector, a second canonical database, and a parallel HumanAgentWiki deployment are out of scope.

### Context Search & Explain — backend v1 (2026-10-20)

The first shipped slice of the Context Graph retrieval target is **canonical lexical search**, not semantic/embedding retrieval. It does not create a new table, derived index or browser cache. It re-reads current SQLite context and workspace entities for each request. Search reads one canonical entity snapshot plus a bounded joined SQLite query for claim and subject rows, rather than reading/parsing the full store per claim; protected evidence is excluded by SQL before external serialization. An additive migration installs `context_evidence_claim_guard_idx(claim_id, archived_at, workspace_id)` to make the correlated external evidence guard index-backed. The SQL intentionally does not constrain `e.workspace_id` before checking it, so malformed cross-workspace evidence remains a reason to deny the entire claim; the scale test asserts this guard's actual SQLite `EXPLAIN QUERY PLAN` and checks active normal, confidential, foreign-workspace and orphaned evidence.

- Owner cookie endpoints: `GET /api/context/search?workspaceId=<id>&q=<text>&kinds=person,project,claim,relation&limit=15&cursor=0` and `GET /api/context/explain?workspaceId=<id>&claimId=<id>`. They return `schemaVersion: 1`, with `Cache-Control: private, no-store`. Owner explanations include bounded active evidence (up to 10), review decisions (20), change-history summaries (20) and related claims (15). An archived claim remains explainable to its owner, but never becomes agent-eligible. The explanation explicitly distinguishes `eligibleForInternalAI` (the existing resolver can redact individual protected sources while keeping an eligible claim) from `eligibleForExternalSearch` (strictly excludes claims citing any protected source); `internalBlockers` and `externalBlockers` use the same respective policies.
- Search ranking: normalized Unicode case/diacritics, exact title first, then title prefix, then substring across title and claim literal. Newer revisions break ties. The strict upper bound is 30 hits per page; cursor is an offset over the reauthorized result set, not a durable snapshot token. It accepts up to 15,000 combined results (5,000 people, 5,000 projects and 5,000 claims/relations). For owner reads only, `partial: true` discloses if a 5,000-record per-category canonical scan was capped. External responses omit this flag entirely to avoid leaking counts of protected candidates; no semantic coverage is claimed.
- Integration: `POST /api/integrations/aifred/tools` may accept `tool: "context.search"` after bearer authentication **and** explicit opt-in through `AI_EXECUTIVE_CONTEXT_SEARCH_WORKSPACES` (comma-separated exact workspace IDs; empty by default, `*` and `all` do not grant access). The tool is registered read-only. Only current, confirmed, normal, valid, non-archived claims with live references and exclusively normal, non-archived sources are searchable. External responses are deliberately restricted to concise claim/relationship fields; they include **no source, evidence, excerpt, citation locator, review history, or owner explanation**. People and project objects without eligible claims are not separately exposed.
- Source details and change history are **only** available from the cookie-authenticated owner explanation route. Owner routes reject any Authorization header; integration tokens are not owner credentials. Every query requires one existing workspace. Return a not-found for a claim in any other workspace, without leaking its title or existence. No request parameter can enlarge privileges.
- This slice does not grant Shared viewers an independent role: current authentication only exposes the owner session. Any future viewer/member API must have explicit role- and workspace-aware ACL enforcement *before* these endpoints are exposed to those identities. Cross-workspace aggregation, semantic retrieval, historical revision fetch, raw source search, citations to external clients and MCP explain remain out of scope.
- Tests: `tests/context-search.test.mjs` and `tests/context-search-scale.test.mjs` cover owner search, external deny-by-default, cross-workspace access, sensitivity, source inheritance, archived/expired/stale/pending claims and response bounds, with a ~5k claim and multi-thousand entity performance/cursor regression. `e2e/context-search-auth.spec.ts` checks the actual HTTP owner versus bearer cookie boundary. Full Browser E2E on the exact release SHA is mandatory before server deployment; pull requests use the lighter PR Checks gate (see AGENTS.md and DEVELOPMENT.md).

### Canonical data and derived index

SQLite on the canonical server owns notes, entities, claims, evidence, sources, relations, revisions, archival state, and authorization metadata. A separately stored, versioned semantic index is rebuildable from those records. Each entry identifies the canonical object and section IDs and revision, workspace, sensitivity and access-policy fingerprint, content type, language, model and index versions, indexing time, and status. Text fragments and vectors are retained copies with their own deletion policy.

The index has no independent write authority or history of truth. Index only after canonical validation. Archive, deletion, revision, workspace, sensitivity, or permission changes make affected entries unavailable immediately at retrieval, even while removal or reindexing is pending. A transactional outbox and idempotent worker reconcile the index; stale entries cannot be presented as complete. Periodic reconciliation checks counts and revisions against SQLite and supports a full rebuild without claiming completeness during the rebuild.

### Server-local embedding and evaluation

Embedding inference and the vector index run on the canonical server, outside static serving. No model, vector index, or embedding corpus is distributed to the PWA. Local inference sends no source content to an external provider. Model artifacts have verified origin and integrity; text copies, vectors, and caches follow source retention and erasure rules.

BGE-M3 is an evaluation candidate, not a selected model. Stage 1 defines numeric pass/fail thresholds *before* benchmarking: recall@k and nDCG against a lexical baseline on a human-judged Czech and mixed-language holdout; first-result latency; full and incremental reindexing time; peak RAM and disk; model download size; and the permitted operating hardware. It also fixes dataset provenance, measurement procedure, privacy rules, and fallback criteria. Stage 2 records results and model choice without protected content in telemetry. A failed benchmark keeps lexical retrieval as the supported path.

A missing model, indexing failure, or rebuild does not block authorized exact and metadata search. The response identifies which sources and index revisions were actually searched and does not imply complete semantic coverage.

### Typed resolver and optional MCP

Only the server-side PACT Context Resolver combines lexical and semantic candidates. Before retrieval and again before serialization, it checks one explicit workspace, actor and session, subject and project scope, tool and agent allowlists, sensitivity, claim review status, freshness, source access, and size limits. Authorization applies before ranking and after it; neither a client cache nor a language model grants access.

Versioned read-only operations are `context.search` (typed exact, full-text, or semantic candidates with canonical ID, match type, provenance, freshness, and citation locator), `context.get` (one authorized object, claim, or section at a requested revision), `context.neighbors` (requested graph edges with type, direction, review state, evidence, and depth/count limits), and `context.explain` (why a claim, documentary link, or similarity was returned, including index/model version and freshness limits). A requested historical revision is returned only after the current ACL, workspace, sensitivity, archival, deletion, and source/evidence checks; it never revives access to content that is no longer eligible. Citations and excerpts apply the same current checks. Similarity is ranking metadata, never a truth probability.

Optional MCP may expose these four explicitly registered operations, including `context.explain`, as audited, rate- and size-limited read-only tools. It does not expose confirmation, Undo/Redo, arbitrary SQL, filesystem access, raw indexes, or provider credentials. Existing token and allowlist rules continue for external ChatGPT and Voice; new OpenAPI or MCP operations require implementation, authorization tests, and versioning.

The existing Context Graph claim schema uses `normal`, `confidential`, and `restricted`. Legacy `pact_context` and compatibility API inputs retain `normal`/`sensitive`: map legacy or input `normal` to `normal`, map `sensitive` to `confidential`, retain stricter imported labels, and fail closed as `restricted` on unknown mappings. The index derives its sensitivity from the current canonical claim, source, or entity using that mapping; it never weakens a source restriction. Both `confidential` and `restricted` are excluded from external provider bundles and MCP responses by default, even when the actor can view them in the UI. Workspace type and sensitivity are checked independently; Personal and Shared are workspace boundaries, not sensitivity values.

### Safe wikilinks and graph meaning

Parse only `[[target]]` and `[[target|label]]`. At note save time, resolve an explicit stable target ID or an unambiguous title *among targets the editor is authorized to access in the selected workspace*, and persist the resolved target ID with the source note revision. The displayed alias may change without retargeting the link. An unresolved, ambiguous among accessible targets, or inaccessible target remains safe plain text or a repair suggestion; indistinguishable error behavior and counts must not reveal hidden targets. Rendered Markdown is sanitized and never executes link content.

A wikilink is a documentary navigation mention with note provenance. It does not create a subject, confirmed claim, or semantic relation. The graph keeps separate layers for typed evidence-backed claim relations, documentary mentions, and transient ranking similarities. Only a confirmed eligible claim relation can supply an agent or plan with a semantic fact. Each edge shows type, direction, review state where applicable, freshness, validity, provenance, and evidence; similarity displays model/index version rather than confidence. Automatic similarity cannot alter a claim or relation without the existing proposal and owner review process.

### Citations, audit, offline behavior, and recovery

Citations bind stable source, object, revision, and section locators to a bounded authorized excerpt. Retrieval audit records actor, tool, workspace, policy and model/index versions, canonical revisions, time, and outcome; queries and content require an explicit protected retention policy. Derived metadata inherits the strictest source restriction until an audited owner-approved downgrade.

Reindexing is scoped by workspace, resumable from checkpoints, and never advertises complete results during a full rebuild. Offline PWA search is lexical only over previously synchronized canonical Dexie data and visibly labels its coverage as a local subset. Semantic search, candidate combination, `context.explain`, and MCP calls require the server. Existing offline behavior remains: a previously synced, signed-in PWA can display all canonical data it holds and queue allowed edits under the Current MVP contract. No new expiring authorization lease hides that existing data while offline.

New semantic-result excerpts and derived search caches are separately scoped to workspace and actor and must not extend canonical offline retention. They are cleared on sign-out and invalidated on workspace, permission, or sensitivity changes when the client next connects; no client-side vector index is kept. Confidential and restricted material is excluded from external provider and MCP paths by default. Server retrieval rechecks current authority, so stale derived entries cannot leak after revocation. Full backups and exports cover canonical data and provenance. An optional encrypted vector snapshot is verified against canonical revisions on restore and discarded and rebuilt when mismatched.

Stages: (1) contracts, representative corpus, numeric evaluation gates, and canonical outbox; (2) server-local lexical/semantic retrieval, BGE-M3 benchmark, and fallback; (3) saved-ID wikilinks, graph layers, and freshness UX; (4) Resolver operations and optional MCP with negative authorization tests, including revoked/archive/delete/restrict access to historical revisions, evidence, citations, and excerpts; (5) encrypted restore, retention, and interruption/retry tests. Each stage reports shipped versus target status and requires no new external account, production deployment, or external model transfer by itself.

Receipt je klíčovaný aktér + úkol + `commandId` a status čte jen receipt vlastní identity po ověření aktuálního práva zápisu: B se nedozví ani nepřehraje výsledek příkazu A (stejný `commandId` od dvou editorů jsou dva nezávislé příkazy) a bývalý editor po snížení nebo odebrání nezjistí nic. Odvolaná durable session je ověřena v transakci před změnou i těsně před `COMMIT` (401, nic se nezapíše). Záměrně konzervativní CAS: jakákoli změna členství nebo role v Oblasti (přidání, odebrání, změna role kteréhokoli člena) zvýší `policy_revision` a zneplatní všechny dosud vydané tokeny názvu pro úkoly této Oblasti (409, klient musí načíst detail znovu); přeřazení téhož úkolu zneplatní jeho token také, protože se mění revize úkolu.

Samostatný povolený SQL bump `tasks.revision` také zneplatňuje cursor. Regresní test kontroluje i skutečný `EXPLAIN QUERY PLAN` nad stejným SQL, jaké se používá k výpočtu cursoru. **Tombstony, změnový záznam a smazání úkolu (R2c.1, pouze izolovaný staging, bez UI, za stávajícími HTTP + write příznaky):** staging schema **v8** (`TARGET_STORE_SCHEMA_VERSION = 8`; v7 se nemigruje, preflight ho odmítne a vyžaduje nový bootstrap) nahrazuje dočasný zákaz mazání trvalými tombstony a změnovým záznamem. **Tombstony:** `task_tombstones` a `project_tombstones` (`id`, `area_id`, `revision`, `change_seq`, `deleted_at_ms`, `WITHOUT ROWID`) nesou jen neprůhledné ID, Oblast v okamžiku smazání, revizi `původní + 1`, sekvenci svého záznamu ve změnovém záznamu a čas, nikdy název ani jiný obsah. Jsou neměnné (žádný UPDATE), nesmazatelné (žádný DELETE ani po retenci), chráněné proti `INSERT OR REPLACE` už v BEFORE INSERT a mají kapacitu `TARGET_STAGING_MAX_TOMBSTONES = 4096` na tabulku (fail closed). Tombstone lze vložit jen pro **žijící** řádek, s revizí přesně `revision + 1`, v jeho aktuální efektivní Oblasti (u úkolu v projektu v Oblasti projektu) a s `change_seq` rovnou přesně příští sekvenci změnového záznamu. `task_deletion_guard` povolí DELETE úkolu jen s takovým tombstonem; `task_conflict_guard` odmítne vložení úkolu s tombstonovaným ID (též `INSERT OR REPLACE`/`OR IGNORE`), takže smazané ID nelze znovu použít a nevznikne ABA; `immutable_task_id` zůstává, protože přejmenování by ochranu obešlo. Stejná pravidla platí pro projekty (`project_deletion_guard` navíc nikdy nesmaže projekt s úkoly; příkaz smazání projektu v R2c neexistuje, trigger je jen hranice pro surové SQL). Smazání zvýší `content_revision` **staré** efektivní Oblasti o 1 ve stejné transakci, takže cursory přes tuto Oblast (#155/#157) skončí jako `Cursor stale` / `read_stale_reload`. `task_title_audit.task_id` už nemá cizí klíč na `tasks`: content-free auditní řádky smazaného úkolu zůstávají, ale `GET .../audit` pro smazaný úkol vrací stejné nerozlišitelné 404 jako pro neexistující. **Změnový záznam:** `change_log(seq AUTOINCREMENT, entity_kind task|project|membership, entity_id, area_id, op upsert|leave|tombstone|member_add|member_remove|member_role, revision, member_user_id, member_role)` s CHECK vazbami op/kind/nullability, bez obsahového sloupce. Zapisují ho **výhradně SQLite triggery** ve stejné transakci jako změna, takže se loguje i přímé staging SQL: vložení úkolu a každý posun revize (`task_area_content_insert`/`_revision`) dá právě jeden `upsert` v nové efektivní Oblasti; přesun úkolu mezi Oblastmi (přes `area_id` nebo `project_id`) navíc právě jeden `leave` pro původní Oblast s novou revizí (`task_area_content_move_old`, **BEFORE UPDATE**; zapíše `leave` ještě před vnější změnou řádku a před následným `upsert` z AFTER triggeru, takže `seq(leave) < seq(upsert)` bez závislosti na pořadí AFTER triggerů; revize se vždy zvýší o 1, proto oba záznamy nesou `OLD.revision + 1`; vnořený UPDATE revize na BEFORE trigger nesedí, takže duplicity nevznikají), změna rodiče uvnitř téže Oblasti jen `upsert`. Smazání úkolu/projektu zapíše `tombstone` s revizí tombstonu. Projekty logují `upsert` při vložení a posunu revize; trigger přesunu projektu (`project_change_log_move`, dnes nedosažitelný, protože `project_area_assignment_guard` přesun zakazuje a odemkne ho až potvrzený příkaz) by zapsal `leave` + `upsert` pro projekt i pro **každý podřízený úkol** (revize úkolů se nemění, zapisuje se aktuální) a zvýšil `content_revision` obou Oblastí vždy jednou. `area_members` INSERT/DELETE/změna role zapíše `membership` záznam (`entity_id` = Oblast, `member_user_id`, role po změně, `NULL` při odebrání; stejná role nic nezapíše). Záznam je append-only (žádný UPDATE ani DELETE), `INSERT OR REPLACE` stávající sekvence je odmítnut, explicitní `seq` musí být kladná a striktně větší než všechny uložené. **Návrh `change_seq` tombstonu:** tombstone se vkládá **před** DELETE s `change_seq = MAX(seq) + 1` (BEFORE INSERT trigger ověří přesně tuto hodnotu, existenci žijícího řádku, revizi i Oblast); `AFTER DELETE` trigger úkolu pak vloží záznam `tombstone` s **explicitním** `seq` z tombstonu a monotónní kontrola odmítne celý DELETE, pokud mezitím vznikl jiný záznam. Tombstone, záznam a DELETE se tak nemohou rozejít ani při surovém SQL, nepoužívá se žádný placeholder a příkaz navíc po DELETE zpětně načte záznam a ověří shodu `seq`, Oblasti a revize. **Preflight** (`tombstone_invalid`, `audit_invalid`) ověřuje ohraničeně (primární klíč a částečný index, nikdy sken celého logu): každý tombstone má záznam `tombstone` se stejným `seq`, ID, Oblastí a revizí, žádný žijící úkol/projekt nenese tombstonované ID, počet záznamů `tombstone` se rovná počtu tombstonů, kapacita je dodržena a každý řádek `task_delete_audit` má receipt a odpovídající tombstone. **Příkaz smazání:** `deletePreflightedTargetTask` (`lib/target-task-delete-writer.ts`) má stejný základ jako zápis názvu (pinned fd, `BEGIN IMMEDIATE`, kanonický preflight, fingerprint, živá session před změnou i těsně před `COMMIT`, fail closed při kapacitě) a pevné pořadí: identita, session, ACL, receipt (replay/konflikt), CAS (stejný token jako `snapshotRevision` z detailu), `stale_revision`, kapacity, tombstone, DELETE, ověření právě jednoho záznamu `tombstone` se shodným `seq`, receipt, `task_delete_audit`, session, COMMIT. Požadavek je přesně `{commandId, taskId, expectedRevision}`. Právo je stejné jako pro název: vlastník soukromé Oblasti nebo editor/admin sdílené; viewer, nečlen, cizí soukromý i neexistující úkol vrací nerozlišitelné `unavailable` (HTTP 404). **Opakování po úspěchu:** pokud úkol už neexistuje a existuje tombstone, vyhodnotí se právo zápisu proti `area_id` z tombstonu a AKTUÁLNÍ roli aktéra v ní; je-li povoleno a aktér má vlastní receipt pro (aktér, úkol, `commandId`), vrátí se `{ok:true, replayed:true}` (jiný digest = `idempotency_conflict`), jinak `unavailable`. Tombstone se tak nikdy neprozradí aktérovi bez práva zápisu v Oblasti, ani editoru, který příkaz nevydal. Receipt je v samostatném jmenném prostoru metadat `r2:task-delete-receipt-v1:` + SHA-256 (aktér, úkol, `commandId`), digest je SHA-256 (úkol, `expectedRevision`); strop `TARGET_STAGING_MAX_RECEIPTS` (4096) se počítá **zvlášť** pro delete receipty, takže příkazy názvu a smazání se vzájemně nevyčerpají (celkem nejvýše 2 × 4096 receiptů). `task_delete_audit` je content-free append-only (`receipt_key`, aktér, úkol bez FK, Oblast, `policy_revision`, `revision_before`, `tombstone_revision`, `change_seq`, `expected_revision`, restore generace, čas) se stejnými triggery neměnnosti, 90denní retence, ochrany proti nahrazení a kapacity 4096 jako audit názvu. Smazání úkolu s řešitelem je povoleno editoru/adminovi bez další podmínky; `member_revocation_guard` a guardy snížení role po smazání nenacházejí žádný úkol, takže odebrání řešitele nic neodřazuje. **Ověření výsledku:** `verifyTargetTaskDeleteCommand` přes `POST .../delete/status` s `{commandId, expectedRevision}` vrací `committed` | `not_recorded` (jen u stále existujícího úkolu), konflikt obsahu pod týmž `commandId` je `idempotency_conflict`; stejné tombstone-aware ACL, takže aktér bez receiptu dostane u tombstonovaného ID nerozlišitelné 404. **HTTP** (`POST /api/target-staging/tasks/[taskId]/delete` a `.../delete/status`, za HTTP + write příznaky) kopíruje bezpečnostní pořadí routy názvu (příznaky, identita, konfigurace, parametr, same-origin a `Origin`, `admitStagingIdentity` a vlastní limiter, teprve potom tělo ohraničené na 32 KiB, validace, živá kontrola, podproces, `no-store`) s kódy 200 `{ok:true}` / `{ok:true,replayed:true}`, 400, 401, 403, 404 (nerozlišitelné, vč. vypnutého příznaku), 409 `{"error":"Revision conflict","code":"stale_revision"|"idempotency_conflict"}`, 429 (30/10 min smazání, 60/10 min status), 503. Smazaný úkol zmizí ze seznamů (`personal`, `shared`, `my-plan`), z detailu i z auditu (404) a cursory přes jeho Oblast jsou zneplatněny. Příkaz přesunu položky ani znovuvytvoření ID v R2c HTTP neexistuje; ochrany platí pro surové SQL a knihovní operace. **Rekonciliace preflightu:** receipty `r2:task-delete-receipt-v1:` jsou 1:1 s řádky `task_delete_audit` (receipt bez auditu, např. surově vložený pro žijící úkol, store zablokuje). Poslední záznam `upsert`/`tombstone` každé entity musí odpovídat živému stavu (žijící úkol/projekt: `upsert` s aktuální revizí a efektivní Oblastí; neexistující: `tombstone` se `seq` = `change_seq`; záznamy `leave` se ignorují, takže nezáleží na pořadí spouštění triggerů), poslední záznam členství na dvojici (Oblast, uživatel) musí odpovídat živému řádku `area_members` nebo být `member_remove` (`change_log_invalid`, `membership_log_invalid`; množinové SQL nad indexem plného klíče, od v9 `change_log_by_key(entity_kind, entity_id, member_user_id, seq)`). Každé ID úkolu/projektu, které se kdekoli ve změnovém záznamu objeví (i jen jako `leave`), musí být živé nebo tombstonované, a každé `member_remove` musí mít dřívější `member_add`/`member_role` téže dvojice. **Změnový záznam nemá na stagingu kapacitní strop** (na rozdíl od ostatních ledgerů) a roste až do komprese/retence v R2c.2; cena rekonciliace v preflightu každého požadavku s ním roste (změřeno cca 37 ms při 204 tis. řádků úkolů; kontroly členství jsou jedna agregace na dvojici Oblast–uživatel, takže cena roste lineárně s logem i při velkém pohybu členů). **Doplňující pravidla:** `commandId` platí v rozsahu (aktér, úkol) u receiptů názvu i smazání, stejné `commandId` u jiného úkolu je samostatný příkaz. ID úkolů a projektů jsou byte-přesné identity (bez normalizace velikosti písmen či mezer); ochrana tombstonem platí pro byte-shodná ID a klient v R2c ID nevytváří. Hranice důvěry: surový SQL/`writable_schema` přístup k staging souboru je mimo model hrozeb; preflight nekonzistence jen zjistí a store selže uzavřeně (503). Osamělý tombstone (bez DELETE) store zablokuje, dokud ho operátor neopraví v novém staging store; automatická oprava neexistuje. Kapacity stagingu (tombstony, delete receipty, delete audit po 4096) jsou trvalé provozní limity stagingu; produkční limity určí R4. 409 u rout smazání nese strojový `code` (`stale_revision` | `idempotency_conflict`); routy názvu si ponechávají dosavadní tělo kvůli kompatibilitě. Kontrola owner cookie po commitu může stejně jako u title PATCH ohlásit potvrzené smazání jako zamítnuté; klient se zotaví přes status endpoint nebo přesné opakování (`replayed`).


**Bootstrap a autorizovaný změnový feed (R2c.2a, pouze izolovaný staging, bez UI, za stávajícím HTTP příznakem, výchozí vypnuto):** `GET /api/target-staging/changes[?cursor=<opaque>]` (jediný povolený parametr; pokud `cursor` chybí, začíná bootstrap; explicitně prázdný `?cursor=`, neznámý či opakovaný parametr a cursor delší než `MAX_FEED_CURSOR_LENGTH` (3452 znaků, pevná délka každého vydaného cursoru) vracejí HTTP 400 `{"error":"Invalid request"}` po ověření identity a bez spuštění čtecího podprocesu). Stejná admission jako čtení seznamů (flag 404, živá session nebo owner cookie → 401, session-check bucket, vlastní limiter `target-staging-changes` 300/10 min na klienta, izolovaný čtecí podproces `target-staging-feed-child.mjs`, `Cache-Control: no-store`, živý linearizační bod před uvolněním těla). Podporuje owner cookie i trvalou session cookie. Cursor se ověřuje a dešifruje v rodičovském procesu (tajemství podproces nikdy nedostane); podproces dostane jen dešifrované claimy, znovu je validuje a porovná se snapshotem. **Mechanismus níže (kryptografie cursoru a pravidlo viditelnosti) je návrh předložený ke schválení vlastníkem v tomto PR.**

- **Cursor.** AES-256-GCM, pro každý token nový náhodný 96bitový nonce, klíč z HKDF-SHA256 nad stávajícím `AI_EXECUTIVE_SESSION_SECRET` s vlastním doménovým řetězcem `lumi:r2c:feed-cursor:v1` (oddělený od HMAC domén cursorů seznamů). Token = `base64url(verze 1 B ‖ nonce ‖ ciphertext ‖ tag)`, AAD je doménový řetězec; otevřený text se vždy zarovná mezerami na jednu pevnou velikost 2560 B (pokrývá nejhorší platné claimy; delší se odmítne), takže všechny tokeny mají stejnou délku (3452 znaků) a nic z nich nelze vyčíst; ID v klíčích musí být dobře utvořené UTF-8 a řazení keysetu v JS i SQL je po bajtech UTF-8. Claimy: `v`, `uid` (aktér), `epoch` (`revocation_epoch` identity při vydání), `gen` (`restore_generation`, zároveň ID instance store, protože je to náhodné UUID na bootstrap), `iat` a stav pozice. **Od R2c.3 nese každá úspěšná odpověď také `restoreGeneration` store (viz zápisový kontrakt).** **Feed cursor záměrně NENÍ vázaný na session** (na rozdíl od HMAC cursorů seznamů z R2-ID.1): po `revokeSession` pokračuje nová session téže identity se starým cursorem; sám nikdy neautentizuje, každý požadavek vyžaduje živou session. Pozice: `b` (bootstrap: watermark `W` a poslední klíč `(areaId, kind, id)`), `f` (feed: `p` = sekvence posledního záznamu posuzovaného pro tohoto aktéra, nikdy hlava logu), `a` (bootstrap jedné Oblasti: `areaId`, sekvence grantu, poslední klíč `(kind, id)`). Chyby: nedešifrovatelný/poškozený cursor (prázdný nebo příliš dlouhý cursor v dotazu je 400 `{"error":"Invalid request"}` po ověření identity, bez dešifrování a bez spuštění čtecího podprocesu), `uid` ≠ aktér nebo `epoch` ≠ aktuální epocha → 400 `{"code":"cursor_invalid"}`; `gen` ≠ aktuální → 409 `{"code":"resync_required"}` (pořadí kontrol: `uid`, `gen`, `epoch`); změna členství mezi snapshotem a uvolněním → 409 `{"code":"read_stale_reload"}` (klient zopakuje stejný cursor). Retence a komprese logu a odlišené kódy 401 patří do R2c.2b.
- **Bootstrap (bez cursoru).** Server v prvním snapshotu zachytí `W = COALESCE(MAX(seq),0)` a vrací aktuální stav čitelných položek aktéra (soukromé Oblasti vlastněné aktérem a sdílené Oblasti, kde je člen, nejvýše `MAX_SCOPED_READ_AREAS`), keyset stránkováním podle `(areaId, kind, id)` (BINARY), nikdy offsetem, po 100 položkách; odpověď `{"phase":"bootstrap","items":[...],"more":bool,"cursor":...,"restoreGeneration":"<uuid>"}`. Poslední stránka (`more:false`) vrací cursor ve fázi feedu s `p = W`. Oblast, kterou aktér od začátku bootstrapu ztratil, se přeskočí a oznámí se jednou `access_lost` (jen pokud byl v `W` členem); Oblast získaná během bootstrapu dorazí později oznámením udělení z feedu. Konzistenci zajišťuje stabilní keyset plus přehrání feedu od `W` (klient aplikuje podle revize).
- **Bootstrap Oblasti.** Oznámení `access_granted` nese šifrovaný `areaCursor` (stejné AEAD, fáze `a`). Jeho použití stránkuje aktuální stav právě této Oblasti stejnými DTO a skončí `{"phase":"area_bootstrap","items":[...],"done":true,"cursor":null,"restoreGeneration":"<uuid>"}`; hlavní feed cursor klienta se nemění. Oblast, kterou aktér mezitím ztratil, vrátí prázdné `done` bez dat (ztrátu oznámí hlavní feed).
- **Feed (`phase:"f"`).** Až 100 záznamů se `seq > p` seřazených podle `seq`. Záznam v Oblasti A se `seq = s` je viditelný, právě když: A je soukromá Oblast aktéra, nebo aktér byl v `s` členem A (poslední členský řádek `(A, aktér)` se `seq < s` je `member_add`/`member_role`), nebo jde o členský řádek o samotném aktérovi. Členské řádky o jiných uživatelích se nevydávají nikdy. Dotaz je řízený částečným indexem `change_log_content_by_area(area_id, seq) WHERE entity_kind <> 'membership'` (od v9; členské řádky jiných uživatelů se neprocházejí) jen nad relevantními Oblastmi (soukromé + aktuální členství + Oblasti s vlastním členským řádkem za pozicí) a pro každý interval členství zvlášť; ostatní Oblasti se nečtou, záznamy z mezer, kdy aktér nebyl členem, se filtrují a pozici nikdy neposouvají. Vlastní členské řádky se od schématu v9 (R2c.2b) hledají indexem `change_log_by_member(entity_kind, member_user_id, seq)`. Další `p` je sekvence posledního posuzovaného viditelného záznamu (vydaného nebo viditelného, ale už nečitelného `upsert`), jinak beze změny, takže skrytá aktivita nemění ani dešifrovanou pozici, ani obsah odpovědi. `more` = stránka byla plná (nebo vyčerpán rozpočet 20 dávek kandidátů). Tvary záznamů: `upsert` (`type, kind, id, revision, areaId, areaKind, title, ...`, u úkolu `projectId`, `effectiveAreaId`, ve sdílené Oblasti `assignedToMe`; u projektu bez `projectId`) pouze pokud aktér položku **právě teď** smí číst (jinak se přeskočí a vysvětlí ji pozdější `left_scope`/`tombstone`/`access_lost`); `left_scope` (`kind, id, areaId` původní Oblasti, nikdy cílová); `tombstone` (`kind, id, areaId, revision`); vlastní `member_add` → `access_granted` (`areaId, role, areaCursor`), `member_role` → `role_changed` (`areaId, role`), `member_remove` → `access_lost` (`areaId`). Odebrání a opětovné přidání mezi dotazy tedy vydá `access_lost` a pak `access_granted` a nic z mezery.
- **Linearizace.** Podproces vrací spolu se stránkou záznam přispívajících Oblastí (jen Oblasti vydaných `upsert` položek, s rolí a `policy_revision` ze snapshotu). Těsně před uvolněním těla trasa na živém store v jedné transakci nejdřív ověří session (401), potom pro každou takovou Oblast stejný přístup a `policy_revision` (`verifyTargetStagingReadLive`); při změně 409 `read_stale_reload` bez dat. Obsahově prázdná oznámení (`left_scope`, `tombstone`, členská oznámení) Oblast do záznamu nepřidávají, protože na stávající přístup nespoléhají.
- **Idempotentní oznámení a limity stránky (R2c.2a).** Každá stránka (bootstrap, bootstrap Oblasti i feed) má nejvýše 100 položek; oznámení `access_lost` ztracených Oblastí jsou součástí téhož keysetu (pseudo-klíč `(areaId, "lost", areaId)`), počítají se do limitu a lze je obnovit z cursoru. Oznámení (`access_lost` i ostatní) jsou idempotentní a mohou se opakovat mezi bootstrapem a přehráním feedu (člen odebraný po `W` dostane `access_lost` z bootstrapu i z přehrání `member_remove`); klient je musí zpracovat idempotentně, potlačení duplicit server nedělá. Feed při více než `MAX_SCOPED_READ_AREAS` relevantních Oblastech vrací 409 `resync_required` (klient provede nový bootstrap). `ownMembershipRows` je od R2c.2b (schéma v9) seek přes `change_log_by_member`, ne průchod všemi členskými řádky.
- **Oblast získaná během bootstrapu** může být kromě oznámení udělení z feedu obsloužena i zbývajícími stránkami bootstrapu (čitelné Oblasti se počítají znovu na každé stránce); je to idempotentní.

**Odlišené kódy 401, schéma v9 a komprese změnového záznamu (R2c.2b, pouze izolovaný staging, bez UI; mechanismus je návrh předložený ke schválení vlastníkem v tomto PR):**

- **Kódy 401 na všech endpointech `/api/target-staging/**`.** Ověření živé session (admission) proběhne na každé cílové route před kontrolou cesty, dotazu a těla, takže mrtvá session dostane kódovanou 401 i při neplatném vstupu; živá session s neplatným vstupem dostane 400. Tělo je `{"error":"Authentication required","code":"session_expired"}`, když předložený token ukazuje na existující, neodvolaný řádek se shodnou epochou identity, který jen vypršel; jinak `{"error":"Authentication required","code":"session_revoked"}`: odvolaný řádek, epocha nižší než aktuální epocha identity (`revokeAllForUser`), neznámý token (včetně řádku smazaného po 90 dnech) a malformovaná session cookie. Odvolání má přednost před vypršením. Bez session cookie, nebo při selhání owner cookie, zůstává dosavadní tělo bez `code` (zpětná kompatibilita). Kód se odvozuje jen z předloženého tokenu, takže ho zná jen jeho držitel. Klasifikuje čistá funkce `classifyTargetStagingSessionDenial` vedle `lookupLiveTargetStagingSession`, volaná ve stejném pinned snapshotu jako ověření (admission, kontrola těsně před uvolněním po čtecím podprocesu, linearizační body zápisů); pořadí 401 před 409/404 zůstává. Zápis, jehož session vyprší či je odvolána uvnitř transakce, vrátí tentýž kód (klasifikuje živý store, ne podproces). **Kód obnovy (`restore`) v tomto PR není:** vyžaduje autentizovat, že token předchází aktuální `restoreGeneration`, což patří do postupu obnovy R2c.4; do té doby takový token dostane `session_revoked`/`session_expired` podle výše.
- **Schéma v9** (`TARGET_STORE_SCHEMA_VERSION = 9`; v8 se nemigruje, preflight ho odmítne a je nutný nový bootstrap). `change_log.committed_at_ms` (`NOT NULL DEFAULT` čas vložení v ms s přesností na sekundu, `CHECK > 0`; hodnotu doplňuje výchozí hodnota sloupce, ne trigger), index plného klíče `change_log_by_key(entity_kind, entity_id, member_user_id, seq)` nahrazuje `change_log_by_entity`, index `change_log_by_member(entity_kind, member_user_id, seq)` (vlastní členství aktéra je seek; testováno přes `EXPLAIN QUERY PLAN`) a klíč `metadata.change_log_floor` (desítkové celé číslo, bootstrap `0`).
- **Hranice komprese (floor) a řízené mazání.** Floor smí jen růst a nikdy nepřekročí `COALESCE(MAX(seq),0)`; klíč nelze smazat, přejmenovat ani nahradit (`INSERT OR REPLACE`), jen `UPDATE` jeho hodnoty. Trigger `change_log_no_delete` je nahrazen řízeným mazáním: řádek lze smazat, jen když `OLD.seq <= floor` a existuje pozdější řádek téhož klíče s `seq <= floor` (klíč: `(entity_kind, entity_id)` pro úkol/projekt, `(Oblast, uživatel)` pro členství). Pro každý klíč tedy vždy zůstane poslední řádek na hranici nebo pod ní a všechny řádky nad ní; tombstone je posledním řádkem svého klíče, takže se nikdy nesmaže a `change_seq` odkazy tombstonů zůstávají platné. `UPDATE` a `INSERT OR REPLACE` řádků zůstávají zakázané. Preflight navíc ověřuje platnost floor (celé číslo, `<= MAX(seq)`), nepřítomnost nahrazeného řádku pod floor (počet řádků `seq <= floor` = počet různých klíčů; jednoprůchodový SQL) a upravenou kontrolu pořadí členských řádků; rekonciliace s živým stavem používá poslední řádek klíče, a komprese ho proto nemění.
- **Příkaz komprese (jen pro operátora, žádný HTTP endpoint).** `compactTargetStagingChangeLog(store, { retentionDays, now })` (`lib/target-staging-change-log-compaction.ts`) v jedné transakci `BEGIN IMMEDIATE` nad pinned fd: nový floor = (nejmenší `seq` s `committed_at_ms >= now - retentionDays·86 400 000`) − 1, jinak `MAX(seq)` (nikdy méně než dosavadní; řádky v retenci se tak nezkomprimují ani při skoku hodin), pak smaže nahrazené řádky pod floor po dávkách (dotaz i trigger hledají nahrazující řádek přes celý klíč v indexu `change_log_by_key(entity_kind, entity_id, member_user_id, seq)`, protože členské řádky mají jako `entity_id` Oblast; práce je lineární pro úkoly, projekty i členství), vrací `{floor, deleted}`. Minimální retence je 7 dní (menší se odmítne); **navržená výchozí retence je 30 dní** (rozhodne vlastník). CLI: `scripts/target-staging-compact-change-log.mjs --directory <abs> --generation <uuid> [--retention-days N]` (stejné bezpečnostní kontroly jako `target-staging-session.mjs`, výstup JSON).
- **Cursory za hranicí.** Každý cursor, jehož pozice leží pod floor, vrátí 409 `{"code":"resync_required"}` a žádná data: feed s `p < floor`, bootstrap s watermarkem `w < floor` i cursor bootstrapu Oblasti s `w < floor` (grantová sekvence). Členská historie pod floor už nemusí existovat (bootstrap z ní určuje ztracené Oblasti k `w`), proto by jinak vznikla částečná data bez `access_lost`. Klient provede nový bootstrap a zachová frontu; čerstvý bootstrap předá `p = W >= floor`. Viditelnost podle intervalů členství zůstává správná pro každé `P >= floor`, protože poslední členský řádek `(Oblast, uživatel)` na hranici nebo pod ní zůstává a určuje stav členství ve floor.
- **Důsledek pro retenci (návrh).** `p` postupuje jen přes viditelné záznamy, takže aktér bez viditelné změny novější než floor dostane po každé kompresi `resync_required` a znovu udělá bootstrap; při retenci 30 dní je to očekávané.
- **`committed_at_ms`** je `DEFAULT` sloupce, ne hodnota nastavená triggerem; surový `INSERT` by mohl dodat vlastní hodnotu, což leží mimo model důvěry (zápisy jdou jen přes triggery a pinned writery).
- **Provozní postup po zabitém procesu komprese.** SIGKILL během komprese může nechat horký `-journal`; SQLite data při příštím otevření vrátí, ale pinned writer každý zápis odmítne a CLI hlásí `journal_present`. Postup: zastavit všechny writery a staging server; ověřit stav jen ke čtení (`inspectIsolatedTargetStore`) na kopii; nechat SQLite provést rollback jedním otevřením DB běžným nástrojem (journal tím zmizí), případně journal přesunout stranou až po ověření kopie; znovu spustit kompresi, nebo vytvořit nový staging store novým bootstrapem.

**Zápisový kontrakt cílových endpointů (R2c.3, pouze izolovaný staging, bez UI; název hlavičky a kódy níže jsou mechanismus navržený ke schválení vlastníkem v tomto PR):**

- **Dotčené endpointy.** Všechny zápisové: `PATCH /api/target-staging/tasks/{taskId}/title`, `POST .../title/status`, `POST .../delete`, `POST .../delete/status` a `POST /api/target-staging/areas/{areaId}/members`. Čtení (včetně `GET .../title`, tedy náhledu CAS tokenu) a legacy `/api/store` se nemění a hlavičku nevyžadují.
- **Hlavička protokolu.** Požadavek musí nést právě jednu hlavičku `x-lumi-target-protocol: 1`. Chybějící, opakovaná (spojená hodnota `1, 1`) nebo jakákoli jiná hodnota je HTTP 400 `{"error":"Invalid request","code":"protocol_unsupported"}`. Kontrola běží po admission (kódovaná 401 mrtvé session zůstává první) a po neplatné cestě či dotazu (400), ale před limiterem a před čtením těla, takže požadavek bez verze neutrácí rozpočet limiteru ani se nečte.
- **Zdroj `restoreGeneration` pro klienta.** Každá úspěšná odpověď `GET /api/target-staging/changes` (`bootstrap`, `area_bootstrap` i `feed`) nese pole `restoreGeneration`, tj. aktuální `restore_generation` store (UUID). Je to údaj na úrovni store, ne data úkolu; klient ho použije v zápisech a při změně dostane `resync_required` (zápis 409, cursor 409 podle R2c.2a). Doplňuje ho route z ověřené konfigurace store (preflight vynucuje shodu s metadaty).
- **Tvar těla.** Ihned po parsování JSON: objekt obsahující kterýkoli z klíčů `entities`, `relations`, `baseRevision` je HTTP 400 `{"error":"Invalid request","code":"legacy_snapshot_rejected"}` (před kontrolou množiny klíčů). Jinak se přesná množina klíčů rozšíří o `writeAreaId` (řetězec, stejná pravidla jako `areaId`) a `restoreGeneration` (UUID). Chybějící nebo neplatné pole a neznámý klíč jsou 400 `{"error":"Invalid request"}`.
- **Pořadí kontrol uvnitř transakce** (`BEGIN IMMEDIATE` u zápisů, připnutý snapshot u status endpointů), vždy před mutací, receiptem a CAS: (a) živost session (kódované 401) jako dosud; (b) `restoreGeneration` ≠ `restore_generation` store → HTTP 409 `{"error":"Resync required","code":"resync_required"}` (úroveň store, o úkolech nic neprozradí); (c) u příkazů nad úkolem: (1) aktér smí úkol zapisovat (živý úkol; u mazání a jeho ověření i Oblast z tombstonu podle R2c.1), jinak nerozlišitelné 404; (2) aktér má zápisové právo v `writeAreaId` (soukromý vlastník nebo editor/admin sdílené Oblasti), jinak **totéž** 404 bez ohledu na to, zda Oblast existuje; (3) `writeAreaId` je efektivní Oblast úkolu (u smazaného úkolu Oblast tombstonu), jinak HTTP 409 `{"error":"Revision conflict","code":"write_area_mismatch"}`. Teprve poté přehrání či konflikt receiptu, CAS a mutace. Kód `write_area_mismatch` tak dostane jen aktér, který smí zapisovat úkol i pojmenovanou Oblast, a nic nového se nedozví.
- **Příkaz členství.** `writeAreaId` musí být rovno Oblasti v cestě; jinak 400 `{"error":"Invalid request"}` rozhodnutý v route ještě před ověřením admin práva (nečlen i neexistující Oblast tedy dostanou totéž 400, ne 404). Dále platí kontrola (b) před ověřením admin práva a beze změny zbytek R2-ID.2a.
- **Receipty.** Digest titulního i mazacího příkazu se oproti dosavadnímu stavu nemění a `writeAreaId` do něj nepatří (mazání zůstává `task-delete-v1`). Kontrola Oblasti (c)(3) vynutí `writeAreaId` = aktuální Oblast úkolu (u smazaného ID Oblast tombstonu), takže se jiný `writeAreaId` shodný s receiptem může objevit jen po přesunu úkolu. Po přesunu proto stav příkazu s **aktuální** Oblastí úkolu vrátí normální výsledek (`committed`/`not_recorded`), zatímco **stará** Oblast je 409 `write_area_mismatch`. Dřívější receipty se přehrávají normálně.
- **Tombstone a oracle existence.** U smazaného ID se nejdřív hledá receipt smazání **vlastní** aktérovi (aktér, `taskId`, `commandId`); bez něj je odpověď nerozlišitelné 404 bez ohledu na `writeAreaId` (editor Oblasti, který nemazal, nepozná smazané ID od neexistujícího). Kontrola shody Oblasti (`write_area_mismatch`) a digestu se použije až u aktéra s vlastním receiptem. U živých úkolů zůstává pořadí (c)(1)–(3).
- **Důsledky pro klienta (R2c.5).** (1) Po přesunu úkolu mezi Oblastmi vrací titulní i mazací status a opakování se starou Oblastí 409 `write_area_mismatch`; s aktuální Oblastí úkolu dostanou normální výsledek (`committed`/`not_recorded`, přehrání). R2c.5 proto ověřuje stav s aktuální Oblastí z feedu a `write_area_mismatch` bere jako konflikt (ponechat lokální koncept, nabídnout nové načtení), nikdy jako `not_recorded`. (2) Titulek potvrzený před pozdějším smazáním úkolu vrací u titulního statusu i opakování 404 (tombstone cesta existuje jen u mazání); R2c.5 to ohlásí jako neodeslatelné, úkol je pryč a nic se neztratí. (3) Existující testy se změnily jen přidáním hlavičky a polí; v `shared-title` po přesunu úkolu stará Oblast dává 409 `write_area_mismatch` a aktuální `committed`.
- **Pořadí vrstev na route:** zapnutý příznak (404) → **brána kotvy (503, R2c.4a)** → identita a admission (kódované 401) → cesta a dotaz (400) → **hlavička protokolu (400)** → limiter (429) → čtení těla → **legacy tvar (400)** → množina klíčů a pole (400) → živost session a konfigurace → podproces s kontrolami (b)(c). Hranice mezi stavem session a stavem store se nemění.

**Nevratný žurnál a detekce rollbacku (R2c.4a, pouze izolovaný staging, bez UI; mechanismus je návrh ke schválení vlastníkem v tomto PR; restore postup R2c.4b zde NENÍ):**

Rozdělení R2c.4: **R2c.4a** (tento krok) dodává nevratný žurnál a fail-closed detekci rollbacku, tedy požadavky (b), (c) a (f). **R2c.4b** dodá postup obnovy: přehrání žurnálu po záloze, novou `restoreGeneration`, `revokeAll`, invariant posledního admina a kód 401 `restore` (požadavky (a), (d), (e)). Záznamy žurnálu už teď nesou vše, co 4b potřebuje: každý záměr má údaje bez obsahu uživatele, z nichž lze změnu přehrát (viz Obsah záznamů), a `restore_generation`, pod kterou vznikl.

- **Soubor.** `lumi-target.journal` v staging adresáři vedle `lumi-target.sqlite`. Vytvoří ho bootstrap (`O_EXCL|O_NOFOLLOW`, mode `0600`, fsync) a hned do něj zapíše záznam `genesis`. Otevírá se vždy přes připnutý deskriptor adresáře s `O_NOFOLLOW|O_NONBLOCK` (po `lstat`; FIFO nebo zařízení na místě žurnálu se odmítne, aniž by zablokovalo event loop před-autentizační brány) (čtení `O_RDONLY`, zápis `O_RDWR|O_APPEND`), nikdy přes symlink; musí to být běžný soubor, `nlink = 1`, vlastník je uid procesu, mode přesně `0600`, velikost nejvýše 64 MiB (staging mez). Cokoli jiného je `journal_invalid`.
- **Atomický svědek commitu.** Soubor `lumi-target-witness.sqlite` leží ve stejném staging adresáři a na stejném souborovém systému jako hlavní SQLite DB; bootstrap jej vytvoří s právy `0600` a počátečním záznamem `(n=0, genesis_hash, restore_generation)`. Každý další úspěšný zápis uloží neměnný záznam `(n, hash intentu, restore_generation)` pomocí SQLite `ATTACH DATABASE` v **téže transakci** jako aktualizaci hlavní databáze. Oba DB soubory používají rollback-journal režim DELETE (nikoli WAL) a `synchronous=FULL`: SQLite super-journal zaručuje atomický commit více databází na jednom filesystemu. Čtenář pod zdrojovým SQLite SHARED zámkem ověřuje žurnál i aktuální nejvyšší hodnotu svědka `W`; platí `A < W → restore_pending`, `A > W → journal_invalid`. Chybějící/neplatný svědek znamená `journal_invalid`. Proto obnova **jen** souboru `lumi-target.sqlite` po COMMIT bez JSONL `confirm` neobnoví revokaci: svědek už nese potvrzené `n`. **Při obnově nikdy nevracet ani nekopírovat zpět žurnál či svědka.** Obnova obou SQLite souborů současně, celého adresáře nebo hostitelského snapshotu zůstává mimo dosažitelnou detekci a vyžaduje externí kotvu pro produkci.
- **Kontrola integrity svědka.** Ověřený žurnál určuje pro každý záměr přesný hash i výsledek `confirm`/`abort`. Při prvním otevření procesu se mimo zámek hlavní DB porovnají všechny řádky SQLite svědka s hashi skutečně potvrzených záměrů; chybějící, přebývající či poškozený záznam končí `journal_invalid`. Záměry `abort` nemají řádek v SQLite svědkovi (mezery v číslování jsou legitimní). Při živé kontrole se ověřuje poslední ověřená hranice, počet řádků a nově připsaný suffix; změna souboru bez posunu potvrzeného konce vynutí plnou kontrolu. Stejně jako cache žurnálu to není obrana proti hostilnímu operátorovi, který během běhu procesu přepíše starší řádek a zároveň přidá nové záznamy. Regresní testy pokrývají změnu prostředního hashe, odstranění potvrzeného řádku i záměr `abort`. Zapisovač nastaví `busy_timeout` ještě před prvním SQL dotazem a připojením svědka.
- **Formát.** Append-only JSON řádky v kanonické podobě (klíče řazené, bez mezer; řádek, který po parsování nedá přesně stejný text, je neplatný): `{"g":<restore_generation>,"h":<hex>,"k":<druh|null>,"n":<int>,"p":<payload|null>,"prev":<hex>,"t":"genesis"|"intent"|"confirm"|"abort"}`. Hash řetězec: `h = sha256(prev + kanonický JSON řádku bez h)`; `genesis` má `n = 0` a `prev` = 64 nul. Číslo `n` je číslo záměru: `intent` má `n` předchozího záměru + 1, `confirm`/`abort` nesou `n` záměru, který uzavírají. Před dalším `intent` musí být předchozí záměr uzavřen. `abort` smí uzavřít jen neuzavřený záměr, `confirm` nikdy ne zrušený (opakované nebo pozdní `confirm` je pravdivé a přípustné). Číslo zrušeného záměru se nepoužije znovu. Všechny záznamy nesou `restore_generation` store (UUID); v 4a se musí shodovat s metadaty i s konfigurací, změnu generace definuje 4b.
- **Obsah záznamů** (bez obsahu uživatele, žádné názvy úkolů, tokeny ani cookies): členství `{area, user, op, role}` (`op` = `add`/`set_role`/`remove`/`noop`; `role` po změně, `null` při odebrání); vydání/odvolání session `{userId, tokenHash, epoch}` (hash tokenu je v DB tak jako tak; `epoch` = epocha session); `revokeAll` `{userId, epochAfter}`; zápisy obsahu (název, smazání) jen `{seq:[od,do]}` = rozsah `change_log` zapsaný tímto commitem; komprese `{floor}`. Druh `k`: `title`, `delete`, `membership`, `session_issue`, `session_revoke`, `session_revoke_all`, `compaction`.
- **Schéma v10.** Metadata klíč `anchor_seq` (kanonický desítkový řetězec, bootstrap `"0"`), který je číslem posledního záměru commitnutého s DB. Triggery stejného druhu jako u `change_log_floor`: hodnota se smí jen zvýšit, musí zůstat kanonickým desítkovým řetězcem (nejvýše 15 číslic, bez nul na začátku, typ text) a nesmí se smazat, přejmenovat, ani nahradit (`UPDATE OR REPLACE`, přejmenování jiného klíče na `anchor_seq`, `INSERT [OR REPLACE]`). Preflight ověřuje přítomnost a tvar; počet řádků metadat je nyní 6 + receipty. Starší staging stores se nemigrují (jako dosud).
- **Dvoufázový zápis** (jediné místo: `withPinnedTargetStagingWrite`, tedy zápis názvu, smazání, příkaz členství, vydání/odvolání/`revokeAll` durable session i komprese; operátorské CLI jdou stejnou cestou, žádný jiný zapisovač neexistuje). Po `BEGIN IMMEDIATE` a kanonickém preflightu, pod týmž zámkem: (i) přečte a ověří žurnál a kotvu; je-li poslední záznam neuzavřený `intent n`: `anchor_seq == n` → doplní `confirm n` (pád po COMMIT), `anchor_seq == poslední potvrzené` → doplní `abort n` (pád před COMMIT), jinak fail closed. (ii) Tělo zápisu proběhne. (iii) `context.commit(záznam)`: těsně před COMMIT připojí a `fsync`ne `intent n = poslední záměr + 1` s obsahem, v téže transakci nastaví `anchor_seq = n` a vloží záznam `n` do připojeného atomického SQLite svědka, COMMIT obou souborů a potom v nové krátké `BEGIN IMMEDIATE` (čerstvé čtení konce, protože řetězec je lineární a jiný proces mohl záměr už uzavřít) připojí `confirm n`. Selhání připojení `intent` transakci vrátí zpět (nic se necommitne). Selhání `confirm` po COMMIT nechá koncový `intent`, který uzavře příští zapisovatel podle (i). Zápis, který nic necommituje (replay, odmítnutí), nic nezapíše do žurnálu.
- **Detekce při každém požadavku.** Kotva `A` (DB) a žurnál se čtou **pod týmž zámkem SQLite** (SHARED snapshot u čtení, `BEGIN IMMEDIATE` u zápisu), takže mezi nimi nemůže proběhnout commit a není nutná žádná tolerance mimo uvedenou. `H` = nejvyšší potvrzené `n` (`genesis` je potvrzený 0), `L` = nejvyšší záměr, `W` = nejvyšší atomicky potvrzené číslo u svědka. Nejdřív se požaduje `A == W` (`A < W` je `restore_pending`, `A > W` je `journal_invalid`). Poté pravidla žurnálu: `A < H` → `restore_pending`; `A == H` → ok; `A` rovno koncovému neuzavřenému záměru `n` (commitnuto, `confirm` ještě není) → ok; koncový neuzavřený záměr nad `A` (zápis probíhá na jiném procesu nebo pád před COMMIT) → ok, příští zapisovatel ho uzavře (požadavek (c): souběžná revokace ani pád store nezablokují); jakákoli jiná `A > H`, zejména `A > L` → `journal_invalid`. Chybějící žurnál, přerušená řada (smazaný nebo upravený řádek, přehozené pořadí), nezpracovatelný nebo nekanonický řádek, neplatný hash, nenavazující `n`, symlink, jiný než běžný soubor, jiný mode, vícenásobný odkaz, shoda `g` s metadaty nesedí → `journal_invalid`. Ověřuje se **celý řetězec**, ale **jen jednou na proces a inode**: proces si drží cache ověřeného prefixu klíčovanou `(dev, ino)` (bajtová délka, hash posledního řádku, kontext řetězce). Další kontrola vyžaduje velikost ≥ délka v cache, znovu načte a ověří poslední řádek v cache (musí dát uložený hash) a ověří jen připojené bajty; při jakékoli neshodě, zmenšení nebo jiném inode se ověří znovu celý řetězec (výsledek zůstává fail-closed). Kompromis: úprava **staršího** řádku na místě za běhu procesu, který ho už ověřil, ten proces nezaznamená; nový proces (restart) vždy jednou ověří celý řetězec. Měřeno testem: plné ověření 5000 zápisů (10 001 záznamů, 2,4 MB) ≈ 80 ms, 20 000 zápisů ≈ 350 ms; kontrola s cache ≈ 0,02 ms (celá brána vč. otevření SQLite ≈ 2 až 3 ms), první kontrola po jednom novém zápisu ≈ 3 ms (5000) a ≈ 7 ms (20 000). **Kde se platí plné ověření:** každé čtení a zápis běží v čerstvém podprocesu s prázdnou cache, takže plné ověření (≈ 80 ms při 5000 a ≈ 350 ms při 20 000 zápisech) platí **každý podproces**, zatímco dlouhý rodičovský proces (brána) ho platí jednou. Proto se v každé cestě (zapisovatel, čtecí podproces, živá kontrola) žurnál **nejdřív ověří a nahřeje cache před zámkem SQLite** (před `BEGIN IMMEDIATE`, před SHARED zámkem čtení i před `BEGIN` živé kontroly); kontrola uvnitř zámku pak jen znovu ověří hraniční řádek a připojené bajty se stejnými pravidly verdiktu. Dva studené zapisovače se 200 ms časovým limitem zámku tak uspějí i při 20 000 zápisech (test). Náklad na požadavek je tedy: brána ≈ 2 až 3 ms (cache), čtecí/zapisovací podproces = jedno plné ověření mimo zámek + inkrementální kontrola v zámku. Předehřátí mimo zámek je u zapisovače pokryté testem (dva studení zapisovači nad 20 tis. zápisy); u čtecího podprocesu a živé kontroly jde o optimalizaci dostupnosti, kterou žádný test nevynucuje (bez ní by studený proces držel SHARED zámek po dobu plného ověření). Žurnál roste bez omezení (strop 64 MiB ≈ 250 000 zápisů, pak `journal_invalid`; rotace patří do 4b/produkce).
- **Kódy a pořadí.** `restore_pending` i `journal_invalid` jsou HTTP 503 `{"error":"Staging unavailable","code":"restore_pending"|"journal_invalid"}` s `cache-control: no-store`, bez dat, na **každém** `/api/target-staging/*` endpointu. Pořadí na route: zapnutý příznak (404) → **brána kotvy (503)** → identita a admission (401) → … → limiter … Brána běží **před** identitou, aby se proti nedůvěryhodnému store nespustila žádná kontrola session; proto neověřený požadavek dostane 503 a ne 401. Brána má vlastní limiter (1200 / 10 minut na klienta, 429). Store, který nelze vůbec přečíst (nenastavená konfigurace, uzamčený, jiné schéma), brána nepřepíše: nechá stávající fail-closed cestu (503/401). Totéž ověření běží znovu v dětském čtecím procesu (`withPreflightedStore`, nad snapshotem, který vznikl pod SHARED zámkem) a v živých kontrolách session/Oblasti těsně před uvolněním odpovědi (tam je výsledek obecné 503 bez kódu), takže ani obnova uprostřed požadavku data neuvolní. Zápisy nad nedůvěryhodným store vrátí `denied` (koncový fragment se na takovém store neusekává: verdikt se vyhodnotí z úplných řádků dřív než jakákoli změna souboru, a to jak před zápisem, tak při doplnění `confirm` po COMMIT pod novým zámkem; obě cesty používají jednu společnou funkci s týmž verdiktem včetně atomického svědka, tedy `A == W` a `A` i žurnál musí vyjít `ok`, takže store obnovený na místě po COMMIT se nedoplní o `confirm` ani neoseká; před jakoukoli změnou žurnálu obě cesty navíc znovu ověří, že kanonická cesta hlavní DB i svědka stále míří na připnuté, resp. připojené inody (bez symlinku, nlink 1, bez sidecarů), takže atomická výměna souboru přes `rename` starší zálohou po COMMIT nebo po ATTACH `confirm` nedoplní; stejná kontrola platí i pro inode žurnálu, který zapisovač po otevření připne, takže starší kopie žurnálu přejmenovaná přes kanonickou cestu nepošle záměr ani `confirm` do osiřelého inode; kontrola běží i před přidáním záměru a těsně před COMMIT, selhání vrátí transakci zpět a zápis se nehlásí jako úspěšný. Přijaté zbytkové okno: `rename` po poslední kontrole ještě může nechat dopsat jeden řádek `confirm`, což je neškodné, protože další čtenář selže uzavřeně; při nepřátelské výměně hlavní DB, svědka nebo žurnálu po COMMIT může volající stále dostat `ok` pro zápis, který už v kanonickém store není, a store poté selže uzavřeně (všichni zapisovatelé odmítnuti) až do zásahu operátora, takže za tohoto modelu útoku potvrzení není trvalé) (`unavailable`/404 jako u ostatních hranic) a nezapíšou ani DB, ani žurnál. Totéž platí pro režim obnovy (`withPinnedTargetStagingRestore`, sdílená transakce): před tělem vyžaduje stejné cesty a stejnou důvěru až na jediný rozdíl, že přijímá `restore_pending` (`A < W`); po vlastním COMMIT musí být store plně důvěryhodný pod **novou** generací (`A == W == n`, verdikt ok, pravidla přechodu generace, cesty hlavní DB, svědka i žurnálu) před doplněním `confirm`; jinak se `confirm` nedoplní a nástroj hlásí `confirm_untrusted` (ne `ok`), operátor nesmí novou generaci nastavit a store selhává uzavřeně.
- **Neukončený koncový fragment.** Čtenář nezamyká žurnál, takže může vidět rozepsaný poslední řádek zapisovatele (nebo zbytek po selhání zápisu, ENOSPC/EIO). Čtenáři proto ignorují **jen** neukončený fragment za posledním `\n` (bere se jako zápis v běhu; verdikt vychází z úplných řádků, z nichž každý musí být kanonický a navazující). Fragment, který se parsuje jako JSON, ale není přesně svým kanonickým textem, nebo je delší než mez řádku, je `journal_invalid`. Zapisovatel pod zámkem zápisu fragment useknutím (`ftruncate` + `fsync`) vrátí na poslední `\n` dřív, než uzavře koncový záměr; je to bezpečné, protože `intent` je plně fsyncnutý před COMMIT, takže fragment je vždy nedokončený `intent` (DB necommitnuta) nebo `confirm` (znovu uzavřen z `A == n`).
- **Pád uprostřed zápisu a provozní postup.** Pád před COMMIT (SIGKILL) může nechat vedle DB soubor `lumi-target.sqlite-journal` s **nulovou hlavičkou** (není horký, DB soubor se nezměnil). Běžné otevření DB ho **nesmaže** a pravidlo o sidecarech (R2c.2b) pak odmítne všechny zápisy i čtení v podprocesu, dokud operátor nezasáhne. Postup: zastavit všechny writery a server; zkopírovat DB i `-journal` stranou; ověřit, že prvních 8 bajtů `-journal` je nulových (není horký); teprve potom ho odstranit. **Horký journal (nenulová magie) se nikdy nemaže ručně**: SQLite ho vrátí při běžném otevření DB pro čtení i zápis. Po odstranění je koncový `intent` uzavřen příštím zapisovatelem jako `abort` (potom `intent`/`confirm` jeho vlastního zápisu) a store se nepovažuje za obnovený (test to reprodukuje). Dřívější tvrzení, že journal po běžném otevření zmizí, platí jen pro horký journal.
- **Zdokumentovaná omezení.** (1) **Obnova celého staging adresáře nebo snapshotu hostitele vrátí i žurnál a svědka a nelze ji odhalit**; postup obnovy (4b) ji zakáže a vyžaduje obnovu jen hlavního DB souboru s následným operátorským nástrojem, nikdy svědka. (2) Ztracený `confirm` po COMMIT je rozlišitelný díky SQLite svědkovi, pokud se vrací **jen hlavní DB**; atomický svědek má již vyšší `n` (regresní test pro odvolání session). Neodhalitelné zůstává současné vrácení DB **i** svědka a žurnálu, případně dvojice DB+svědek při nezapsaném confirmu; operátorské obnovení svědka je zakázáno. (3) Útočník s oprávněním zapisovat do adresáře může žurnál přepsat (řetězec není podepsaný, jde o ochranu proti omylu a obnově ze zálohy, ne proti hostilnímu operátorovi); nevratnost vůči hostitelskému snapshotu patří mimo staging (externí high-water mark). (4) Chybějící žurnál nelze automaticky znovu vytvořit: bylo by to přesně to, co obnova chce zakrýt. (5) Známé omezení stagingu: brána před autentizací odhalí i nepřihlášenému volajícímu, zda je store `restore_pending` nebo `journal_invalid` (obsah-prostý stav, ale rozlišení je viditelné); a její limiter (1200 / 10 minut) je počítán na klienta podle stávajícího klíče `enforceRateLimit`, takže když se vyčerpá bucket sdílený klienty za stejným klíčem (např. za reverzní proxy bez rozlišení klienta), může zablokovat i vlastníka (429). (6) Test-only mezera: porovnání dev/ino mezi `lstat` a `open` žurnálu (záměna mezi voláními) nelze deterministicky vyvolat bez háčku v produkčním kódu, proto nemá test; kryjí ji kontroly symlinku, FIFO, mode, vlastníka a počtu odkazů. Serializér záznamů navíc vynucuje stejná pravidla jako ověřovač, takže záznam, který by ověřovač odmítl, nelze připojit (transakce se vrátí zpět). (7) Když store nelze přečíst vůbec (nenastavená konfigurace, uzamčený, jiné schéma, zámek), brána vrací `null` a **každá** route i tak selže uzavřeně vlastní cestou (child preflight nebo živá kontrola: 503/401, žádná data); brána tedy žádnou ochranu neslabí, jen v tom případě nedodá kód.

**Postup obnovy ze zálohy s anti-rollback ochranou (R2c.4b, pouze izolovaný staging, bez UI; mechanismus je návrh ke schválení vlastníkem v tomto PR, nelze jej považovat za schválený, dokud vlastník nerozhodne):**

R2c.4b doplňuje k 4a (žurnál, svědek, brána `restore_pending`) operátorský nástroj, který z obnovené zálohy udělá důvěryhodný store: dodává požadavky (a), (d) a (e) z řádku R2c.4 v [ROADMAP.md](ROADMAP.md) a kód 401 obnovy z řádku R2c.2. Kód se jmenuje **`session_restored`** (v ROADMAPu dosud pracovně „kód obnovy“).

- **Postup operátora (závazný).** (1) Zastavit server a všechny zapisovače. (2) Nahradit **jen** soubor `lumi-target.sqlite` konzistentní zálohou (`sqlite3 .backup` nebo `VACUUM INTO`) pořízenou ve **stejné verzi schématu** (v11; starší záloha se nemigruje a nástroj ji odmítne důvodem `unsupported_backup`). Do té doby brána vrací 503 `restore_pending` na každém endpointu (prostá kopie bez nástroje tedy zůstane blokovaná i tehdy, když po záloze neproběhla žádná revokace). Zbylý `lumi-target.sqlite-journal` se odstraní jen podle pravidel 4a (nulová magie). (3) `node --experimental-loader ./scripts/target-staging-ts-loader.mjs scripts/target-staging-restore.mjs --directory <abs> --generation <aktuální restoreGeneration z konfigurace> [--grant-admin <areaId>:<userId>]...` vytiskne JSON s **novou** `restoreGeneration` a počty (nikdy tokeny ani obsah); exit 0 při úspěchu, 1 při odmítnutí (kromě `confirm_untrusted`; store zůstává `restore_pending`, jeho obsah se nezměnil; v žurnálu však může zůstat nebo se zapsat uzavření konce: useknutí zlomku řádku a `confirm`/`abort` koncového neuzavřeného záměru, o němž rozhoduje svědek, což provede každý zapisovač jako první krok; po selhání těsně před COMMIT nebo při něm může navíc zůstat neuzavřený restore záměr, který další běh nástroje nebo zapisovač uzavře podle svědka (`abort`), viz „Chyby uprostřed obnovy“). Rozlišené důvody odmítnutí: `invalid_request` (špatné argumenty, i `--generation`, které není UUID, více než 16 grantů nebo příliš dlouhý seznam), `generation_mismatch` (korektní UUID, které není generací tohoto store; hlásí se jen tehdy, když se žurnál sám ověří, `restore_generation` zálohy je generace, kterou tento žurnál použil, a konfigurace není ani platná, ani generace koncového neuzavřeného restore; nic dalšího se nesdělí, jinak `unavailable`), `unavailable` (store není v obnovitelném stavu `restore_pending`: zdravý, už obnovený, `journal_invalid` nebo nečitelný), `unsupported_backup`, `backup_provenance`, `backup_predates_restore`, `last_admin`, `grant_invalid`, `grant_unneeded`, `grant_removed_by_journal`, `capacity_exhausted`, `replay_failed`, `confirm_untrusted` (**exit 2**: restore se commitnul, svědek ho má a JSON nese `restoreGeneration` i `previousGeneration`, ale `confirm` nešlo bezpečně doplnit: cesta byla během běhu nahrazena či změněna, nebo selhal zápis. Server nespouštět, dokud se adresář staging nezkontroluje (jen očekávané soubory, nic nenahrazeno); poté lze novou generaci nastavit a spustit: brána ověřuje store při každém požadavku, je-li důvěryhodný, první zapisovatel doplní `confirm`, jinak zůstane vše 503 a obnova vyžaduje kopii DB pořízenou PO tomto restore, protože záloha před ním je odmítnuta jako `backup_predates_restore`. Opakované spuštění nástroje po `confirm_untrusted` nic neuzavírá: store už není `restore_pending`, nástroj skončí s exit 1 a důvodem `unavailable` a koncový záměr nechá; `confirm` doplní první důvěryhodný zapisovatel pod novou generací; to je očekávané), `write_failed`. (4) Nastavit `AI_EXECUTIVE_TARGET_STAGING_RESTORE_GENERATION` na vytištěnou hodnotu a spustit server; dokud konfigurovaná generace nesedí, store je fail-closed (503 bez kódu). Když nástroj spadl po COMMIT a výstup se ztratil, nová hodnota je v DB (`SELECT value FROM metadata WHERE key='restore_generation'`); příští zapisovatel doplní chybějící `confirm`.
- **Zakázané obnovy.** (i) **Žurnál `lumi-target.journal`, svědka `lumi-target-witness.sqlite`, celý staging adresář ani snapshot hostitele nikdy nevracet:** vrátí i nevratný zdroj, takže ztráty nelze odhalit (omezení 4a (1)). (ii) Záloha starší než předchozí restore (její okno přehrání překračuje změnu generace): důvod `backup_predates_restore`; nástroj ověřuje, že mezi `anchor_seq` zálohy a nejvyšším potvrzeným záměrem neleží záznam `restore`, a že `restore_generation` zálohy je generace, kterou měl žurnál platnou u záměru `A` (jinak `backup_provenance`, např. záloha jiného store). Provozně: po restore je třeba pořizovat nové zálohy; starší zálohy se nepoužijí (omezení stagingu). (iii) Store, který není ve stavu `restore_pending` (zdravý, `journal_invalid`, chybějící nebo poškozený žurnál či svědek, nečitelná DB), nástroj odmítne (`unavailable`) a jeho stav nezmění. (iv) Záloha jiné verze schématu.
- **Co nástroj udělá (jedna transakce, vše nebo nic).** `withPinnedTargetStagingRestore` (`lib/target-staging-pinned-write.ts`) sdílí s `withPinnedTargetStagingWrite` připnuté otevření, kanonický preflight, otevření žurnálu a `ATTACH` svědka, ale přijme **právě** stav `restore_pending` (kotva `A` DB je pod nejvyšším atomicky potvrzeným číslem svědka `W`, žurnál i svědek úplně ověřené) a nic jiného; běžný zapisovač dál `restore_pending` odmítá, pravidlo důvěry se neoslabuje. Záloha prochází preflightem proti **vlastní** `restore_generation`, proveniencí proti žurnálu. Pod `BEGIN IMMEDIATE`: koncový neuzavřený záměr se uzavře podle **svědka** (svědek má `n` → `confirm`, jinak `abort`; vlastní kotva zálohy rozhodnout nemůže); pak musí platit `A < H` a `W == H` (`H` = nejvyšší potvrzený záměr).
- **Přehrání (a), (d).** Potvrzené záměry `n ∈ (A, H]` ve vlastním pořadí žurnálu: `membership` {`area`, `user`, `op`, `role`} se použije přesně (`add`, `set_role`, `remove`; `noop` se ignoruje; `add` existujícího člena nastaví roli, aby stav konvergoval). Všechna přehrání včetně **povýšení**, takže „C povýšen po záloze, potom A snížen“ nechá C adminem. Chybějící Oblast (nebo soukromá) či identita, nebo chybějící řádek u `set_role`/`remove`, se přeskočí a započítá do `skipped`; **přeskočení nikdy neuděluje přístup** (přeskočí se jen krok, jehož cíl v obnovené DB neexistuje; krok, který právo odebírá a který selže na invariantu, se nikdy nepřeskočí, viz dále). Před odebráním nebo snížením na viewer se úkoly člena v Oblasti odpřiřadí stejně jako u živého příkazu. Triggery posledního admina zůstávají aktivní: odmítnutá operace nese důvod `last_admin`, přeskočit ji nelze (vrátila by roli, kterou žurnál odebral), přehrání se dokončí jen kvůli výpisu Oblastí a celá obnova se odmítne s `blockedAreas` (store zůstane `restore_pending`, transakce se vrátí zpět a DB se nezmění; žurnál se nezmění, až na případné uzavření koncového záměru podle „Chyby uprostřed obnovy“). Totéž platí pro závěrečnou kontrolu, že žádná sdílená Oblast nezůstala bez admina. **Rozhodnutí operátora:** opakovatelné `--grant-admin <areaId>:<userId>` (nejvýše 16; existující identita s osobním workspace a sdílená Oblast, jinak `grant_invalid`) nastaví/vloží roli admin. **Grant je přípustný jen pro Oblast, kterou by invariant posledního admina bez něj zablokoval:** uvnitř téže transakce se nejprve provede suché přehrání bez grantů (`SAVEPOINT`, sběr `blockedAreas`, `ROLLBACK TO`) a jakýkoli grant pro jinou Oblast odmítne celou obnovu důvodem `grant_unneeded` (nic se nezmění). Grant se pak použije **před** přehráním (aby sňatí předchozího admina z žurnálu neporušilo invariant) a **znovu po něm** (aby ho žurnál nevzal zpět). **Grant nikdy nepřebíjí žurnál:** pokud poslední potvrzený členský záměr pro dvojici (Oblast, uživatel) v `(A, H]` uživatele odebral nebo snížil pod admina, celá obnova se před jakoukoli změnou odmítne důvodem `grant_removed_by_journal` (obnova nikdy nevrátí odebrané členství ani sníženou roli). Pravidlo `grant_removed_by_journal` se týká jen okna přehrání `(A, H]`; členský stav samotné zálohy se bere tak, jak je (uživatel, který v záloze chybí, může být explicitním rozhodnutím operátora povýšen na admina blokované Oblasti). Rozhodnutí se zapíše do záznamu `restore` čitelně jako `grantAdmin` = seřazené dvojice `[areaId, userId]` bez duplicit (jen ID, žádný obsah) a vypíše se i v JSON zprávě CLI; seznam je omezen na 16 dvojic a na 1200 znaků kanonického JSON, aby záznam vešel do řádku žurnálu (2048 B). Záměry `title`, `delete`, `compaction` se ignorují (obsah po záloze se obnovou ztrácí z definice); `session_*` viz dále.
- **Revokace všeho (a).** Pro **každou** identitu je nová epocha = `max(epocha v DB zálohy, nejvyšší epocha, kterou žurnál pro uživatele kdy zaznamenal (vydání, odvolání, revokeAll) přes CELÝ žurnál) + 1` (po jedné, trigger vyžaduje +1) a všechny otevřené řádky session se označí odvolané. Epocha se tedy nevrací a každá session před obnovou je mrtvá. Odvolání v žurnálu (`session_revoke`) se sbírají přes celý žurnál.
- **Kód 401 `session_restored`.** Nová tabulka (schéma **v11**) `restore_superseded_sessions(token_hash, user_id, restore_generation)` je append-only (UPDATE, DELETE i REPLACE zakázané triggery; strop 16 384). Nástroj do ní **před** jakoukoli změnou zapíše každý token, který byl živý v nevratném zdroji: řádek v záloze nebo `session_issue` z `(A, H]`, který **není** odvolaný (řádek DB nebo `session_revoke` v žurnálu) a jehož epocha **není nižší** než nejvyšší epocha identity v DB zálohy a v žurnálu před navýšením. Pořadí klasifikace v `classifyTargetStagingSessionDenial`: token v tabulce → `session_restored`; jinak dosavadní logika (revokace má přednost před vypršením, neznámý token `session_revoked`). Token odvolaný v žurnálu nebo s nižší epochou se do tabulky nikdy nedostane a zůstane `session_revoked`; **náhodný neznámý token `session_restored` nikdy nedostane**, protože do tabulky zapisuje jedině restore. Session vydaná po záloze i po zaznamenaném `revokeAllForUser` (jeho nová epocha) dostane `session_restored`; session před tímto `revokeAll` `session_revoked`. Kód je HTTP 401 `{"error":"Authentication required","code":"session_restored"}` s `cache-control: no-store` na **všech** cílových endpointech všude, kde se mapuje `session_revoked`/`session_expired` (mapovač `stagingIdentityRefusal`/`stagingUnauthorizedRefusal`, uvolnění odpovědi `verifyStagingIdentityBeforeRelease`, čtecí linearizace `verifyStagingReadBeforeRelease`, cesta přes čtecí podproces i zápisy, jejichž kontrola v transakci vrací `session_revoked`, které route překlasifikuje podle živého store). Vypršení nepřebíjí: superseded token má kód obnovy i po vypršení.
- **Nová generace (e).** Nová náhodná UUID `restoreGeneration` se zapíše do `metadata.restore_generation` a (v téže transakci) do nové append-only tabulky `restore_generations(generation, previous_generation, journal_n, restored_at_ms)`. Protože CAS tokeny úprav (`targetTaskTitleEditRevision`), cursory feedu a závazný kontrakt zápisu (`restoreGeneration` v těle příkazu, R2c.3) generaci zahrnují, starý offline příkaz dostane 409 `resync_required` a nezapíše se, starý cursor 409 `resync_required` a starý CAS token neodpovídá. Změnové sekvence, revize a tombstony, které se po obnově mohou znovu objevit pod stejnými čísly, jsou proto bez ABA: starý cursor ani token je nikdy nepřijme. Testy: příkaz titulu, smazání a členství se starou generací; cursor z doby před obnovou i po znovupoužití čísla sekvence; stejná hodnota CAS tokenu u nezměněného řádku úkolu.
- **Žurnál.** Obnova se zapíše stejnou dvoufázovou cestou jako každý zápis: záměr `n = L+1`, druh `restore`, `g` = **nová** generace, `p` = {`from` = `A`, `through` = `H`, `previousGeneration`, `superseded`, `skipped`, `grantAdmin` (pole seřazených dvojic `[areaId, userId]`, i prázdné)} (bez uživatelského obsahu), `anchor_seq = n` (pouze navýšení, trigger to dovoluje), řádek svědka `n` s novou generací, COMMIT, potom `confirm` s novou generací. **Ověřovač** (a stejné pravidlo u svědka) mění generaci **jedině** u záměru `restore`, jehož `p.previousGeneration` je platná generace; generace se nesmí znovu použít, `through` musí být nejvyšší potvrzené číslo, `from` nesmí ležet před předchozím restore a `grantAdmin` musí být (jen u `restore`, tam vždy) seřazené pole nejvýše 16 dvojic platných ID bez duplicit. `confirm`/`abort` takového záměru nesou novou generaci; po `confirm` mají všechny záznamy novou generaci, po `abort` se vracejí k předchozí. Řádky svědka nesou generaci záměru, který zrcadlí. Jakákoli jiná změna generace je `journal_invalid`. Koncový neuzavřený `restore` záměr akceptuje konfiguraci s původní i novou generací (DB metadata rozhodne, kterou) a zapisovač jej uzavře novou generací.
- **Schéma v11.** Dvě tabulky výše (a jejich triggery; preflight porovnává plné DDL). Preflight dále: audit řádky (titul, smazání, členství) musí nést aktuální generaci **nebo některou z `restore_generations.previous_generation`** (jinak by po obnově každý starší audit řádek shodil store; řádek neznámé generace dál `audit_invalid`); historie generací musí tvořit jeden řetěz končící aktuální generací a každý `restore_superseded_sessions` odkazuje na generaci historie (jinak `restore_history_invalid`). Počet řádků metadat se nemění (6 + receipty). Starší stores se nemigrují; nástroj přijme jen zálohu aktuální verze.
- **Chyby uprostřed obnovy.** Výjimka nebo selhání před COMMIT vrací změny zpět (obsah DB se nezmění, store zůstává `restore_pending`). Odmítnutí nebo selhání ale nemusí znamenat, že se žurnál nedotkl: jako každý zapisovač nástroj nejprve uzavře konec žurnálu pod zámkem (useknutí nedopsaného zlomku řádku a `confirm`/`abort` koncového neuzavřeného záměru, o němž rozhoduje svědek) a toto uzavření zůstane i při následném odmítnutí; jde o tentýž krok, který by provedl kterýkoli zapisovač, a stav store se jím nemění; v žurnálu zůstane nedokončený `restore` záměr; běžný zapisovač na dosud `restore_pending` store je odmítnut a záměr nechá, uzavře ho `abort` (rozhoduje svědek) až další spuštění nástroje a obnovu provede znovu s jinou generací. SIGKILL po záměru před COMMIT zanechá stejný nehorký `-journal` jako u zapisovače (pravidla 4a). Pokud COMMIT vyhodí chybu až po svém účinku, nástroj to pozná (ROLLBACK sonda, pak kotva a řádek svědka) a pokračuje pokusem o `confirm`: výsledek je `ok` nebo `confirm_untrusted`, nikdy `write_failed` (to platí tam, kde je k dispozici `DatabaseSync.isTransaction`, tedy Node 22 jako v CI a v tomto repozitáři; na běhovém prostředí, kde není boolean, se COMMIT, který vyhodí chybu, bere jako nepotvrzený a končí `write_failed` / `failed` i tehdy, když se ve skutečnosti provedl: fail-closed). Běh po COMMIT před `confirm` je popsán v kroku (4).
- **Zdokumentovaná omezení.** (1) Obnova celého adresáře nebo snapshotu hostitele a současný návrat DB, svědka i žurnálu nejsou odhalitelné (omezení 4a). (2) Zálohu starší než poslední restore použít nelze; po každém restore je nutná nová záloha. (3) Obsah po záloze se ztrácí (jen zabezpečení se přehrává); `title`/`delete` nelze přehrát a nesmějí se, protože žurnál záměrně obsah nenese. (4) Identita nebo Oblast vytvořená po záloze mimo žurnál (staging je zakládá přímo SQL) po obnově neexistuje, příslušné kroky přehrání se přeskočí; kvůli tomu nelze přehrát ani udělení admina takové identitě, proto je tu `--grant-admin`. (5) Tabulka `restore_superseded_sessions` je omezena (16 384), `restore_generations` (256); po vyčerpání nástroj odmítne obnovu důvodem `capacity_exhausted` (nic se nezmění) a je třeba nový staging store. (6) Nová epocha každé identity znamená, že se po obnově musí přihlásit všichni; klient dostane `session_restored` a nesmí smazat frontu (R2c.5). (7) Brána po restore se starší zálohou s jinou generací než konfigurace vrací 503 bez kódu (metadata nesedí), ne `restore_pending`; nástroj ji přesto zpracuje a odmítne ji důvodem `backup_predates_restore`. (8) Mechanismus nebyl prověřen vůči hostilnímu operátorovi (staging).

**Klientské sync jádro (R2c.5a, pouze knihovna bez UI a bez DOM; mechanismus je návrh ke schválení vlastníkem v tomto PR; IndexedDB adaptér a Playwright scénáře dodá R2c.5b):**

R2c.5 se dodává ve dvou PR. **R2c.5a** (tento krok) je knihovna `lib/target-sync/` (TypeScript, bez Reactu, bez DOM): `storage.ts` (rozhraní `TargetSyncStorage`), `memory-storage.ts` (referenční adaptér se vstřikováním chyb), `transport.ts` + `fetch-transport.ts` (typované výsledky a `fetch` implementace), `client.ts` (`TargetSyncClient`), `fake.ts` (fake server s modelem kontraktu, `FakeScheduler`) a unit testy `tests/target-sync-*.test.mjs` včetně integračního testu nad **skutečnými** route handlery, skutečnými durable sessions a skutečným operátorským restore. **R2c.5b** přidá IndexedDB adaptér a cílené Playwright scénáře bez plné E2E sady. Zapojení do `use-lumi-app` je R3.

- **Úložiště.** `TargetSyncStorage` nabízí jmenné prostory (`openNamespace`, `listNamespaces`, atomické `deleteNamespaces`); `TargetSyncNamespace` nabízí `get`, `list(prefix)` a atomické `transaction(ops)` (`put`, `delete`, `deletePrefix`). Název prostoru je neprůhledný řetězec odvozený z (`userId`, `restoreGeneration`). Klient drží vždy jen handle vázaný na **jeden** prostor, takže aktivní session nemá jak číst cizí prostor. Smluvní požadavky na každý adaptér: transakce je atomická (nikdy napůl aplikovaná stránka feedu), handle smazaného prostoru odmítá čtení i zápis a prostor znovu nevytvoří, hodnoty jsou JSON a vrací se jako nezávislé kopie.
- **Transport.** Každá odpověď staging rout se mapuje na jediný typovaný výsledek: `ok` (s `replayed`), `conflict` (`stale_revision`, `idempotency_conflict`, `write_area_mismatch`, `unspecified` pro 409 titulní routy bez `code`), `resync_required`, `read_stale_reload`, `cursor_invalid` (400), `unavailable` (404), `unauthorized` (`session_expired` | `session_revoked` | `session_restored` | bez kódu), `store_unavailable` (503, volitelně `restore_pending` | `journal_invalid`), `rate_limited` (429 s `Retry-After`), `invalid` (ostatní 4xx včetně `protocol_unsupported`) a `uncertain` (síťová chyba, timeout, 5xx mimo 503, neparsovatelné nebo tvarově chybné tělo 200). Každý zápis nese `x-lumi-target-protocol: 1`, `credentials: same-origin` a tělo s přesnou množinou klíčů routy včetně `writeAreaId` a `restoreGeneration`; ID úkolu je jen v URL. Mapování bylo ověřeno proti kódu rout, ne jen proti dokumentaci.
- **Identita.** `activate({userId})` nejdřív **atomicky smaže každý jmenný prostor každé jiné identity** (bez události, bez počtu, bez jakékoli informace nové identitě) a teprve potom otevře prostor stejné identity; stejná identita znovu otevře svůj (případně zamčený) prostor, odemkne ho a znovu dostane neodsouhlasená hlášení. Pozdní odpověď transportu patřící předchozí identitě se po přepnutí zahodí (každý krok enginu po `await` ověřuje, že session je stále aktivní). Selhání mazání jiných prostorů aktivaci zruší a zůstane jako nedokončené mazání. **Zdokumentované omezení 5a:** na zařízení smí být lokálně jen jedna identita; kryptograficky oddělené zamčené prostory více identit nejsou součástí 5a (možná budoucí práce), proto přepnutí identity data předchozí identity maže. Offline změny předchozí identity nelze po přepnutí obnovit.
- **Bootstrap a feed.** Klíčové stránky bootstrapu, potom feed od watermarku; každá stránka (položky, kurzor, fáze, hlášení) se zapisuje **jednou atomickou transakcí**, takže selhání zápisu nezanechá napůl aplikovanou stránku a stejná stránka se při dalším průchodu zopakuje. Upsert se použije jen pokud je novější (vyšší revize, nebo **stejná revize s jinou efektivní Oblastí**, což je případ přesunu projektu); tombstone vždy vítězí a smaže položku i její příkazy; oznámení jsou idempotentní. `left_scope` smaže položku, jen pokud lokální efektivní Oblast odpovídá Oblasti v oznámení (opožděné oznámení o staré Oblasti nesmaže položku už viděnou v nové), a smaže její koncept a příkazy s hlášením počtu; `access_lost` smaže položky, tombstony, koncepty a příkazy dané Oblasti s hlášením počtu; `access_granted` zahájí bootstrap Oblasti z `areaCursor`; `role_changed` označí příkazy dané Oblasti k přehodnocení. `read_stale_reload` zopakuje týž cursor (omezeně, pak back-off); 429 a 503 vedou na back-off přes injektovaný scheduler. `cursor_invalid` a `resync_required` se **shodnou generací** (kompakce logu, příliš mnoho Oblastí) spustí nový bootstrap **bez smazání fronty a konceptů**; jeho dokončení odstraní položky, které server už neukazuje (jejich koncepty a příkazy se smažou a ohlásí jako `not_in_bootstrap`), protože přístup k nim zanikl, zatímco klient nečetl feed. Takový bootstrap se označí `bootstrapId` a nic nemaže, dokud není celý hotový.
- **Fronta a koncepty.** Příkaz má `commandId` (UUID v4, vytvořen jednou), druh (`title` | `delete`), `taskId`, `expectedRevision` (CAS token), `writeAreaId`, `restoreGeneration`, stav (`queued` | `sending` | `uncertain` | `frozen`) a počty pokusů. Odesílání je jednopřístupové a FIFO na úkol. Před každým pokusem se stav `sending` zapíše do úložiště, takže příkaz zachycený pádem aplikace se po restartu bere jako `uncertain`. **CAS token** (hash obsahu a ACL, klient ho z feedu neodvodí) se čte přes `GET .../title` **až po úpravě** a přijme se jen tehdy, když po následném dohonu feedu má položka stále revizi, na které uživatel úpravu postavil (`baseItemRevision`); jinak by token potichu přenesl cizí novější obsah. Bez sítě se koncept zařadí **bez tokenu** a token se získá se stejnou kontrolou při odesílání. Výsledky:
  - `ok` / `replayed`: příkaz i koncept zmizí, nový stav přinese feed.
  - `uncertain` (a také 401 a prostý 503 u zápisu, protože kontrola owner cookie nebo `!unchanged` může přijít až po commitu): příkaz zůstane `uncertain` a **nikdy se neposílá naslepo znovu**. Zeptá se status endpoint se stejným `commandId` a **aktuální Oblastí položky z feedu** (po přesunu vrací stará Oblast `write_area_mismatch`): `committed` = hotovo, `not_recorded` = tentýž příkaz smí být odeslán znovu, neznámý výsledek = zůstává `uncertain` a back-off.
  - `conflict` (včetně `write_area_mismatch`): koncept zůstane, stav `conflict`, `reloadOffered`, událost `conflict`. Zahodit lze koncept jen explicitně (`discardDraft`); `reloadTask` dohoní feed a vrátí čerstvou položku, `resubmitDraft` ho postaví na aktuální položku s novým `commandId`.
  - `unavailable` (404, např. snížení na viewer bez `access_lost`) a `invalid` (400): příkaz se vyřadí z odesílání, koncept zůstane `unsendable` a ohlásí se počet; nikdy se neopakuje. U tombstonu je koncept `unsendable` (`item_deleted`); smazán je jen při `access_lost` nebo `left_scope`.
  - `rate_limited` a `store_unavailable` s kódem (`restore_pending`, `journal_invalid`): příkaz zůstane ve frontě s back-offem (odpověď přišla před jakoukoli prací).
  - `role_changed`: příkazy Oblasti se před dalším odesláním přehodnotí čtením CAS tokenu (server rozhoduje; 404 = neodeslatelný), takže nedojde ani k pokusu o zápis.
  - **Odchylka od prvního návrhu:** prostý 503 bez kódu při zápisu se bere jako nejistý, ne jako „ponechat ve frontě“, protože route ho umí vrátit i po commitu.
- **401.** `session_expired` a 401 bez kódu (owner cookie) = konzervativně totéž: odesílání se pozastaví, jmenný prostor se zamkne (data a fronta zůstanou, **všechna čtecí API vrací `locked`**, úpravy jsou odmítnuty), událost `locked` a `reauth_required` jde jen této identitě. Po `activate` téže identity se prostor odemkne a fronta pokračuje; každý příkaz server znovu autorizuje. `session_revoked` nebo `logout()`: spočítají se neodeslané změny, hlášení (`session_revoked` / `logout`) se pošle **nejdřív této identitě**, teprve potom se smažou všechny prostory identity; nikdy jiné identitě. `session_restored`: fronta se **zmrazí** (stav `frozen`, v nové generaci se nikdy automaticky neodešle), cache se vyprázdní, prostor se zamkne jako `restore_pending_reauth` a pošle se `reauth_required`; po `activate` téže identity proběhne obnova níže.
- **Obnova a resync.** Spouští ji `session_restored` + nové přihlášení, nebo první stránka nového bootstrapu s **jinou** `restoreGeneration` (po `resync_required` z feedu nebo zápisu). Postup: (1) fronta staré generace se zmrazí a cache se vymaže ve staré generaci (nikdy se znovu nenahrávají staré položky); (2) nový plný bootstrap se zapisuje do nového prostoru (`userId`, nová generace), který si pamatuje zdroje (`supersedes`); do dokončení jsou čtení i úpravy `resyncing`; (3) v téže transakci jako poslední stránka se z každého konceptu staré generace, jehož úkol je v novém bootstrapu čitelný, stane **lokální koncept** (`local`, bez příkazu, bez `commandId`), ostatní se smažou; (4) ohlásí se jedno hlášení `restore` s oběma počty (`keptAsDrafts`, `removed`); (5) starý prostor se smaže (po pádu mezi 3 a 5 ho smaže další `activate`). Do dalšího kroku se **nic automaticky neodešle**; `resubmitDraft` je explicitní akce, která koncept postaví na čerstvou položku a nový CAS token nové generace. Druhá obnova uprostřed rozpracované první zachová původní zdroje konceptů. Obnova nevrací odebrané členství ani session, takže B odebraný po záloze po bootstrapu nemá položky a jeho koncepty se smažou s ohlášeným počtem.
- **Hlášení a události.** Typovaný proud `report`, `reauth_required`, `locked`, `conflict`, `unsendable`; každá událost nese `userId` a doručí se jen aktivní identitě. Hlášení jsou perzistovaná ve jmenném prostoru a znovu se doručí téže identitě po restartu, dokud je `acknowledgeReport` nepotvrdí; hlášení čekající při přepnutí identity se smaže s prostorem a nová identita je nikdy neuvidí. Hlášení při `session_revoked` a `logout` nelze perzistovat (prostor se maže), proto se emitují synchronně před smazáním.
- **Scheduler a hodiny.** Injektovaný `SyncScheduler` (`now`, `setTimeout`, `clearTimeout`); back-off je exponenciální (1 s až 60 s) a respektuje `Retry-After`; testy používají `FakeScheduler` a žádné skutečné časovače.
- **Hranice a omezení 5a.** (1) Jedna identita na zařízení, bez kryptografického oddělení (viz Identita). (2) Aktivní `activate` nečeká na rozpracovaný síťový požadavek předchozí session; její pozdní výsledek se zahodí a handle smazaného prostoru musí odmítat zápisy (smluvní požadavek na adaptér, IndexedDB adaptér v R2c.5b to musí splnit a otestovat). (3) Selhání mazání při `session_revoked`/`logout` vrátí `wiped: false` a mazání se dokončí před další aktivací; do té doby klient nic nezpřístupňuje. (4) Offline úprava bez tokenu se při odeslání ověřuje dohonem feedu; mezi čtením tokenu a dohonem feedu zůstává okno ohraničené jedním požadavkem (server stejně ověřuje CAS). (5) Jeden koncept na úkol; úprava textu nevyslaného příkazu mění jeho obsah, odeslaný nebo nejistý příkaz je `busy`. (6) Selhání zápisu do úložiště vrátí chybu `storage_error` a ponechá stav před změnou. (7) Projekty se ukládají a synchronizují, ale R2c nemá projektové příkazy.
