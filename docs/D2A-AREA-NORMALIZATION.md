# D2 / krok 2a — normalizace Oblastí (přípravná implementace)

Kontrakt: ARCHITECTURE.md, PRODUCT.md LUMI-FR-013 a rozhodnutí vlastníka z 2026-10-23.

## Dodaná bezpečná část

- Funkce planAreaNormalization je čistý, deterministický **návrh** transformace dvou polí entities a relations: **žádné čtení ani zápis živé SQLite**, žádné změny workspaceId, ID, dat a revizí existujících entit.
- Každý projekt a samostatný úkol získá přesně jednu explicitní vazbu belongs_to_area; úkol s belongs_to_project vlastní area vazbu nemá, odvozuje ji od projektu. Redundantní existující vazby jsou **pouze v návrhu** odstraněny a jejich ID jsou v auditním reportu. Duplicitní `belongs_to_project` ke stejnému projektu se stejně jako duplicitní `belongs_to_area` deterministicky redukují na nejstarší relaci (podle `createdAt`, při shodě podle ID); různá cílová project ID celou normalizaci blokují. Původní relace se nemutují a odstraněná ID jsou v `removedRedundantRelationIds`.
- Výchozí oblast **Nezařazeno** je soukromá uvnitř personal workspace. Legacy sdílená data zůstávají uvnitř svého původního shared workspace s kompatibilní oblastí **Nezařazeno (původní sdílené)**. Textové legacy properties.area se mapuje jen podle přesného normalizovaného popisku **v témže workspace**; neznámý popisek vytvoří oblast ve stejném workspace, nikdy nezakládá nové sdílení.
- Nové ID oblastí a vazeb se odvozuje deterministicky (SHA-256 ze scope a canonical label / ID). Také zobrazovaný název nově vytvořené Oblasti se vybírá nezávisle na pořadí záznamů (normalizace whitespace/NFC, stabilní výběr ze všech variant v daném workspace); nové názvy nesmějí překročit limit validátoru 1000 znaků. Při opakování na již normalizovaném snímku se nepřidávají další vazby ani entity.
- Strukturální vstupní preflight sdílí s produkčním `validateSnapshot` identický, na SQLite nezávislý validátor (`lib/snapshot-validation.ts`): kontroluje přípustné typy entit (včetně pravidel pro `project.properties.context` z PR #104), ID, titulky, limity obsahu, timestampy, `properties`, workspace roli a členy, kalendářová rozhodnutí, relace i volitelné tombstones (unikátní ID, žádný překryv s živými entitami či relacemi). Chybné vstupy jsou odmítnuty před návrhem pod sanitizovaným důvodem `snapshot-structure-invalid` bez logování obsahu.
- Více možných oblastí, projektů, vadné interní vazby, chybné workspaces (včetně duplicitního či nekanonického workspace ID), rozpor legacy popisku s explicitním přiřazením, chybný typ přítomného legacy `projectId`/`areaId`/`area` nebo nesoulad projektové a úkolové oblasti **zablokují celou transformaci** (AreaNormalizationBlocked), žádná částečná mutace. Aktivní práce nesmí nově získat ani zachovat přiřazení k archivované Oblasti; archivované historické položky mohou své původní přiřazení zachovat. Pro chybějící/nepřiřazenou hodnotu legacy reference je přípustné `undefined`, `null` nebo prázdný řetězec.
- Report před/po uvádí počet entit a relací, vytvořené ID, odstraněné redundantní vazby, úkoly s děděním a potvrzuje neměnnost workspace každého starého objektu. Všechna pole se seznamy identit jsou řazena stabilně, bez závislosti na pořadí vstupních záznamů. Obsahuje také `existingAreaKindBackfillIds` a `areaKindBackfillRequired`: původní Oblasti bez `properties.kind` zůstanou beze změny (zachování starých revizí), **výsledek s tímto příznakem se nesmí považovat za plně normalizovaný ani aplikovat bez samostatného transakčního a auditovaného doplnění typu private/shared**. **Rozdíl počtů je explicitní a očekávaný** při doplnění chybějících oblastí/vazeb nebo odstranění redundance; nikdy nejde o tichou ztrátu původních projektů, úkolů, poznámek či vazeb. Před budoucí aplikací se musí auditovat každé odstraněné redundantní ID.

## Offline náhled nad výslovně připravenou kopií

Spustit na syntetickém/zkopírovaném JSON snapshotu s poli entities a relations:

    node --experimental-loader ./tests/ts-loader.mjs scripts/plan-area-normalization.mjs /cesta/ke/kopii.json

Plánovač respektuje i volitelné `tombstones` z offline snapshotu: pokud deterministické ID nově vytvářené Oblasti, vazby `belongs_to_area` nebo doplňované `belongs_to_project` bylo v minulosti smazáno, návrh skončí `AreaNormalizationBlocked` s kódem `tombstoned-generated-…`. Při duplicitních tombstone ID nebo překryvu tombstone s existujícím živým ID entity či relace zablokuje celý snapshot jako `snapshot-structure-invalid`, ještě před návrhem. Nikdy automaticky neoživuje smazaná ID ani je nenahrazuje nově vymyšlenými; vstupní záznamy a tombstones ponechává beze změny. Snapshot bez `tombstones` zůstává podporovaný jen jako starší offline formát, nikoli jako důkaz absence historických smazání. Skript pouze čte soubor a vrátí hash vstupu a auditní report bez obsahu záznamů. **Nemá přepínač pro aplikaci změn**. Pro SQLite se nejprve pořídí ověřená konzistentní kopie a ta se samostatným bezpečným nástrojem exportuje do JSON; živý store.sqlite se tomuto skriptu nepředává.

## Zbývá před aplikací 2a a navazujícím 2b

1. Ověřená plná záloha SQLite včetně historie, tokenů a lokálních klientských front, pnpm check-data nad kopií a inventář nejednoznačných vazeb, legacy štítků a reálných počtů dat.
2. Samostatný **transakční, zálohovaný a vratný 2a aplikátor** (povinná brána: klasifikace všech `existingAreaKindBackfillIds` a jejich auditovaná revizní změna před aktivací Area oprávnění): kontrola předpokládaných ID/revizí a původního snapshot SHA, nezměněný workspace každé položky, kontrola referencí a counts, audit, čitelnost z GET /api/store, nové device base a kompatibilita se starým offline snapshotem. Při konfliktu abort beze změn.
3. Doplňování oblastí musí platit také pro **nové zápisy** klienta, včetně offline scénářů; jinak se starý snapshot může vrátit před normalizaci. Do té doby jde **pouze o náhled**, ne zapnutou migraci.
4. Krok **2b** je další samostatná migrace se změnou sdílených workspaceId a s předčasnou restoreGeneration / offline-sync bariérou; **2c** řeší přiřazení otevřených legacy sdílených úkolů k owner. Teprve po 2a–2c lze aktivovat cílové UI Můj plán či víceuživatelský přístup.

Celá browser E2E sada se spouští až jako release gate bezprostředně před nasazením.
