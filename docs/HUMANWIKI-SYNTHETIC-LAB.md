# HumanWiki H0 / H1-synthetic laboratory

This is an offline design probe for [LUMI-FR-014](PRODUCT.md#lumi-fr-014) and the [HumanWiki decision](decisions/2026-11-08-humanwiki-knowledge-bootstrap.md). It is isolated in `scripts/humanwiki-synthetic`; no application route, Context Graph writer, database migration, provider call, account connector, or upload endpoint invokes it. The CLI accepts only the two checked-in fictional fixtures. It has no path argument for a real export. Its marker `synthetic_fixture: true` is a fixture convention, **not** an authorization control for production data.

Run `node scripts/humanwiki-synthetic/run.mjs chatgpt 1`, then run it again to resume the next message. Omit the final number to finish the bundled fixture. Use `claude` for the other fixture. The private local checkpoint lives in the OS temporary directory under `lumi-humanwiki-synthetic-lab`; delete that directory to restart the lab. It contains only the bundled fictional text and is never a production store. This lab is POSIX-only: its private-directory checks and directory sync depend on POSIX ownership, permission bits, and file flags. The CLI prints non-content counts and source ID. `node --test tests/humanwiki-synthetic.test.mjs` runs the focused contract tests.

The two allowlisted shapes mimic a narrow text-only ChatGPT `mapping` and Claude `chat_messages` structure; they do not assert compatibility with actual provider export versions. Parser limits: 256 KiB bundle, 50 conversations, 1,000 messages and 8,192 characters per message. Unsupported content, missing stable IDs, duplicate IDs, bad time, or unknown bundle shape fail with a clear error. Timestamps must include a UTC `Z` or explicit numeric offset and a real calendar date; zone-less, rolled-over or invalid-offset times are rejected. Valid offsets are normalized to UTC deterministically. Messages are sorted by stable IDs using UTF-16 code-unit order, independent of host locale, so replay order is deterministic. Each nonempty line gets an exact source/conversation/message/line locator, speaker, observation time, content digest, and conservative provenance. Markdown `>` lines are tagged `quoted_third_party` with `speaker=unknown` and a separate enclosing message speaker, so a quote never inherits the owner's identity. Text from assistant turns remains `assistant_generated`; other roles remain `unknown`. This is only a simple quote heuristic: inline quotations, code fences, attachments, branch semantics, edited/deleted messages, and provider-specific metadata need later adapters and tests. The fixture text is untrusted data and is never executed as instructions.

The staged record has `review=proposed`, `freshness=current`, an independent `disputed=false` axis, `sensitivity=unclassified`, and `scope=owner_private_unassigned`. It is a source segment, **not a claim**: no automatic identity resolution, fact extraction, confirmation, sharing, task, or external action occurs. In particular an assistant's fictional ownership assertion remains assistant-authored evidence, not proof of owner biography. Quoted text does not inherit the enclosing user speaker's provenance. Unknown sensitivity bars any future egress or sharing until classification and consent are implemented.

The checkpoint binds source ID and bundle digest to the next-message cursor. Resume replays and validates every prior record before advancing, so a truncated/edited checkpoint or changed fixture fails closed instead of skipping input. A present malformed checkpoint, including a falsy JSON value, is preserved and rejected rather than treated as a new import. The CLI requires its checkpoint directory to be owned by the current user, private, and not a symlink. It writes the entire state to a private temporary file, syncs it, atomically renames it and syncs the directory. An older lab checkpoint schema is deliberately rejected; delete only this lab's temporary directory to restart. This proves local replay and idempotence for the fixture; it does **not** implement the production consent ledger, encrypted quarantine, independent revocation witness, ACL, cross-source evidence independence, Context Resolver, or safe real-export retention. H1-real remains blocked by the R2d/R3 identity, ACL, sync, resolver and revocation gate, explicit consent, and the R4 production gate. Gmail content remains outside this lab and subject to its existing no-body/no-excerpt/no-background rule.

## Read-only synthetic source inspection (next H1-synthetic slice)

Before staging the fictional fixture, run `node scripts/humanwiki-synthetic/inspect-cli.mjs chatgpt` (or `claude`). The command accepts **only those two checked-in fixture names**, has no path argument, does not read or write checkpoints and does not call providers, application routes or the network. It returns a deterministic JSON inventory: the fixture's synthetic source ID, format and SHA-256, total/staged/pending message and source-segment counts, plus counts for the four independently preserved provenance categories. **No message text, quote text, claimed personal facts or identity graph is included** in the output. The separate `inspectSyntheticImport(parsed, prior)` pure helper can also validate an existing synthetic checkpoint without mutating it and report its progress; malformed or source-mismatched checkpoints fail closed.

This inventory is an **inspection aid**, not an import approval, a sensitivity classifier, consent record, trustworthy cross-source evidence counter or actual review queue. Every segment remains unclassified and proposed; `claims_created = 0` and `real_import_enabled = false`. As with the existing source digests, the non-keyed SHA-256 here is permitted only for bundled fictional fixtures and **must not be used for real-source deduplication, erasure tombstones or privacy claims**. H1-real and H2 still require the independent identity/ACL/revocation, consent and production release gates documented above.

## H1-synthetic: explicit triage intent rehearsal (no approvals)

Run `node scripts/humanwiki-synthetic/triage-rehearsal-cli.mjs` to inspect the default **zero-decision** rehearsal over the two checked-in fictional fixtures. The CLI takes no arguments, never accepts real paths or uploads, reads no checkpoints, writes nothing, and has no provider, network or production integration. The in-memory `rehearseSyntheticTriage([chatgptBundle, claudeBundle], intents)` helper is a **test-only API**, not an authorization or consent boundary. The `synthetic_fixture` marker does not make arbitrary user data safe.

For negative tests, callers may supply explicit ordered intents, each with an exact four-part source locator and one of three limited choices: `consider` (flag the *source segment* for later claim review), `skip` (skip this rehearsal's candidate; **not** erase the source), or `defer` (leave further assessment for later). No implicit decisions are made. Duplicate locators, unrecognized locators, invalid choices and unexpected/free-text input fields fail closed. Decisions apply to the **single selected locator**, never to other copies of the same text or to unrelated sources. The output contains a deterministic, nonpersistent **rehearsal event list** with ordinal steps, canonical locators and choices; it is **not** an audit log or durable consent/revocation record.

This mechanism does **not** change the Context Graph `review` status of any segment or claim. Even a `consider` choice leaves the segment `proposed`, `unclassified`, owner-private, awaiting explicit future review and ineligible for automatic confirmation. Provenance and direct/enclosing speaker remain unchanged; evidence independence is never asserted, including for identical text. Reports expose no text, source-content fingerprint or untrusted free-form comments, and maintain `claims_created=0`, `review_outcomes_written=0`, `real_import_enabled=false`. Real claim confirmation, source erasure, durable logs, consent, ACL, classification, external AI and H1-real/H2/R4 remain blocked behind their separately documented safety gates.

To smoke-test stale-source rejection over **only fictional committed fixtures**, run `node scripts/humanwiki-synthetic/version-bound-triage-cli.mjs`. The CLI accepts no paths or arguments, never writes checkpoints, and prints only whether one bound toy decision was valid for the unchanged fixture and rejected after a simulated edit. Rehearsal recomputes that source's digest and **fails closed** if any message text, speaker, timestamp, or other serialized part of that bundle changes, even if the selected message's locator stays unchanged. Invalid, missing, forged or duplicated intents and invalid locators are rejected by the binding/rehearsal checks. No implicit choices or propagation to identical text.

## H1-synthetic: source lifecycle policy preview — no actual operations

Run `node scripts/humanwiki-synthetic/lifecycle-preview-cli.mjs` to compare four **hypothetical states** of only the two checked-in fictional sources. The no-argument CLI reads no real exports, does not create/delete sources, writes no checkpoint or tombstone, and never calls the network, app runtime or a model. The pure `previewSyntheticSourceLifecycle([chatgpt, claude], scenarios)` helper receives at most one `{ source_id, action }` per fictional source. Inputs are strictly allowlisted and unknown/duplicate sources fail closed. This helper is not a production authorization boundary; the fixture marker itself is untrusted.

The actions deliberately retain different semantics from the [HumanWiki lifecycle decision](decisions/2026-11-08-humanwiki-knowledge-bootstrap.md):

- `pause_sync`: would stop **new source reads** but leave previously authorized pending source-segment review available; does not invalidate source evidence merely by pausing
- `disconnect_source`: would stop new reads and suppress source-dependent review and evidence; dependent caches/summaries would need invalidation, but no confirmed claim is silently erased
- `revoke_import_consent`: would stop ongoing import/analysis, suppress pending unclassified proposals, and require a **source-specific retention/consent re-evaluation** before anything could be retained; separately authorized confirmed claims are outside the lab model
- `request_erasure`: would deny access and future reimport without new explicit consent, require deletion of source-dependent derivatives and a durable tombstone plus independently anchored witness before *actual* completion could ever be reported

The preview's `would_allow_*` flags express hypothetical policy decisions, **never a permission to use actual content**. Its `visible_entries` contain no text or fingerprints, and exclude message-level locators for simulated inaccessible sources; `suppressed_segments` is a fictional fixture diagnostic count only and must not be shown across unauthorized boundaries in real UI. The state flags explicitly remain `operation_completed=false`, `durable_lifecycle_event_written=false`, `witness_confirmed=false`. No revocation, deletion or anti-rollback protection has occurred: `actual_source_reads_performed=0`, `tombstones_written=0`, `real_import_enabled=false`. Do not infer that `request_erasure` alone fulfills a GDPR-style deletion or durable revocation.

Actual token revocation, separate retention rights, Context Graph claim/evidence revalidation, ACL checks, cache invalidation, append-only registry, external independent witness and safe restore remain **blocked until the real H1/R2d/R3/R4 gates are implemented**. This test-only snapshot neither promotes assistant text nor creates claims, confirmed reviews or externally visible knowledge.

## H1-synthetic: restore preflight vs independently witnessed revocations (toy only)

Run `node scripts/humanwiki-synthetic/restore-preflight-cli.mjs` for a content-free demonstration of backup rollback detection. The CLI accepts **no arguments** and creates only two fake scoped source tokens and two tiny fictional registry events **in memory**. It opens no user exports, touches no application DB or backups, connects to no network/external witness, writes no registry/tombstone/checkpoint and authorizes no imported knowledge.

`makeSyntheticRestoreFixture()` prepares fictional `request_erasure` and `revoke_import_consent` events with monotonically numbered sequence and a toy SHA-256 event hash chain. `previewSyntheticRestorePreflight(state)` checks the complete contiguous toy registry chain, an explicit separately supplied witness high-water sequence and digest, available-key and externally verified-witness **test flags**, and the restored snapshot's last applied checkpoint. It distinguishes:
- An older DB snapshot with intact newer registry **and** witness: `requires_replay_and_revalidation` (no replay occurs in this PR)
- An older DB snapshot **and an equally old registry** with newer supplied witness: `blocked` (`registry_behind_external_witness`), avoiding apparently consistent rollback
- Missing/unverified witness, missing key, sequence gaps, hash mismatch, unanchored registry tail, or inconsistent snapshot cursor: always `blocked`
- A fully matching snapshot/registry/witness: `checks_passed_in_toy_only`, **never production authorization**

The toy scenario is intentionally *stricter* than the roadmap's minimum `registry >= independently confirmed high-water mark`: its registry must match the exact supplied witness tip, so any unwitnessed tail blocks. Outputs contain only synthetic reason codes, fictional opaque tokens and optional **not-yet-replayed** event metadata, no content, text hashes or real source identifiers. Even a successful toy check always has `data_release_authorized=false`, `actual_restore_applied=false`, `replay_completed=false`, `actual_witness_contacted=false`, `durable_events_written=0`, `tombstones_written=0`, `real_import_enabled=false`.

**Not a security implementation:** the SHA-256 chain has no secret or authenticity guarantee. A caller could forge both data and its digest, and `toy_independent_witness_verified=true` is **merely a simulated input boolean**, never an independent external authentication. Real H1-real/R2d/R3/R4 must implement a separately trusted anti-rollback witness outside both DB and registry recovery domains, authenticated/monotonic checkpointing, atomic durable revocation and witness confirmation, scoped HMAC rather than unkeyed source-content fingerprints, safe key rotation/loss, end-to-end restore replay, cache/AI index invalidation, identity/Area ACL and genuine retention/consent enforcement before any real knowledge may be released. This laboratory must never be wired into real consent, erasure or production APIs.

## H1-synthetic: post-restore replay obligations (dry-run only)

Three possible states are intentional: `blocked` means the preflight rejected a missing/wrong witness, missing key, corrupted chain or snapshot, so **no per-source event obligations** are exposed; `requires_hypothetical_replay` lists a content-free, ordered obligation set for each pending fictional revocation or erasure; `preflight_passed_revalidation_still_required` means no pending events but never implies the restored system or dependent caches are fit to serve.

The distinct **policy obligations** are:
- `request_erasure`: delete the source and claims supported exclusively by it, remove the erased evidence from multi-source claims and revalidate independently lawful remaining evidence, invalidate dependent search/caches/embeddings/exports/summaries, and protect against resurrection by a durable independent tombstone/witness

All scenarios retain explicit global gates for current independently verified anti-rollback witness, **actual** registry replay, identity/Area ACL, consent and evidence revalidation, derived-index and cache invalidation, transactional restoration, and final release review. The plan only names the work; it performs **none** of it. `all_release_gates_satisfied=false`, `replay_completed=false`, `data_release_authorized=false`, `actual_restore_applied=false`, `actual_witness_contacted=false`, `tombstones_written=0`, `durable_events_written=0`, and `real_import_enabled=false` are invariant. The source IDs and counts in this CLI are fictional fixture diagnostics only, never a permission-safe design for production.

This is **not** a post-restore executor, claims provenance engine, retention auditor, real consent implementation, append-only registry, or independently anchored witness. The preceding toy preflight's SHA chain and caller-supplied witness flag remain non-authenticating. Before enabling real H1/H2 or R4 any such flow needs durable, authenticated and atomically confirmed revocation recording, anti-rollback external witness, safe key/HMAC rotation and recovery, source-specific lawful retention decisions, full derived-store invalidation and ACL revalidation. Never use this lab as a production recovery or data-release control.

## H1-synthetic: claim/evidence and derived-output invalidation graph (read-only)

Run `node scripts/humanwiki-synthetic/derivative-impact-preview-cli.mjs` to inspect the next **fictional, nonpersistent** step after restore preflight and replay-obligations planning. `previewSyntheticDerivativeImpact(state, graph)` first rechecks the upstream in-memory restore/witness gate. It does **not** reuse a cached or client-asserted pass flag. If the gate is blocked, it reveals **no** claim IDs, source IDs, artifact IDs, dependency links, or impact counts. ## H1-synthetic: completeness gate for the fixed fictional dependency graph

The read-only `previewSyntheticDerivativeImpact` now verifies **toy fixture coverage**, not only the format and known IDs of the supplied dependency graph. A graph can be syntactically valid yet omit a known claim, omit a terminal export/cache, or reroute an existing dependency to another allowed ID. In these cases a later impact calculation might silently miss a dependent artifact. The new in-module reference manifest independently lists the **expected six fake claim/evidence sets and ten fake artifact/dependency sets**.

After revalidating the existing toy restore preflight and before returning any source-specific impact, the preview now compares each claim's evidence and each artifact's dependency set to this fixed expected inventory (order-insensitive, but exact membership required). Missing/repointed known edges, missing nodes or empty graphs return `impact_status=blocked`, `reason=fictional_dependency_coverage_incomplete` and **empty** `claim_impacts`/`artifact_impacts`. A missing/wrong witness still blocks first and never inspects an arbitrary graph. The fixture-only CLI demonstrates a missing known artifact being blocked; negative tests cover partial graphs, missing evidence and valid-looking rewired edges.

**Interpretation is essential:** `fictional_fixture_manifest_matched=true` is evidence only that the two hardcoded toy arrays agree. The graph manifest is code running in the same trust domain as the toy fixture; it is not an independent audit or a production source of truth.

Before any H1-real/production release, derive the complete source-to-claim-to-artifact inventory from an authoritative, access-controlled provenance store; bind it to a durable revision and independently verified revocation checkpoint; fail closed on missing/unindexed consumers, unsatisfied ACL/retention/evidence checks and concurrent changes; verify actual cache/index/AI export invalidation **transactionally** before serving. This laboratory does none of that.

## H1-synthetic: revision-bound dependency observation — stale results never imply release

Run `node scripts/humanwiki-synthetic/derivative-revision-cli.mjs` for a zero-argument, zero-write demonstration of rechecking a previously prepared **fictional** dependency observation against the current in-memory toy restore and graph. The helper pair `bindSyntheticDerivativeRevision(state, graph)` and `recheckSyntheticDerivativeRevision(state, graph, binding)` builds on the complete #349–#353 preflight, replay plan and fixed-fixture graph coverage gate. ## H1-synthetic: optimistic epoch fence / interleaving rehearsal (zero-write)

Run `node scripts/humanwiki-synthetic/epoch-fence-rehearsal-cli.mjs` to inspect a deterministic, fixed-fictional simulation of a stale dependency result between two checks. This continues the #354 version-bound preview but adds an explicit **caller-supplied toy epoch** to the fictional restore state and graph revision binding. All source/claim/artifact IDs remain hardcoded toy identifiers; the CLI takes no parameters and writes nothing.

`bindSyntheticEpochFence(frame)` validates a narrow `{toy_epoch, restore_state, graph}` structure, passes the existing upstream preflight and graph-coverage gates, and combines the previous two toy revision digests with a nonnegative safe-integer toy epoch. `recheckSyntheticEpochFence(frame, binding)` freshly reruns the upstream integrity/coverage checks and compares current toy epoch **and** both digests. Its positive status, `toy_fence_matches_no_release`, never authorizes or performs a restore, deletion, cache invalidation, read, or transaction. Missing witness or incomplete graph blocks before source-specific information is considered.

`rehearseSyntheticFenceWindow(firstFrame, finalFrame, binding)` demonstrates two explicit observations: if the first recheck is stale or blocked, it does not inspect the final frame; otherwise it checks the final frame again. The smoke scenarios include: unchanged inputs (only `toy_checks_match_no_commit`); a changed but valid snapshot without epoch increment (stale); an unavailable witness at the final check (blocked); and an **explicit A → B → A transition**: A at epoch 1 uses the original fictional restore cursor; B at epoch 2 advances that cursor to a different, independently valid toy snapshot; A at epoch 3 restores the exact original graph and snapshot, which the earlier epoch-1 binding rejects as stale. A lower final epoch is explicitly rejected as a hypothetical rollback. The CLI and regression tests verify B is genuinely different from A and independently passes the toy restore preflight, then check that returned A has exactly the original content.

**Critical limitation:** the epoch is supplied by the caller and has **no trustworthy monotonicity guarantee**. A negative A → B → A scenario deliberately restores both the original content **and the original epoch**: the toy check then returns `toy_checks_match_no_commit`, demonstrating that it cannot detect this rollback. This result still has `data_release_authorized=false` and `actual_compare_and_swap_performed=false`. The detection case works only when a cooperating simulated writer increments the epoch, so an actor who restores the old epoch together with old inputs can forge apparent agreement. The two checks are **not atomic with any real operation**; a concurrent mutation immediately after the final check would not be detected. This is a logical race rehearsal, not a compare-and-swap, lock, transaction, durable witness or source-of-truth revision protocol. The binding hashes are unkeyed **toy-only** SHA-256 over fictional metadata and must never be persisted or used with personal source material.

Every return value keeps `actual_compare_and_swap_performed=false`, `real_monotonic_epoch_authenticated=false`, `actual_witness_contacted=false`, `data_release_authorized=false`, `actual_invalidation_performed=0`, `actual_deletions_performed=0`, `actual_replay_performed=false` and `real_import_enabled=false`.
