# Owner session revocation — security hotfix (2026-11-12)

Scope: one security PR **outside milestone A**. Only the owner cookie `ai_executive_session`; never the already-revocable target durable sessions in `lib/target-staging-durable-session.ts`.

## Issuance and renewal audit
- Password login (`app/api/auth/login/route.ts`) calls `createSessionToken()` after verifying the password.
- Passkey login (`app/api/auth/passkeys/login/verify/route.ts`) calls the **same** `createSessionToken()` after verifying a WebAuthn assertion.
- Passkey registration does **not** issue or refresh a cookie.
- Auth status is read-only. No activity-based refresh or token-renewal route exists in `app/api/auth/**`.

## Revocation contract
- The signed owner payload includes integer `issuedAt` (milliseconds). Old cookies without it and signed cookies older than seven days are rejected.
- A single authoritative `valid_from_ms` integer lives in `$AI_EXECUTIVE_DATA_DIR/owner-session-valid-from.sqlite`, in a dedicated SQLite database with one row. Every owner-cookie check reads it live; `issuedAt > valid_from_ms` is required.
- **No HTTP request initializes or repairs the store.** A missing, invalid, symlinked, unreadable or unsafe-permission state file denies authentication. Password login gets HTTP 503 and passkey login gets HTTP 503, rather than implying invalid credentials.
- Authenticated logout increments the cutoff with `max(Date.now(), previous + 1)` in a synchronous SQLite `BEGIN IMMEDIATE` transaction, then expires the cookie. Every previous owner cookie is rejected across all devices/processes, including legacy and target-staging reads. Concurrent logouts cannot move the cutoff backwards.
- SQLite rollback-journal transactions release write locks automatically after a killed process, unlike persistent directory-based lockfiles. `synchronous=FULL` protects committed updates. No stale-lock cleanup is required.
- `GET /api/store` and the other primary legacy GET endpoints perform the same owner-cookie validation **after** serializing their response and immediately before release. Target-staging admission/release checks already existed.
- Playwright provisions only its own freshly allocated `lumi-e2e-*` data directory before starting the isolated browser-test server; production remains fail-closed.
- No changes to `lumi_target_staging_session` (durable target sessions), integration bearer tokens, or their independent revocation.

## First deployment — mandatory one-time step
1. Verify every app worker uses the **same private, persistent** `AI_EXECUTIVE_DATA_DIR` on one shared filesystem. The cutoff is not included in ordinary application data backups and **must not be rolled back**.
2. **Always run the reviewed target script**, even on the very first rollout. Follow [the reviewed-SHA deployment entrypoint](../deployment/DEPLOY.md), which executes `deployment/deploy-safe.sh` from the pinned commit with `git show`. Do **not** launch the old working-tree copy (`/opt/ai-executive/deployment/deploy-safe.sh`) before updating the checkout: that version cannot initialize the new cutoff. The reviewed target script performs **one-time** initialization as the service account, after backing up the data and checking the first rollout transition (old commit lacks owner revocation, new commit contains it), **before** the new service starts. It validates existing state without overwriting it; a missing state on subsequent deployments is fatal. For an explicitly authorized nonstandard/manual rollout, run as the service user with `AI_EXECUTIVE_DATA_DIR` set:
   ```sh
   node --experimental-loader ./scripts/target-staging-ts-loader.mjs scripts/owner-session-revocation-init.mjs --init
   node --experimental-loader ./scripts/target-staging-ts-loader.mjs scripts/owner-session-revocation-init.mjs --check
   ```
   `--init` refuses to overwrite a prior cutoff; `--check` never creates it. Both require the real persistent data directory. No login can bootstrap the state.
3. Deploy the new code, then sign in once on each device. Pre-deployment cookies lack `issuedAt`, so every device must reauthenticate. **First-rollout rollback is fail-closed after the code switch has begun or provisioning could have started:** the deployment trap stops the service and refuses to reset/start older cutoff-unaware code. If backup creation fails **before** fast-forward and before any initialization attempt, the still-unchanged old service may be restarted only when its original checkout is verified and no cutoff file exists; repair the backup problem and retry the normal reviewed deployment. A previously present cutoff blocks that early restart. After code switch or possible provisioning, absence of the file is not proof that a prior cutoff never existed. Preserve the state and verified backups, investigate the failure, then deploy a version that checks the cutoff. Starting the old code again requires explicit operator action **and rotation of `AI_EXECUTIVE_SESSION_SECRET` first** so that no previously issued signed cookie becomes valid. Do not delete or roll back the cutoff. To restore a stopped, already cutoff-aware checkout after repairing the underlying failure, use the guarded **`--recover-stopped`** entrypoint in [deployment/DEPLOY.md](../deployment/DEPLOY.md), not the normal deploy command; it accepts the same or a newer reviewed `main` SHA only with a valid existing cutoff and a stopped service, and preserves backup/health checks. It refuses recovery if the cutoff is missing or the checkout lacks this security feature.
4. Normal restarts require **no** initialization command. If the file disappears/is damaged, leave authentication denied, investigate and recover the original state. **Do not just recreate it.** If irrecoverable, rotate `AI_EXECUTIVE_SESSION_SECRET` (invalidating every old signature) *before* an explicitly authorized re-provisioning; restarting or logging in does not reinitialize the file.
   **Exceptional first-rollout recovery:** If an operator already deployed the feature using the *old* on-disk deploy script, the new app can be running with no cutoff file and sign-in returns 503. Do **not** pretend this is a routine missing-state restart, and do **not** run `deploy-safe.sh` again expecting it to initialize the file: `PREV` already contains the feature, so the first-rollout guard will refuse. Instead, stop the service and confirm from deployment history, backups and authentication logs that this is genuinely the **first** installation and that the cutoff **never existed** (not lost, deleted or restored). An operator may then use the explicit `--init` and `--check` commands above as the service account with the persistent data directory and restart after validation. If you cannot establish that no prior state existed, treat it as state loss and **rotate `AI_EXECUTIVE_SESSION_SECRET` before any re-provisioning**. Do not use anonymous login attempts as proof. Record the reason and verification in the incident log before bringing the service online.
5. Never restore an older cutoff snapshot. SQLite requires a local filesystem with functioning cross-process locks. Separate replicas using independent directories are unsupported.

## Regression and verification
`tests/owner-session-revocation.test.mjs`: explicit provisioning, old token refusal, cross-origin/anonymous logout, copied cookie rejected on `/api/store` and `/api/target-staging/tasks`, new login, monotonic concurrent cross-process logouts, durability across process restart, killed write-holder recovery, missing/corrupt/symlinked store refusing login and authenticated requests, and passkey storage-outage classification. Full browser E2E remains a pre-production gate, not a PR gate.
