# R3: stagingové přejmenování projektu

Výchozí stav je nadále default-off. Pro oba nové endpointy (`GET` preview i `PATCH` write) je nutný samostatný serverový příznak `AI_EXECUTIVE_TARGET_STAGING_HTTP_PROJECT_TITLE_WRITE_ENABLED=true` **spolu s** `AI_EXECUTIVE_TARGET_STAGING_HTTP_ENABLED=true` a `AI_EXECUTIVE_TARGET_STAGING_HTTP_WRITE_ENABLED=true`. Bez samostatného příznaku odpovídají oba endpointy 404, i když jiné stagingové zápisy běží; příznak je nezávislý na vypnutém UI. Stejnou podmínku ověřují izolované podprocesy, nikoli jen HTTP router. `GET /api/target-staging/projects/:id/title` vrací editorovi nebo správci sdílené Oblasti a vlastníkovi soukromé Oblasti `{snapshotRevision,writeAreaId,restoreGeneration,principalBinding}`. Nový `principalBinding` je neprůhledný HMAC vydaný až po serverové kontrole aktuálního aktéra a oprávnění; zůstává shodný pouze pro stejného aktéra, projekt, restore generaci a podepisovací secret, není zapisovací oprávnění a `PATCH` jej nikdy nepřijímá. Spolu s odděleným potvrzovacím endpointem a klientským zámkem umožňuje ověření stejného aktéra po novém přihlášení; editor se otevře pouze při souběžném explicitním zapnutí všech sedmi default-off příznaků a aktuálním serverovém ACL. `PATCH` vyžaduje vedle stávajících HTTP a write flagů i hlavičku `x-lumi-target-protocol: 1`, stejný Origin a tělo `{commandId,title,expectedRevision,writeAreaId,restoreGeneration}`. ID aktéra plyne ze session. Oprávnění, generation, cílová Oblast a CAS se před zápisem znovu ověří v `BEGIN IMMEDIATE`. Viewer, nečlen a neexistující projekt dostávají 404; změna revize či konflikt ID příkazu 409. Při nejistém výsledku lze přesně zopakovat tentýž příkaz; aktuální oprávnění se znovu kontroluje i při replayi. Náhled není oprávněním k zápisu. Revize náhledu odpovídá autorizovanému projektovému detailu, takže ji může zneplatnit i souběžná změna obsahu Oblasti.

Zápis projektu, změnový feed a content-free audit/receipt se commitují atomicky; audit nepřenáší název a je neměnný. Je omezen na 4096 záznamů a při naplnění zápis selže uzavřeně. Audit má vlastní `project_title` intent v anti-rollback žurnálu. Pokud se datový COMMIT provedl, ale potvrzení žurnálu je nedůvěryhodné, backend **nikdy neodpoví úspěchem**; HTTP vrátí 503 a klient zachová výsledek jako nejistý. Důvěryhodnost úložiště je nutné obnovit/ověřit před opakováním **téhož** příkazu, nikoli vydávat nový `commandId`. Režim nezapíná produkční runtime ani R4 a samotné API nepředstavuje dokončení uživatelského toku R3-FE-4.

Nově vytvořený staging používá schéma v26. Přesné schéma v25 zůstává čitelné, zapisovatelné dosavadními příkazy i obnovitelné ze zálohy; nový projektový příkaz i jeho náhled jsou ve v25 nedostupné. Přechod je **explicitní operátorský krok**, nikoli automatická migrace při startu a nepovoluje reset ani produkční cutover. Před jeho provedením zajistit ověřenou obnovitelnou zálohu a zastavit staré instance serveru. Nad přesnou stagingovou cestou a aktuální generací se pak spouští:

```sh
node --experimental-loader ./scripts/target-staging-ts-loader.mjs scripts/target-staging-upgrade-v25.mjs --directory <absolutní-cesta> --generation <restore-generation>
```

Příkaz kontroluje přesné původní schéma, data, cestu, žurnál a svědka v zamčené transakci; přidá jen auditní tabulku, znovu ověří celé v26 a atomicky zaznamená `schema_upgrade` s původní a cílovou verzí. Uchovává existující data, session, generation i synchronizační historii. Opakování v důvěryhodném v26 vrací `already_current`. Exit 1 znamená odmítnutí nebo chybu, exit 2 (`confirm_untrusted`) znamená commit bez ověřeného potvrzení: před opakováním ověřit cestu a stav žurnálu i svědka, server mezitím nespouštět. Obnova starší zálohy v25 po přechodu ji vrací s novou restore generation a klient musí synchronizovat znovu; následně lze explicitní upgrade bezpečně zopakovat. Starší binární verze nezná v26 ani nový typ žurnálu a po přechodu musí selhat uzavřeně; rollback softwaru proto vyžaduje samostatný ověřený postup. Žádná uložená data ani záloha nejsou tímto kódem automaticky měněny.

**Stav UI — explicitní poslední opt-in:** editor zůstává **výchozně vypnutý**, ale nový samostatný příznak `AI_EXECUTIVE_TARGET_UI_PROJECT_REAUTH_RECOVERY_ENABLED=true` spolu se všemi šesti dosavadními UI/backend podmínkami nyní umožňuje cílené testování skutečného toku v izolovaném stagingu. `session_expired` se odlišuje od revokace a běžného 401; obsah původního příkazu i neodeslaného konceptu zůstává pouze v paměti do ověření **stejného aktéra a stejné generace úložiště** podle serverového `principalBinding`. Po reloadu se zachovává pouze neprůhledné UUID a důkaz identity v `sessionStorage`, nikoli název. Nový zápis se blokuje pro stejnou dvojici aktér–projekt, dokud server nepotvrdí původní commit; zámek zůstává uchován při přihlášení jiného aktéra, ale jeho obsah se mu nezobrazuje ani neblokuje nezávislé projekty. Všechny zápisy používají serverový CAS. `not_recorded` původní zámek nikdy neuvolní ani nepovolí nové UUID pro stejnou dvojici. Ztráta přístupu, revokace a jiný účet zahazují soukromý obsah. Tento feature gate není produkční aktivací, nenahrazuje samostatné end-to-end přijetí ani R4 release souhlas. Backendový zápis je nadále samostatně default-off.

**Čtecí potvrzení příkazu:** `POST /api/target-staging/project-title/recovery` přijímá pouze `{commandId}`, identitu zjišťuje výhradně na serveru a nikdy nevrací název projektu. Neměnný audit ověřuje aktuální oprávnění zapisovat do Oblasti, generaci i aktivní session; při potvrzeném zápisu vrací `{status:"committed",principalBinding}` (bez názvu ani identifikátorů projektu) pro ověření identity původního aktéra. Odpověď `{status:"not_recorded"}` **nedokazuje**, že dřívější požadavek nemůže později commitnout, a nesmí uvolnit bezpečnostní zámek ani povolit nový příkaz. Endpoint je default-off za samostatným projektovým backendovým flagem.
