# R3: stagingové přejmenování projektu

Výchozí stav je nadále default-off. `GET /api/target-staging/projects/:id/title` vrací editorovi nebo správci sdílené Oblasti a vlastníkovi soukromé Oblasti `{snapshotRevision,writeAreaId,restoreGeneration}`. `PATCH` vyžaduje vedle stávajících HTTP a write flagů i hlavičku `x-lumi-target-protocol: 1`, stejný Origin a tělo `{commandId,title,expectedRevision,writeAreaId,restoreGeneration}`. ID aktéra plyne ze session. Oprávnění, generation, cílová Oblast a CAS se před zápisem znovu ověří v `BEGIN IMMEDIATE`. Viewer, nečlen a neexistující projekt dostávají 404; změna revize či konflikt ID příkazu 409. Při nejistém výsledku lze přesně zopakovat tentýž příkaz; aktuální oprávnění se znovu kontroluje i při replayi. Náhled není oprávněním k zápisu. Revize náhledu odpovídá autorizovanému projektovému detailu, takže ji může zneplatnit i souběžná změna obsahu Oblasti.

Zápis projektu, změnový feed a content-free audit/receipt se commitují atomicky; audit nepřenáší název a je neměnný. Je omezen na 4096 záznamů a při naplnění zápis selže uzavřeně. Audit má vlastní `project_title` intent v anti-rollback žurnálu. Režim nezapíná produkční runtime ani R4 a samotné API nepředstavuje dokončení uživatelského toku R3-FE-4.

Nově vytvořený staging používá schéma v26. Přesné schéma v25 zůstává čitelné, zapisovatelné dosavadními příkazy i obnovitelné ze zálohy; nový projektový příkaz i jeho náhled jsou ve v25 nedostupné. Přechod je **explicitní operátorský krok**, nikoli automatická migrace při startu a nepovoluje reset ani produkční cutover. Před jeho provedením zajistit ověřenou obnovitelnou zálohu a zastavit staré instance serveru. Nad přesnou stagingovou cestou a aktuální generací se pak spouští:

```sh
node --experimental-loader ./scripts/target-staging-ts-loader.mjs scripts/target-staging-upgrade-v25.mjs --directory <absolutní-cesta> --generation <restore-generation>
```

Příkaz kontroluje přesné původní schéma, data, cestu, žurnál a svědka v zamčené transakci; přidá jen auditní tabulku, znovu ověří celé v26 a atomicky zaznamená `schema_upgrade` s původní a cílovou verzí. Uchovává existující data, session, generation i synchronizační historii. Opakování v důvěryhodném v26 vrací `already_current`. Exit 1 znamená odmítnutí nebo chybu, exit 2 (`confirm_untrusted`) znamená commit bez ověřeného potvrzení: před opakováním ověřit cestu a stav žurnálu i svědka, server mezitím nespouštět. Obnova starší zálohy v25 po přechodu ji vrací s novou restore generation a klient musí synchronizovat znovu; následně lze explicitní upgrade bezpečně zopakovat. Starší binární verze nezná v26 ani nový typ žurnálu a po přechodu musí selhat uzavřeně; rollback softwaru proto vyžaduje samostatný ověřený postup. Žádná uložená data ani záloha nejsou tímto kódem automaticky měněny.

**Stav UI:** rozpracovaný editor je pevně vypnutý i při nastavení `AI_EXECUTIVE_TARGET_UI_PROJECT_EDIT_ENABLED=true`. Důvodem je otevřená bezpečnostní a datová mezera: session runtime při jakémkoliv 401 zneplatní session-bound generaci a zahodí paměťové příkazy, zatímco nové přihlášení stejné identity dostane jinou generaci. Existující sync klient vyžaduje již serverově ověřeného `userId` a zpracovává pouze zápisy úkolů. Zapnutí projektu vyžaduje identity-bound uchování při `session_expired`, bezpečné znovuotevření jen po ověření téže identity a mazání při revokaci, spolu s integračními a bezpečnostními testy. Backendové staging API zůstává samostatně default-off.
