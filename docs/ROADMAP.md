### Řízení iterací a exit H1-synthetic — 2026-11-09

Platí [pravidla milníků](../AGENTS.md#outcome-based-milestone-governance-binding): jeden milník = jeden end-to-end akceptační test, rozpočet 1–3 PR, nejvýše dvě syntetická PR za sebou, stav roadmapy se aktualizuje ve feature PR.

**H1-synthetic — historicky uzavřeno po #355; pozdější laboratorní dodatky #358–#364 jsou také sloučené** (pouze fiktivní metadata; `claims_created=0`, `real_import_enabled=false`). Vlastníkem schválená jednorázová výjimka pro poslední bezpečnostní syntetický krok (check/use epoch, ABA) byla využita a PR #355 je v `main`. Další čistě syntetická PR bez nového výslovného rozhodnutí nevytvářet. **H1-real** = samostatný milník s akceptačním tokem export → návrh znalosti → lidské review → Context Graph → citované zobrazení; skutečný import vyžaduje ACL, klasifikaci citlivosti, souhlas, revokaci a R3/R4 brány.

**H1-real.0 — nový přípravný milník (zahájen 2026-11-10, po výslovném požadavku „pokračuj další HW iterací“):** Nejprve **readiness a default-deny vstupní hranice**, ne opět další syntetické importní demo. [Bezpečnostní kontrakt](HUMANWIKI-H1-REAL-ENTRY.md). **Akceptační krok této iterace:** nová funkce `denyHumanWikiH1RealImport` vždy odmítne volání *před čtením předaného requestu*, a to i při klientských `verified=true` a zapnuté env proměnné; metadata-only CLI vypíše šest nesplněných důkazů bez čtení soukromých souborů. **Nyní je napojena na skutečný deny-only `POST /api/humanwiki/import` handler**, který vždy vrací `404` bez čtení těla požadavku; integrační testy ověřují přístup k `Request` a falešné klientské souhlasy. Handler nesmí parsovat ani uložit upload, ale Next.js/runtime může převzít část přenosu před jeho zavoláním. To stále není importér ani důkaz o povolení reálné ingestace; před přidáním povolovací větve musí být odděleně ověřena identita, Area ACL, souhlas a nezávislý witness. Rozpočet přípravy **1–3 PR**; její úspěch není dokončením H1-real ani povolením uploadu. **Stav: deny-only serverová trasa a testy v PR k review, `real_import_enabled=false`**, další krok bude skutečný backendový ověřovací řetězec identity/Area ACL a evidence zdrojového souhlasu + nezávislého svědka, vyžadující oddělená bezpečnostní review a výslovný souhlas vlastníka před prvním reálným exportem.

**H1-real.1 — owner-authenticated readiness status (sloučeno #372, 2026-11-10):** Nezávislá rozpracovaná integrační iterace po sloučeném [#371](https://github.com/Kocooour/AI-executive/pull/371). **Konkrétní staging akceptace:** při výchozím vypnutém `AI_EXECUTIVE_HUMANWIKI_READINESS_ENABLED` nový `GET /api/humanwiki/readiness` vrací obecné `404`. Po explicitním zapnutí vrací `200` a **šest stále nesplněných bezpečnostních bran** výhradně vlastníkovi se skutečně nakonfigurovaným a platným podepsaným owner cookie; chybějící/expirující/podvržený token, developer bypass a ztráta konfigurace selhávají `404`. Druhý integrační test potvrzuje, že autentizovaný GET nikdy neodemkne původní `POST /api/humanwiki/import`, který stále odmítá bez čtení těla. [Kontrakt a reprodukce](HUMANWIKI-H1-REAL-ENTRY.md#h1-real1--autentizovaný-read-only-náhled-připravenosti-2026-11-10). **Není splněna** owner-private Area ACL, zdrojový souhlas, revokační witness, H1-real bootstrap, ani R3/R4. Další krok je integrovat autoritativní soukromou Area ACL a ledger souhlasů bez zapnutí importu. Milník se hodnotí podle skutečného HTTP handleru a negativních testů, nikoli jen syntetického status helperu.

**H1-real.2 — živý privátní Area ACL preflight (sloučeno PR #374, 2026-11-10):** Dle závazných pravidel milníků následuje **skutečná živá integrace**, nikoli další statický seznam nebo fiktivní token. `GET /api/humanwiki/private-area-preflight` je výchozím nastavením `404`; po explicitním zapnutí a platném owner cookie ověřuje **skutečné soukromé Area ACL** ve validovaném, připnutém, read-only transakčním staging SQLite včetně journal/restore anti-rollback guardu. Actor i Area ID pocházejí jen ze serverové konfigurace, jiný actor/Area, dev bypass, chybné či neplatné credentials, chybějící store nebo nesprávná restore generation vracejí `404` bez identity a dat. [Kontrakt](HUMANWIKI-H1-REAL-ENTRY.md#h1-real2--živá-owner-private-area-acl-pouze-preflight-2026-11-10). **Akceptace:** pět přímých HTTP handler integračních testů se skutečnou izolovanou SQLite a žurnálem, včetně trvalé blokace `POST /api/humanwiki/import`. **Nejde o oprávnění reálného importu**: žádný souhlas zdroje, samostatný witness, atomická use-time CAS, citační provenance, citlivost, review ani R3/R4. **Zbývajících šest H1-real release gate je stále blocked;** další milník musí přinést zdrojově specifickou durable consent evidenci a nezávislý revokační witness před návrhem importéru.

**H1-real.3a — lokální ledger záměrů souhlasu (sloučeno PR #375, 2026-11-10):** izolovaná SQLite append-only evidence pro ChatGPT/Claude s účelem, deklarovanou retencí, per-scope CAS, idempotencí a HMAC řetězem. Grant intent ani withdrawal intent **nejsou** aktivní souhlas či dokončená revokace; import vždy zůstává zamítnutý. [Kontrakt](HUMANWIKI-H1-REAL-CONSENT-INTENT.md).

**H1-real.3b — čerstvý kryptografický high-water preflight (sloučeno PR #377, 2026-11-10):** externí svědek musí odpovědět platným Ed25519 podpisem na náhodný nonce, globální sekvenci/digest a neprůhledné ID registru; helper porovnává lokální HMAC historii před/po volání a odmítne konzistentní starý restore, chybné podpisy, nedostupnost nebo změnu při ověřování. [Kontrakt](HUMANWIKI-H1-REAL-WITNESS-PREFLIGHT.md). **Akceptace** pouze na lokální SQLite a testovacím podpisovém klíči, bez produkčního externího backendu. Není dokázána nezávislost recovery domén ani úschova privátního klíče, neexistuje HTTP upload, skutečný souhlas či odemčení importu; všech šest H1-real gate zůstává blocked. Další milník: skutečná nezávislá monotónní infrastruktura, durable registr revokací a serverové write-time ACL.

**H1-real.4a — skutečná owner-private HTTP hranice pro žádosti o odvolání (sloučeno PR #378, 2026-11-10):** poprvé se propojuje **platná owner cookie + živý owner-private Area ACL + oddělené fyzicky perzistentní SQLite záměry souhlasu** v jediném default-off handleru `GET/POST /api/humanwiki/withdrawal-intent`. Pouze zdrojově specifický `withdrawal_requested` (ChatGPT/Claude), 1024B metadata-only allowlist, Origin CSRF guard, rate limit, přísný FS ownership/mode a HMAC CAS/replay; žádný `grant_requested` nebo upload. [Kontrakt a testy](HUMANWIKI-H1-REAL-WITHDRAWAL-HTTP.md). **Akceptace:** skutečné podepsané HTTP owner session + staging Area, oddělené SQLite s reopen a idempotentním opakováním, cizí Area/token/restore, grant/content, symlink/mode, CSRF a trvale deny-only import. **Výslovně neautorizující:** tento zápis není dokončená revokace, není atomický s ACL staging DB a nevytváří nezávislého svědka. Všech šest reálných H1-real bran zůstává blocked. Další potřebný milník: skutečně externí monotónní witness a transakční write-time ACL, nikoli další syntetická laboratoř.

**H1-real.4b — živé serverové HTTPS porovnání s externě nakonfigurovaným svědkem (sloučeno PR #379, 2026-11-10):** Milníková staging akceptace = autentizovaný vlastník při default-off GET `/api/humanwiki/witness-preflight` nejprve obdrží `404`; po explicitním zapnutí, živé owner-private Area ACL, fyzickém registru HMAC a **serverem připnutém** Ed25519 veřejném klíči se pro každý požadavek vygeneruje čerstvý nonce a odešle přes HTTPS na neměnnou externí URL jen neprůhledné registry ID a nonce. Výsledek se ověřuje proti lokální sekvenci/digest před i po remote I/O. Vadný podpis, coherent old restore, nedostupnost, redirect, velká odpověď, ztráta session/Area či změna klíče selhávají `404`; shoda vrací pouze neautorizující stav. [Kontrakt a integrační testy](HUMANWIKI-H1-REAL-LIVE-WITNESS-HTTP.md). Skutečný klient a serverový HTTP handler jsou implementovány, **remote monotónní witness služba ale ještě není nasazena ani provozně nezávisle ověřena**; testy remote síť mockují. Šest H1-real produkčních bran nadále blocked. Další nutný krok = samostatná durable monotónní witness infrastruktura + atomické event/checkpoint ack, nikoli povolení importu.

**H1-real.5 — samostatná signed monotonic witness služba (sloučeno PR #382, 2026-11-11):** Konkrétní integrační test na oddělené testovací instanci = operator-only `bootstrap`, durable sekvence 0 → 1 → 2 v samostatné SQLite, skutečný lokální HTTPS server podepisuje pouze svůj nejnovější stav pro klientem čerstvě vygenerovanou výzvu, nižší nebo přeskočené sekvence, změněná schémata, klíče, chybějící databáze a pokus o znovuzaložení jsou odmítnuty. [Kontrakt, omezení a reálný TLS test](HUMANWIKI-H1-REAL-INDEPENDENT-WITNESS.md). **Stále neprodukční:** služba není nasazená na odděleném hostu, chybí nezávislý mimo-backupový monotónní anchor, atomická witness ack publikace z aplikace a důkaz o oddělení klíčů/recovery domén. Žádné odemčení souhlasu, revokace, importu ani H1-real bran. Další rozhodnutí: bezpečné produkční oddělení svědka a durable event/ack kontrakt před jakýmkoli povolením dat.

**H1-real.6 — durable witness-side operator handoff s obnovitelným ACK (draft PR, 2026-11-11):** Akceptace = dva nezávislé syntetické HMAC/Ed25519 soubory a skutečný TLS server: lokálně potvrzené `withdrawal_requested` zůstane do zápisu svědka přes HTTP kontrolu blokované, offline operator publikuje přesně navazující globální sequence/digest, ztracený stdout po COMMIT znamená **idempotentní opakování stejného posledního checkpointu bez druhého eventu**, nikoli domněle neúspěšný zápis. Svědek vydá čerstvě podepsaný Ed25519 handoff, konfliktní/stará sekvence a poškozená historie se odmítají. [Kontrakt a integrační test](HUMANWIKI-H1-REAL-WITNESS-HANDOFF.md). **Stále neautorizující přípravný krok:** chybí off-host nasazení, kryptograficky ukotvený externí antirollback, skutečné event→witness source write-before-ack, atomické Area ACL a independent signer custody; žádné odemčení reálného importu, souhlasu ani revokace. Další H1-real rozšíření vyžaduje reálné operátorské prostředí a bezpečnostní rozhodnutí, ne další fixture-only PR.

**H1-real.7 — read-only witness catch-up z lokálního ledgeru (PR 2026-11-11, default-off):** [Akceptace a bezpečnostní hranice](HUMANWIKI-H1-REAL-WITNESS-CATCHUP.md). Operátorský CLI bez argumentů načítá živou fyzickou HMAC evidenci, ověřuje úplnou lokální chain, čerstvě podepsanou vzdálenou Ed25519 high-water a přesnou kontinuitu globálního prefixu; připraví právě jeden navazující neprůhledný `sequence/previousDigest/digest` tuple pro **manuální offline publish**, nebo nic při shodě. Nekonzistentní prefix, witness před lokálním ledgerem, padělaný podpis, stale nonce a souběžný lokální append selhají bezpečně. Akceptace používá skutečné SQLite pro oba registry a kryptograficky podepsané challenge, bez reálných exportů; nejde o produkční síťový deployment. **Není to zdrojový durable event→witness ACK, zpracování revokace ani oprávnění importovat:** všech šest H1-real bran a R3/R4 release gate nadále blokují reálné osobní údaje. Další krok musí zajistit transakční write-before-ack, živou Area ACL v okamžiku použití a provozně doloženou nezávislost svědka; další dry-run nesmí nahrazovat release důkaz.

**H1-real.8 — skutečný owner-private source/witness HTTP consumer (sloučeno PR [#394](https://github.com/Kocooour/AI-executive/pull/394), 2026-11-11):** [Akceptace a bezpečnostní kontrakt](HUMANWIKI-H1-REAL-SOURCE-WITNESS-STATUS.md). Nový výchozím nastavením **vypnutý** `GET /api/humanwiki/source-witness-status` propojuje platnou owner session, živé owner-private Area ACL, skutečně durabilní HMAC evidence ChatGPT/Claude source-specific withdrawal intentů a serverem připnutý Ed25519 HTTPS witness. Akceptace = reálný owner `POST` withdrawal intent → nový owner `GET` hlásí zaznamenaný záměr a nepokryté **vlastní** události vůči podepsanému witness prefixu → oddělený witness operator publish → `GET` hlásí pokrytí vlastních událostí podepsaným prefixem, aniž by došlo k importu, předstíranému completed withdrawal či zápisu checkpointu HTTP handlerem. Podepsaný globální prefix se nikdy nezobrazuje jako globální lag v uživatelském API: další událost **cizího** vlastníka nesmí změnit žádnou odpověď přihlášeného vlastníka (regrese P2 z review PR #394). Integrační testy používají reálné izolované soubory SQLite, HTTP route, TLS listener a testovací klíče; nejde o pouhý helper/dry-run, ale **není to produkční nasazení**. Oprávnění `importAuthorized`, `consentVerified`, `independentWitnessVerified`, `withdrawalComplete` zůstávají `false` a všechny R3/R4 a H1-real release brány trvají. Následující krok musí být provedení a doložení skutečné nezávislé witness infrastruktury a source-level durable event→witness ACK, ne další fixture-only iterace.

**H1-real.9 — read-only stav source intentů v Kontextu (nová FE integrační iterace, PR k review, 2026-11-11):** [Akceptace a bezpečnostní hranice](HUMANWIKI-H1-REAL-CONTEXT-SOURCE-STATUS-UI.md). Konkrétní uživatelský výstup = ve stávajícím Více → Kontext na desktopu i mobilu při **dvou samostatných server-side opt-in** příznacích zobrazený informativní panel, který teprve po výslovném kliknutí ověří na skutečném owner-private API stav ChatGPT/Claude zdrojových žádostí a pokrytí jejich událostí podepsaným svědkem. Nikdy neobsahuje export ani tlačítko k importu/souhlasu/mazání; prohlížeč neukládá výsledky do persistence/cache a zahazuje je při navigaci, logoutu, ztrátě spojení či skrytí. Source-specific metadata a global witness status neunikají mezi vlastníky; server zůstává konečnou ACL autoritou. Cílený unit/SSR test validuje parser a bezpečné chování stavu; nový výchozím nastavením neaktivní [focused Playwright test](../e2e/humanwiki-context-source-status.spec.ts) skutečně montuje Context na syntetickém izolovaném Next serveru, kliká na tlačítko, ověřuje odpovědi 200/404/malformed, mobilní Více → Kontext, návrat bez refetch, pozdní abort/blur a odstranění cookie při obnově. Vlastní [browser workflow](../.github/workflows/humanwiki-context-source-status-browser.yml) musí projít na přesném PR HEAD před review/merge, aniž by spouštěl full Browser E2E. Plná identity-swap/BFCache/VoiceOver akceptace na stagingu a release E2E zůstávají samostatnými branami. Další **produkčně blokující** krok se nemění: skutečná oddělená witness infrastruktura, source-level durable event→ack, off-backup antirollback, consent/withdrawal lifecycle, R3/R4 a owner schválení před reálným importem. **Žádný reálný zdrojový import ani produkční deploy.**

**R3-FE-4 + integrované R3 QA** = další milník, rozpočet 1–3 PR, akceptace: průchozí tok seznam → autorizovaný detail/úprava → zpět včetně offline/revokace.

**Backendový a UI krok R3-FE-4 — PR #370 (default-off):** PR přidává výchozně vypnutý stagingový zápis názvu projektu a výhradně explicitní nedestruktivní upgrade v25 → v26 ([kontrakt a postup](R3-PROJECT-TITLE-BE.md)). Editor hlavního UI **není pevně zakázán**, ale je **default-off**: cílené zapnutí v izolovaném stagingu vyžaduje současně všech sedm příznaků `TARGET_PROJECT_TITLE_EDIT_UI_FLAGS`, včetně samostatného `AI_EXECUTIVE_TARGET_UI_PROJECT_REAUTH_RECOVERY_ENABLED=true`; serverové write API zůstává nezávisle default-off. Implementovaná obnova odlišuje kódované `session_expired` od revokace, uchová obsah nedořešeného příkazu i neodeslaného konceptu jen v paměti do nového serverového ověření stejného aktéra (`principalBinding`); po reloadu blokuje nový zápis pro danou dvojici aktér–projekt, dokud read-only receipt nepotvrdí původní commit. **Zastavení / přijetí:** každá etapa se hodnotí podle skutečně použitelného toku a negativních testů: opakovaný import bez duplicit, nulový únik napříč Oblastmi a modely, explicitní review, změny v čase, odvolání zdroje s revalidací, export/restore, fallback bez indexu. Žádný staging helper, sémantický index ani metadata-only Gmail nelze prezentovat jako hotové učení o uživateli. Historický checkpoint z 2026-11-05 je v archivu níže; stav implementačních PR se řídí aktuálním checkpointem z 2026-11-09, nikoli dobovým popisem.

### Paralelní implementační větev UI — schválený Lumi Design v1.0 / PR #225 (2026-11-04)

**Implementační checkpoint 4. 11. 2026:** [UI-01b / PR #223](https://github.com/Kocooour/AI-executive/pull/223) (obnovitelné odkazy na úkoly a poznámky) a [UI-02a / PR #227](https://github.com/Kocooour/AI-executive/pull/227) (gated náhled čtyřpoložkové mobilní navigace Lumi v1.0) jsou **sloučeny do main**. To **neznamená dokončení UI-01/UI-02 ani aktivaci** cílových víceuživatelských rozsahů, oprávnění, produkčního R3 nebo migrace. Následující řádky definují **zbývající cílový kontrakt**, ne seznam již nesplněných historických dílčích PR.

**Rozhodnutí:** schválené nové UI v [UX/UI specifikaci](UX-UI.md#akceptace-jednoduchých-obrazovek-a-navigace) je **cílový stav**, nikoli runtime dodávka. Revize existující implementace na `main` potvrdila funkční legacy základy Home, Quick Capture, Attention, Calendar, projektové stránky, schvalování a offline indikace; ale mobil stále používá `MobileNav` s „Více“, `lib/view-url.ts` již po sloučení UI-01b (#223) umí typované URL cíle (view/project/task/note) včetně parseru a serializace; zbývá je plně propojit s navigačním stavem, Back/Forward, obnovením fokusu/draftu a bezpečnou serverovou autorizací cílového Area modelu, Today staví na `DayTimeline` a vyjímá časované úkoly ze seznamu, projektová stránka ukazuje kontext před úkoly a detail úkolu je rozsáhlý formulář. Cílový Area/ACL model R2d **není zapojen do produkčního klienta**. Nezaměňovat změnu specifikace v #225 s implementací těchto obrazovek; dřívější mobilní kořenové menu z #204 je **zrušené rozhodnutí**.

**Práce může začít hned**, paralelně s R2d. Nejdřív UI shell a každodenní pracovní plochy, potom bezpečné napojení na cílová data. Na větvích UI-01–UI-08 se **nesmí** vydávat legacy agregované „Vše moje práce“ za cílový autorizovaný globální filtr **Vše** ani za osobní obrazovku `Můj plán`, simulovat produkční práva `viewer/editor/admin`, zapnout default-off staging API nebo sdílet soukromá data na základě klientského filtru. Legacy čtení/zápis může být dočasný vývojový adaptér, nikoli autorita cílového ACL; příznaky pro přepnutí UX nesmějí přepnout produkční store. Tam, kde zatím neexistuje bezpečný endpoint, zůstane funkce vypnutá či pravdivě označená jako nepřístupná.

**UI-06 stav (2026-11-05):** UI-06a (#238) i UI-06b (#240) jsou sloučeny. ## Aktuální staging kontrakt

Celá R2 implementace je **staging-only**, za explicitními serverovými flagy, výchozí vypnutá a nad izolovaným úložištěm. Zelené CI samo o sobě neznamená aktivaci ani splnění produkčních ACL.

**Schéma a revize.** Staging schema v2–v4 přidává `tasks.revision`, `areas.policy_revision` a monotónní projektové revize; SQLite triggery je zvyšují i při návratu hodnoty do původního stavu (ABA). Starší staging schémata se **automaticky nemigrují**; izolované testovací úložiště se znovu vytvoří bootstrapem, produkční data nejsou dotčena. Smazání úkolu je ve schématu v7 dočasně zakázáno, aby se ID nemohlo znovu použít s revizí 0; trvalé tombstony a smazání úkolu přináší schema v8 (R2c.1, viz [architektura](ARCHITECTURE.md)). Aktuální staging schema je **v8**: v5 trvalé sessions (#152), v6 členství (#153), v7 cursor epochy Oblastí (#157), v8 tombstony, změnový záznam a audit smazání (R2c.1). Staré actor-only receipty z #138 vedou k odmítnutí staging preflightu.

**Identita a sessions.** Trvalé identity (`identities`) a sessions (`staging_sessions`, jen hash tokenu, životnost nejvýše 15 minut) s revokační epochou v SQLite (#152). Revokace platí okamžitě i na jiném serverovém procesu a po restartu. Sessions vydává jen operátorský CLI pro syntetické identity, HTTP endpoint pro vydání neexistuje. Stávající owner cookie zůstává pro zpětnou kompatibilitu stagingu. Nejde o produkční přihlašovací službu (passkeys, obnova účtu a pozvánky patří do R5).

**Čtení (`/api/target-staging/...`).**
- `GET tasks` a `GET projects`: stránkování (nejvýše 100 položek) s cursorem podepsaným oddělenou HMAC doménou ze serverového session secretu, vázaným na owner cookie nebo konkrétní trvalou session (#152), aktéra, rozsah, staging directory, restore generation a revizní epochy **pouze přístupných** Oblastí (`content_revision`, `policy_revision` a role, #157). Platí nejvýše 15 minut; změna cookie či session, konfigurace, obsahu nebo oprávnění v přístupné Oblasti nebo expirace vyžaduje nové načtení od první stránky, změny v nepřístupných Oblastech cursor nezneplatní. Cursor není autentizační token a nevolí identitu ani rozsah; actor, Oblast ani scope nelze dodat klientem.
- `GET tasks?scope=shared|my-plan` (#154): úkoly sdílených Oblastí podle aktuálního členství a `Můj plán` (soukromé + mně přidělené sdílené). Před uvolněním odpovědi se znovu ověří session a pak členství, role a `policy_revision` každé přispívající Oblasti; zastaralá stránka vrací 409 `read_stale_reload`, zastaralý detail nerozlišitelné 404. Cursor revize jsou indexované podle Oblastí (#157).
- `GET tasks/[taskId]` a `GET projects/[projectId]`: jediné preflightované snapshot čtení v autentizovaném SQL. ID je jediný parametr cesty, omezený na 512 UTF-8 bytů bez krajních mezer a řídicích znaků. Detail úkolu vrací soukromý úkol vlastníkovi a sdílený úkol aktuálnímu členovi Oblasti (#154); detail projektu zůstává jen pro vlastníka. Neznámé, cizí a nepřístupné položky vracejí nerozlišitelné 404 bez cache. Projekt vrací jen `id`, `title`, `areaId`, `areaKind=private`. Detail úkolu vrací navíc title CAS `snapshotRevision` ze stejného snapshotu, u sdíleného úkolu jen editorovi a adminovi (#158).
- `GET tasks/[taskId]/audit`: cizí, sdílené a neexistující úkoly vracejí nerozlišitelné 404; jinak nejnovějších 50 záznamů vlastního aktéra, aktuální Oblasti a restore generace; pouze `revisionBefore`, `revisionAfter`, `committedAtMs`.
- Každý požadavek znovu ověřuje cookie a ACL v izolovaném čtecím podprocesu s limity souběhu, času a velikosti odpovědi. Nejde o náhradu produkčního zátěžového testu.

**Zápis názvu úkolu.** Samostatný, výchozí vypnutý flag `AI_EXECUTIVE_TARGET_STAGING_HTTP_WRITE_ENABLED=true` nad čtecím flagem.
- `GET`/`PATCH tasks/[taskId]/title`: vlastní soukromý úkol a sdílený úkol pro editora a admina (#158); viewer, nečlen, cizí soukromý a neexistující úkol dostanou nerozlišitelné 404. CAS token pokrývá revizi úkolu, `policy_revision` efektivní Oblasti a restore generaci. Write ACL se opakuje uvnitř `BEGIN IMMEDIATE` s task/policy revizí a restore generation. Idempotentní receipt je vázaný na aktéra + úkol + UUID příkazu; změna payloadu pod stejným UUID je konflikt.
- Každá úspěšná změna má ve stejné transakci obsahově úspornou auditní událost (bez textů názvů). Replay a no-op nevytváří další záznam, selhání auditu vrací celý zápis. Prozatímní minimální 90denní ochrana před smazáním a tvrdý limit 4096 událostí; při nasycení se zápis bezpečně odmítne.

Hraniční chyby mají vlastní kódy: neplatný vstup 400 (případně jiný stav `HttpInputError`, např. příliš velké tělo), chybějící, odvolaná nebo expirovaná session 401 (ověřuje se i po návratu čtecího podprocesu), cizí origin 403, rate limit 429 s `retry-after`, nedostupná nebo změněná staging konfigurace 503. `not_recorded` neopravňuje k nebezpečnému opakování; retry znovu prochází ACL, generací a CAS.

**Příkaz členství.** `POST areas/[areaId]/members` (#153): idempotentní admin příkaz přidání, odebrání a změny role s receiptem, CAS na `policy_revision`, ochranou posledního admina a zrušením přiřazení odebranému nebo na viewer sníženému členu.

**Stále neimplementováno:** změnový feed (změnový záznam a smazání úkolu s tombstony přináší R2c.1), sync a identity-scoped cache (R2c), anti-rollback obnova ze zálohy (R2c), audit zamítnutých pokusů a přímých SQL úprav, auditní časová osa (`tasks/[taskId]/audit`) sdílených úkolů, produkční retence/export/archivace auditu, UI ani produkční aktivace.

## Další iterace: R2c — synchronizační protokol cílového modelu a identity-scoped cache (staging)

**Výchozí rozhodnutí:** legacy úložiště (`GET/PUT /api/store`, globální snímek) a cílový staging store zůstávají **oddělené**. R2c nestaví nový protokol přestavbou legacy `PUT`. Cílový store snímek **nikdy nepřijme**, každý zápis je per-item příkaz. Legacy klient zůstává na legacy úložišti až do cutoveru (R4). Bariéra pro staré klienty proto znamená, že cílové endpointy odmítnou každý mutační požadavek bez explicitní verze protokolu nebo v tvaru snímku, a to **před jakoukoli mutací**. Existující legacy restore fence `409 code:"restored"` na `/api/store` a owner routách ([architektura](ARCHITECTURE.md)) zůstává beze změny. Mimo rozsah R2c je jen předčasná sync bariéra pro variantu se zachováním a migrací legacy dat.

**Cíl:** na izolovaném stagingu dokázat úplný synchronizační cyklus pro 2–3 syntetické identity: stažení autorizovaných změn, offline fronta příkazů, konflikty, odvolání přístupu a obnova ze zálohy. Nic nesmí uniknout přes klientskou cache a nic se nesmí potichu ztratit.

**Akceptační scénáře (syntetické identity A admin, B editor, C viewer, D nečlen):**
1. B offline upraví název sdíleného úkolu, mezitím ho A smaže. Po připojení B dostane konflikt nebo tombstone, jeho změna se neztratí potichu (koncept zůstane k dispozici) a smazaný úkol se znovu nevytvoří.
2. B offline zařadí do fronty tři změny, mezitím ho A odebere z Oblasti. Po připojení server všechny tři odmítne, klient smaže data té Oblasti i frontu a ohlásí B 3 neodeslatelné změny. Feed B nevydá žádný obsah Oblasti.
3. Revokace session C: další požadavek feedu vrátí 401 `session_revoked` a klient smaže jmenný prostor C. Naproti tomu vypršení session B s neodeslanými změnami nic nesmaže: po přihlášení téže identity se změny odešlou.
4. Obnova staging úložiště ze zálohy pořízené před odebráním B a revokací C: dokud procedura obnovy neskončí, server vrací 503 bez dat. Potom starý cursor vrátí `resync_required`, klient vyprázdní cache a stáhne nová data a žádný starý příkaz z fronty se do nové generace automaticky nezapíše. Neodeslané změny k nadále přístupným položkám zůstanou jako lokální koncepty s ohlášeným počtem. B, odebraný po záloze, přijde o data i frontu té Oblasti s ohlášeným počtem; C, jehož session byla odvolána před obnovou, dostane `session_revoked` a klient smaže jeho jmenný prostor. Obnova nevrátí odebrané členství, odvolané sessions ani právo zápisu a revokační epocha se nevrátí zpět (anti-rollback brána z R2c.4).
5. Dva klienti téže identity souběžně mění tentýž úkol: právě jeden zápis uspěje, druhý dostane 409 se zachovaným konceptem. Opakování se stejným `commandId` nezpůsobí dvojí změnu.
6. Legacy klient poslaný na cílový endpoint (tvar snímku, bez verze protokolu nebo bez `writeAreaId`) nic nezapíše.
7. D z feedu nezjistí existenci, počet, revize ani tombstony úkolů Oblastí, kde není členem, a nedostane pro ně ani oznámení ztráty přístupu. Když A přidá D do Oblasti, D dostane úplný aktuální stav Oblasti včetně nezměněných úkolů. Člen odebraný a znovu přidaný nevidí změny z období, kdy členem nebyl.

- **Read/write bezpečnost:** neautorizovaný aktér nemůže číst ani upravit osobní či cizí sdílenou Oblast; viewer nezapisuje, editor/admin jen dle aktuálního členství, projektové děti vždy dědí Oblast.
- **Transakční konzistence:** souběžná změna oprávnění/revize/generace během zápisu vede k bezpečnému zamítnutí; opakování příkazu nezpůsobí dvojí změnu, audit a Undo neobejdou ACL.
- **Synchronizace a revokace:** starý snapshot/pozdní offline fronta nemění novou generaci, po revokaci nevytéká obsah ani přes cache či odvozené kanály; uživatelské profily oddělené. Offline ztracená práva nelze zpětně odebrat již zkopírovanému obsahu, ale server musí po připojení přístup odmítnout.
- **Funkční úplnost:** autorizované task/project/detail a Home/Today/Inbox/Upcoming/search výsledky jsou vzájemně konzistentní. `Můj plán` obsahuje soukromé a mně přidělené sdílené úkoly, `Sdílené` také nepřidělené oprávněné položky.
- **Testování:** syntetické 2–3 identity, pozitivní i negativní scénáře pro čtení/zápis/souběh/offline/revokaci, pravidelné `PR Checks`, [povinné okamžité code review s čistým posledním kolem](../AGENTS.md#mandatory-code-review-on-every-pr) (recenzent nemusí být nezávislý). Celá Browser E2E sada **jen před nasazením** dle [AGENTS.md](../AGENTS.md).

## Co se nemění

- **D2a–D2c legacy migrace a historické backfilly nejsou na kritické cestě.** Dosavadní implementace/testy se nemažou; pokud se později objeví hodnotná data, rozhodne se o jejich konkrétním převodu samostatně.
- Připravovaný čistý model lze vytvářet a testovat pouze v **odděleném úložišti**. Žádná změna roadmapy ani merge PR nedává souhlas ke smazání/nahrazení aktuální produkční DB, účtů, mailu, kalendáře, tokenů či offline cache.
- Před případným resetem: explicitně schválený rozsah, ověřená archivní záloha, test obnovy, inventura zařízení a konektorů. Nespouštět pozvánky ani skutečné sdílení před bezpečnostními branami.
- Product contract: jen dva uživatelské datové prostory **Osobní / Sdílený**; tři **globální** čtecí rozsahy **Vše / Osobní / Sdílené**; **Můj plán** je samostatná osobní úvodní obrazovka, nikoli další globální rozsah. Oblast je jediný organizační štítek a zdroj viditelnosti projektů a samostatných úkolů; žádné implicitní sdílení.
