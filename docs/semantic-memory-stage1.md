# Semantic knowledge memory — Stage 1 contract and evaluation gate

Status: implemented canonical invalidation outbox and content-free derived manifest. This stage does **not** ship semantic retrieval, embeddings, a model, a vector index, new account integrations, or user-facing similarity results. `context.search` remains the existing lexical path.

## Canonical and derived boundary

- `entities`, `context_claims`, `context_subjects`, `context_sources`, and `context_evidence` are canonical. SQLite triggers append an object ID, workspace and operation to `semantic_index_outbox` in the same transaction as each insertion, update or deletion. A rollback removes both. A workspace move queues both the old and new workspace.
- The outbox contains no title, body, excerpt, query or vector. It is local server state and excluded from backups. A restore increments `restoreGeneration` and enqueues a full rebuild after clearing old outbox rows. A new migration also enqueues a full rebuild for existing installations.
- A regular full-snapshot client save preserves unchanged canonical entity rows. It performs only real inserts, deletes, and changed-row updates, so one edited task does not enqueue all workspace entities or force a spurious global rebuild.
- Claim `policyFingerprint` hashes the effective sensitivity **and deterministically ordered source/evidence link IDs, workspaces, revisions and relevant source policy metadata**. A source replacement or policy revision changes the fingerprint even if the maximum sensitivity stays equal. The digest contains no raw excerpts, titles or source locators.
- `semantic-index-v1.sqlite` lives beside the canonical database and is reconstructible. Stage 1 stores only the manifest: index version, canonical ID and revision, workspace, type, nullable section ID, sensitivity, policy fingerprint, nullable language/model version and indexed time. It has no independent review or write authority. Source and evidence changes also invalidate the canonical workspace of every affected claim, even if the linked source/evidence belongs to a different workspace. The next reconciliation recomputes each claim's strictest source restriction.
- `reconcileSemanticManifest()` rebuilds the affected workspace from canonical rows, commits the derived transaction, then acknowledges queue rows. Interruption before acknowledgement replays safely. If the derived file is lost, the next run rebuilds from canonical data. A pending outbox row means the manifest is incomplete. No retrieval path may use it without rechecking current canonical workspace, sensitivity, permission, archive/deletion, claim review, source access and revision **before ranking and before serialization**. In particular, no historical revision bypasses current access.
- Stage 1 does not schedule this reconciler in the production service. The outbox is capped at 1,000 rows by a transactional SQLite trigger: overflow discards granular events **only after adding an obligation to rebuild all workspaces** (`queue_compacted`). The manifest must be treated as incomplete until that full rebuild has succeeded and the marker is acknowledged. Subsequent writes remain queued. A later release must supply a bounded worker, checkpoints and monitoring. The manifest is dormant infrastructure; nothing in the live UI or API reads it or advertises semantic readiness. Current lexical search does not depend on the worker. A batch processes at most 1,000 captured events and acknowledges only their IDs, so a concurrent write remains queued for another pass.
- The manifest intentionally does not claim that note sections, languages, fingerprints or source permissions have been fully indexed. Stage 2 must add a section extractor and server-side policy checks, a worker schedule and periodic reconciliation before advertising completeness. Missing or unknown sensitivity fails closed as `restricted` (including entities with no `properties.sensitivity`); it must not be silently interpreted as public/normal. The index must never be included in app export or sent to the PWA, MCP or a provider.

## Fixed pass/fail gate for Stage 2 evaluation

Freeze the holdout and its judgments before model testing. The synthetic [development corpus](semantic-memory-corpus.json) checks language and policy cases but cannot alone establish production relevance. A separate, owner-approved, non-production holdout must contain at least 120 queries and 600 canonical document/section judgments: at least 70 Czech queries with inflection or paraphrase, 30 mixed Czech/English, 20 exact identifier/title queries, 20 negative or permission cases, and at least 3 independent judgments per candidate (0/1/2 relevance, majority adjudication). Exclude names, emails, tokens, private excerpts, live server exports and direct production content. Record dataset hash, judging instructions and category counts; never record protected text in telemetry.

| Gate | Pass threshold | Measurement |
| --- | --- | --- |
| Relevant retrieval | recall@5 ≥ 0.85, nDCG@10 ≥ 0.78, and nDCG@10 ≥ lexical baseline + 0.08 overall | Macro average per query; report Czech and mixed separately, each ≥ 0.72 nDCG@10. Exact-ID/title must not regress versus lexical. |
| Security | Zero unauthorized IDs, titles, counts, excerpts, vectors or autocomplete hints in every workspace/sensitivity/revocation test | Test before and after ranking and serialization, with archived/deleted/restricted source and stale historical revision. One leak fails the stage. |
| First result | p95 ≤ 800 ms, p99 ≤ 1,500 ms | Warm server, 20 concurrent requests, 1,000 measured searches, local inference included, lexical baseline reported alongside. |
| Incremental update | p95 ≤ 10 s from committed canonical change to available current result | 1,000 mixed inserts/edits/deletes across 10 workspaces; no stale result may be served during lag. |
| Full rebuild | ≤ 30 min for 10,000 1 KB sections; resumption after process kill within 2 min | Fresh rebuild and interrupted restart on the same host; completeness false until verified. |
| Resource budget | Peak added RSS ≤ 2 GiB; index disk ≤ 5 GiB and ≤ 3× canonical indexed text | Measure p95 and peak during steady queries plus rebuild; report OS file cache separately. |
| Model package | Downloaded artifacts ≤ 2 GiB, verified checksum and origin | No external content egress during installation, inference or indexing. |
| Hardware | 4 vCPU, 8 GiB RAM, x86_64, CPU-only, 10 GiB free disk | All thresholds must pass on this reference class or Stage 2 remains lexical. No GPU assumption. |

Use a fixed software revision, dataset SHA-256, model checksum, locale and hardware profile. Run three repetitions of each performance experiment; take the worst passing aggregate. Benchmark lexical and candidate models on the same authorized corpus and search scope. BGE-M3 remains a candidate only. If any relevance, privacy, latency or resource gate fails, keep lexical retrieval as the supported path; report the failed metric, retain the model/index disabled, and do not present semantic coverage as complete. If indexing crashes or model artifacts are missing, exact and metadata search continue with explicit partial coverage.

## Recovery and retention contract

Keep canonical backups and provenance under the existing backup policy. The manifest and any future vector/content copies are disposable, scoped to a workspace and subject to the strictest current source restriction. A restoration or source erasure invalidates old derived state before any search. Stage 2 must bound worker batches, use resumable checkpoints, enforce retention and confirm a full count/revision reconciliation before declaring a rebuild complete. Stage 1 deliberately has no app or MCP route to the manifest.
